## 一、演练的两个核心教学目标

带练之前务必想清楚：这个演练**不是**"教一遍TDD流程"，而是要让学员亲手体会两件容易被忽略的事，讲课/巡场时始终围绕这两点展开：

1. **"骨架先行"不等于违反"测试先行"**——这是学员最容易卡住的认知点，见下文"疑问一"。
2. **CDD（注释驱动开发）的价值在于"分步、可追溯"，不分步就没有教学效果**——这是演练最容易失败的地方，见下文"疑问二"。

如果巡场时发现学员两个问题都没有困惑、一路顺畅做完，反而要停下来确认他们是不是跳过了思考直接抄代码。

---

## 二、疑问一：没有类骨架，测试代码怎么编译/运行？

**学员可能的疑问**："TDD不是说先写测试吗？可是`Account`类都不存在，测试代码怎么可能跑得起来？"

**标准解答**（学员文档4.2已经写了，但讲师要能脱稿讲清楚，尤其口头答疑时）：

- TDD"测试先行"约束的是**业务逻辑的实现顺序**，不是"类/方法骨架是否存在"。
- 骨架（字段、构造函数签名、方法签名）本身不包含任何判断和计算，只是让测试代码能被编译器/解释器识别。
- 如果没有骨架：
  - Java：测试代码直接编译失败，是`Error`
  - Python：`import Account`直接抛`ImportError`
  - 二者都不是TDD要的"Red"，而是代码写错了
- 正确顺序：**先有空骨架 → 再写测试 → 跑测试看到断言失败（真正的Red）→ 再实现业务逻辑**。

**巡场检查点**：Red阶段跑完后，让学员说出"现在看到的是Failures还是Errors"，能答对说明这个概念真的建立了，而不是背了一句话。

## 三、疑问二：为什么AI一下子就把代码全写完了，练不出CDD的感觉？

这是本演练历史版本中最大的教学风险点，也是这次改版的核心动机，讲师必须重点盯防。

**问题根源**：如果把完整的类注释一次性丢给AI说"帮我实现"，AI几乎必然一次性生成整个类的完整代码。学员只能看到"生成前空实现"和"生成后完整实现"两个快照，中间过程完全消失，没法验证"这条注释确实驱动了这段代码"，CDD退化成普通的"写需求描述、AI一把梭"。

**现在的解法**：学员文档5.x把`transfer()`的实现拆成3个明确的增量，每个增量的AI提示词里都带有"严格要求"（明确告诉AI不要做什么），并且给出了每一步跑完测试后应该看到的确切数字：

| 阶段 | Java版检查点 | Python版检查点 |
| --- | --- | --- |
| Red基线 | `Tests run: 7, Failures: 7, Errors: 0` | `9 failed, 0 passed` |
| 增量①（构造函数/属性） | `Tests run: 7, Failures: 7`（transfer仍为空） | `9 tests: 2 passed, 7 failed` |
| 增量②（参数+业务规则校验） | `Tests run: 7, Failures: 4`（3个异常测试变绿） | `9 tests: 5 passed, 4 failed` |
| 增量③（原子转账逻辑） | `Tests run: 7, Failures: 0` | `9 passed` |

**巡场时重点检查**：

- **最常见的翻车场景**：学员在增量②这一步，提示词里明明要求"校验通过后直接return，不要写转账逻辑"，但AI依然把余额更新逻辑一起写了，导致4个正常场景测试也提前变绿（本该是`Failures: 4`，结果直接变成`Failures: 0`）。这不是学员的错，是AI"顺手做完"的倾向；发现后**不要让学员直接跳到下一步**，而是引导他们：
  1. 回头看这次AI生成的完整代码，指出多写的部分在哪
  2. 讨论为什么会发生（提示词不够明确？没有说"严格要求"？）
  3. 重新按提示词的约束发一遍，把范围收紧
  4. 这个"发现越界 → 打回重来"的过程本身就是本演练要练的纪律，比顺利通过更有教学价值，不要因为赶进度而跳过。
- 如果学员为了省事，把5.2/5.3/5.4三个提示词直接连续粘贴发给AI而不中途检查测试结果，等于走了一次性生成的老路，只是分成了三次对话——提醒他们**每一步都要真的运行一次测试**，看到数字变化再继续。
- 5.5节"反例对比"建议现场演示一次给学员看："如果我现在把完整注释一次性丢给AI会发生什么"，直观对比"一步到位"和"分步可追溯"的差异，比讲道理更有说服力。

## 四、课前准备检查清单

- [ ] 确认学员的AI工具支持多轮对话，且能在对话中记住"上一步的约束"（如果每次都是全新会话、AI看不到之前的"严格要求"，分步流程会失效）
- [ ] Java环境：确认Maven可用；如果学员环境没有Maven或搭建成本高，提前准备好[附录A](AI注释驱动TDD银行转账演练v2.0.md#附录a纯jdk免maven环境搭建)里提到的4个jar包离线分发（内网环境建议提前统一下载打包，避免现场卡在网络问题上）
- [ ] Python环境：确认`pytest`环境可用（Poetry或pip二选一）
- [ ] 提前跑一遍完整流程（Red→增量①②③→Refactor），确认当前AI工具版本生成的代码仍然符合各步骤的预期检查点数字——AI模型更新可能导致生成结果与文档示例略有出入，属正常现象，讲师要能现场判断"结果对不对"而不是机械对照文档

## 五、时间分配建议（供参考，按实际班级调整）

| 环节 | 建议时长 | 讲师动作 |
| --- | --- | --- |
| 演练目标讲解 + 疑问一答疑 | 10分钟 | 讲清"骨架先行 vs 测试先行"，可结合本文档第二节口述 |
| 阶段零 + Red阶段（4.1-4.4） | 15-20分钟 | 巡场确认每个学员都跑出`Failures: 7`（或Python的`9 failed`），而不是Errors |
| Green阶段增量①②③（5.1-5.4） | 30-40分钟 | 重点巡场，逐桌确认增量②没有越界；对翻车的学员现场引导"打回重来" |
| 反例对比演示（5.5） | 5分钟 | 讲师现场演示一次"一次性生成"，对比效果 |
| Refactor阶段（六） | 10-15分钟 | 相对宽松，可作为提前完成学员的拓展任务 |
| 总结答疑 | 10分钟 | 收集常见卡点，结合本文档第三节的翻车场景讲解 |

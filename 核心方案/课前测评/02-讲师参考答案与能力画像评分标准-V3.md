# 课前测评 · 讲师参考答案与能力画像评分标准（V3）

> 仅供讲师/项目组内部使用，请勿分发给学员。

## 使用方式

1. 课前1~2天收集学员测试卷（纸质或问卷形式均可），按本文档评分。
2. 单选题按"知识维度/对应课程模块"归类统计对错，快速定位班级整体的薄弱模块，据此决定课上哪些环节需要加重讲解、哪些可以一带而过。
3. 第4、5、7题新增了 **E."不了解，凭感觉选的"** 选项，评分时请把"选E"与"选错(A/B/D中的错误项)"分开统计——前者代表"零先验知识"（需要从头讲概念），后者代表"已有认知但存在误解"（需要针对性纠偏），两种情况的授课策略不同，具体见下文"新概念先验知识诊断"一节。
4. 第20题（自评频率）与主观题21/22不计对错，用于给学员分层（建议按"高频实践组"和"初学摸索组"混合分组，形成传帮带），并提前掌握团队在安全合规认知上的真实盲区，针对性设计课上的"AI失效场景"讨论案例。
5. 建议同时统计"opencode / GitHub Copilot"实际使用比例，课上工具演示环节可据此调整两个工具的演示配比。

> ⚠️ 本评分标准对应 **V3 版测试卷（01-学员课前测试卷-V3.md）**。V3 相对 V2 的调整：
> - 第5题由"三闸口框架"（课程自造术语，学员课前不可能接触）改为考察"Skill机制"，与第4题MCP并列考察AI工具生态认知；
> - 第7题由"SDD+CDD+TDD三分法"（CDD非通用术语）改为考察"SDD vs Vibe Coding"的核心区别，更贴近学员已有的真实使用经验；
> - 第14题由通用的"Playwright E2E是什么"（与AI无关的纯测试常识）改为"AI生成E2E脚本后人工复核要点"，拉回AI辅助主线；
> - 原第15题（自评使用频率）后移至第20题，作为"客观知识题→主观题"的过渡；原第16~20题依次前移为第15~19题；
> - 第4、5、7题新增E."不了解"选项，用于把"零先验知识"和"错误认知"分开统计。
>
> V2 的答案与本文档**题号、部分题目内容均不一致**，请勿混用。

## 新概念先验知识诊断（第4、5、7题 E选项占比）

这三题涉及的概念（MCP、Skill、SDD vs Vibe Coding）都是学员大概率课前从未系统接触过的，"选E"和"选错(非E)"传递的信息完全不同，建议分开统计并分别应对：

- **选E占比高**（如超过班级人数的一半）：说明这个概念对全班基本是"零基础"，课上必须从最基础的定义、动机讲起，不能默认学员有任何先验认知，且要多给具象的示例/演示，不能只讲抽象定义。
- **选错(非E)占比高，选E占比低**：说明学员对概念"有印象但理解有偏差"（比如把 Skill 当成模型微调，或把 SDD 和 Vibe Coding 定义说反），课上应重点用对比讲解、正反案例来纠偏，而不是从零介绍。
- **正确率本身较高**：说明团队已经在实际工作中接触过类似机制（哪怕没用过这个名词），可以适当压缩基础讲解时间，把课时让给进阶实践。

三题若均呈现"选E为主"，建议在模块二开场增加一段"AI工具生态全景图"的铺垫（MCP/Skill/Agent/IDE插件各自的定位与关系），再进入具体机制讲解，避免学员在后续动手环节因为基本概念不清而跟不上。

## 能力画像与班级整体诊断参考

### 单选题正确率分层建议（满分按19题计，第20题为自评不计入正确率）

- **≥80%（15题以上正确，满分19）**：具备较扎实的AI基础认知，课上可适当加快模块一、模块二的理论讲解节奏，把更多时间留给动手实践与跨章综合演练。
- **50%~79%（10~14题正确）**：认知参差不齐，建议保留完整的"①核心知识体系→②AI赋能全景→③演练要点"结构，尤其加强安全合规（第19题）与"AI是辅助非替代"（第6/11/15题）相关内容的讲解深度。
- **<50%（9题以下）**：团队对AI辅助研发整体较陌生，建议第1天适当延长模块一、模块二的时间，增加更基础的工具操作演示（GitHub Copilot / opencode 基本用法），并在每章"演练"环节降低任务难度、提供更完整的模板。

### 安全合规专项诊断（第19题 + 第6题 + 主观题22）

由于友邦咨询属金融行业、对安全要求高，这几题及主观题22的作答质量应作为**课程内容调整的核心依据**：

- 若第19题（数据出境合规）错误率较高，或主观题22回答空泛（答不出具体注意事项），建议在模块一"AI技术选型策略"及模块七"AI辅助编码核心应用场景"中，专门增加10~15分钟的"金融行业AI工具使用红线"专题讨论（可参照课程设计中"AI失效场景"专项讨论的建议，结合客户真实的数据分类分级要求定制案例）。
- 若普遍答得较好，说明团队已有基本的安全意识，课上可将该话题作为"深化"而非"启蒙"来处理，重点转向如何在合规前提下提升效率（如私有化部署工具的最佳实践、脱敏技巧等）。
- 第6题（代码责任归属）错误率高时，应在模块七"反模式警示"环节重点强化"开发者对合入代码负最终责任"的认知。

### 工具使用现状诊断（第20题 + 学员填写的"当前主要使用工具"）

- 统计 opencode / GitHub Copilot 的实际使用比例与熟练度分布，用于决定模块二"六层DevOps AI工具集"演示环节中两个工具的演示时长配比，以及模块七"AI辅助编码核心应用场景"动手实践环节的工具选择。
- 若团队中"偶尔用过/基本没用过"（C/D选项）比例较高，建议第1天课前准备阶段增加更基础的工具环境搭建与首次上手指导，避免后续动手实践环节因工具不熟悉而拖慢进度。
- 建议将第20题结果与单选题正确率交叉对比：若某学员自评"几乎每天都在用"但正确率偏低，说明其使用方式偏"Vibe Coding式"的经验积累、缺乏方法论沉淀，可作为课上第7题相关讨论的现身说法素材（征得本人同意后使用）。

### 主观题21诊断要点

重点关注学员描述中是否体现：
1. 是否有**具体、真实**的工作场景（而非泛泛而谈"用过Copilot写代码"）；
2. 提示词设计是否已具备基本的结构化意识（角色/背景/约束/格式）；
3. 对AI输出是否有**主动修改/校验**的习惯，还是"生成即用"。

若多数学员反馈"生成即用、很少修改"，应在模块七"反模式警示"环节重点强化"AI是高级实习生，代码所有权在开发者"的认知，并在动手实践评分维度中加重"人工修正点说明"的权重。

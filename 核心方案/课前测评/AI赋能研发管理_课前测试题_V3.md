## 第一部分：AI编程范式与工具链

### 【题1】三种AI编程范式的场景匹配

AI编程的三种范式：**Vibe编程**、**Spec驱动开发**、**Copilot增强**。

现在有4个实际的开发场景，每个场景对应一种最合适的AI编程范式。以下匹配中，**最不合理**的一组是：

A. 产品经理需要在2小时内做一个"用户反馈收集页"的可交互原型，给客户演示确认需求方向 → **Vibe编程**。因为这个场景的核心诉求是"快速出可见结果、允许不完美"，Vibe编程的意图驱动+快速迭代特征最匹配

B. 一个5人团队要开发"支付对账系统"的核心模块，涉及金额计算、多账户轧差、异常冲正等复杂业务规则，需要经过架构评审和测试验收 → **Spec驱动开发**。因为这个场景的核心诉求是"逻辑正确性、可审计性、团队协作一致性"，Spec的规格先行+规则驱动特征最匹配

C. 开发者每天编写CRUD接口时，需要频繁写 `getById`、`listByCondition`、`save`、`update` 等高度重复的样板代码 → **Copilot增强**。因为这个场景的核心诉求是"减少重复劳动、提高编码速度"，Copilot的上下文感知+实时补全特征最匹配

D. 一个创业团队需要在3天内上线一个MVP产品，包含用户注册、商品浏览、下单支付等完整流程，团队成员对技术栈不熟悉但希望快速验证商业模式 → **Spec驱动开发**。因为这个场景需要先写清楚规格才能保证代码质量，快速上线反而应该更注重前期规划

### 【题2】AI赋能建模的能力边界

AI大模型可以辅助生成多种建模产物。以下四种模型类型中，**AI最难以直接生成**的是：

A. 用PlantUML语言描述的C4架构图（上下文图、容器图、组件图）。PlantUML是纯文本DSL，AI可以像写代码一样逐行生成，再由PlantUML渲染引擎转为图形

B. 用Mermaid语法绘制的业务流程图（含泳道、决策节点、并行分支）。Mermaid同样是文本驱动的图表语言，AI能根据业务描述生成对应的标记语法

C. 用SVG代码绘制的基础架构拓扑图（服务器、数据库、网络设备的图形化布局）。SVG是XML文本格式，AI可以生成标签化的矢量图形描述

D. 直接输出Visio原生`.vsdx`格式的详细流程图文件（含精确坐标定位、自定义形状、主题样式）。Visio依赖其专有的二进制打包结构和GUI布局引擎，AI无法绕过Visio运行时直接生成合法的二进制格式文件

### 【题5】SOLID原则——依赖倒置

考察以下Java代码：

```java
// 版本A
public class OrderService {
    private MySQLOrderRepository repository = new MySQLOrderRepository();
    public void createOrder(Order order) {
        repository.save(order);
    }
}

// 版本B
public class OrderService {
    private OrderRepository repository;
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
    public void createOrder(Order order) {
        repository.save(order);
    }
}
public interface OrderRepository {
    void save(Order order);
}
public class MySQLOrderRepository implements OrderRepository { ... }
```

从"依赖倒置原则（DIP）"的角度，以下分析中**最准确**的是：

A. 版本B的最大好处是"可以在测试时注入Mock Repository"，方便单元测试——这是DIP的核心价值

B. 版本B让 `OrderService` 依赖接口而非具体实现，当需要从MySQL切换到PostgreSQL时，只需新增实现类而无需修改 `OrderService`——"高层模块不应依赖低层模块，两者都应依赖抽象"

C. 版本B引入了不必要的复杂性——接口+实现类的方式增加了代码量，在小项目中得不偿失

D. 版本B的改进方式与DIP无关——这实际上是"依赖注入（DI）"，DIP和DI是两个不同的概念

### 【题6】Epic-Feature-Story的拆解粒度

一个团队接到的Epic是"为在线教育平台建设直播授课功能"。AI拆解后产出了以下9条，产品经理将它们按Epic/Feature/Story三层归类。以下归类中，**归类最不合理**的条目是：

A. **Story层** — "作为学生，我希望能看到老师的共享屏幕，以便跟随教学内容操作"。理由：表达了一个完整的用户价值——谁（学生）、要什么（看屏幕）、为什么（跟教学），符合INVEST原则中I（Independent）的要求

B. **Feature层** — "互动答疑模块：学生可在直播中发送文字提问，讲师可查看并回复"。理由：是一个可独立交付的能力模块，包含多个子功能（发问、展示、回复），粒度介于Epic和Story之间

C. **Story层** — "建立直播间的数据库表结构（live_room、live_message、live_attachment三张表），定义字段类型和索引"。理由：是最底层的交付单元，细到具体技术实现，符合Story的Small原则

D. **Epic层** — "建设直播授课功能，支持屏幕共享、师生互动、课程回放，提升线上教学体验"。理由：表达了业务目标（提升体验）和价值主张，是对多个Feature的统括，粒度最大

### 【题7】MCP与Skill的协作边界

你的团队同时使用了MCP服务和Skill机制。架构师画了这样一张分工图让你确认：

| 场景                              | 推荐机制       |
| --------------------------------- | -------------- |
| AI需要查询第三方库的最新API文档   | MCP (Context7) |
| AI执行需求评审的标准操作流程      | Skill          |
| AI调用企业内部的用户权限系统      | MCP            |
| 定义"如何生成ADR文档"的模板与步骤 | Skill          |

对于这份分工，你的判断是：

A. 完全合理。MCP负责"连接外部能力获取上下文"，Skill负责"封装操作知识和流程"，分工清晰

B. 有一处不合理：查询API文档也应该用Skill而非MCP，因为这是"知识获取"而非"工具调用"

C. 有两处不合理：内部权限系统和文档查询都应该用Skill，MCP只适合"文件格式转换"类场景

D. 概念上有根本问题：MCP和Skill本质上是同一个东西的不同叫法，不应该做这种分工

### 【题8】PRD的AI生成与人工职责

产品经理使用AI生成了一份50页的PRD（产品需求文档），涵盖了功能描述、用户流程、异常处理、数据字典等。评审会上，开发团队发现：第23页和第41页对同一个"用户积分"的计算规则描述不一致；第35页描述的"退款流程"缺少一个关键的异常分支。

产品经理解释："这是AI生成的，我还没来得及逐页检查。"

对于这种情况的根本原因和责任归属，以下判断中**最准确**的是：

A. 主要责任在AI工具。如果工具更成熟、输出更可靠，产品经理就不需要花时间逐页检查，AI应该对生成内容的一致性负责

B. 主要责任在产品经理。AI生成的内容在任何场景下都只是"初稿"，产品经理有责任对交付给开发团队的文档质量负最终责任——特别是跨章节一致性和异常场景完整性这类AI容易出错的维度

C. 双方都有责任。AI应该更智能地检测跨章节冲突，产品经理也应该更仔细地检查——责任各半

D. 流程设计有根本缺陷。50页的文档不适合一次生成，应该改为分模块生成、分模块评审的迭代方式，这样即使有问题也只影响单个模块

### 【题10】TDD执行顺序的判断

一个开发者正在实践TDD开发"用户注册"功能。他在终端执行了以下操作序列：

```
1. 编写了 testUserRegistration() 测试方法
2. 运行测试 → 红灯（编译失败，因为 UserService.register() 方法还不存在）
3. 创建了 UserService 类和空的 register() 方法
4. 运行测试 → 红灯（断言失败，register() 返回 null 而非期望的 User 对象）
5. 在 register() 中实现了最简逻辑：return new User(request)
6. 运行测试 → 绿灯（测试通过）
7. 修改 register() 添加了密码加密、邮箱验证、重复检查
8. 运行测试 → 绿灯（仍通过）
```

关于步骤7-8，以下评价中**最准确**的是：

A. 步骤7是正确的重构阶段——在绿灯保护下放心地优化实现，测试持续通过说明没有破坏原有功能

B. 步骤7-8的做法是错误的——重构阶段只能"改善代码结构而不改变行为"，添加密码加密和邮箱验证属于"新增功能"，应该在新的红-绿-重构循环中完成

C. 步骤7是正确的，但步骤8有问题——添加密码加密后应该新增专门的测试用例来验证加密逻辑，仅依赖原有测试是不够的

D. 整个流程的顺序错了——应该先实现完整功能，再写测试，TDD的"先写测试"只适用于简单场景

### 【题11】AI生成代码的可维护性陷阱

团队用AI辅助开发了一个订单折扣计算模块，已运行3个月。现在业务提出新需求："新增一种'满3件打8折'的促销规则"。开发者打开代码后发现，原有的3种折扣规则（满减、百分比、买赠）全部写在一个150行的 `calculateDiscount()` 方法中，if-else层层嵌套。

以下关于这个问题根源的分析中，**最准确**的是：

A. AI不擅长设计模式。这种策略类问题应该用"策略模式"重构——将每种折扣规则封装成独立类，但AI无法理解这种抽象，只能生成过程式代码

B. 问题不在于AI，而在于开发者的使用方式——当初让AI生成折扣逻辑时，开发者的提示词聚焦于"实现满减规则"，缺少了对扩展性的架构约束（如"用策略模式、每种规则独立实现"），AI只是忠实地执行了当下的指令

C. 这是AI代码的通病——所有AI生成的代码都存在扩展性差的问题，因此AI只适合原型开发，不适合正式项目

D. 问题在于没有做代码评审——如果生成代码后进行了人工评审，评审人会指出if-else的扩展性问题并要求重构

### 【题12】AI辅助架构决策的人机协作

架构评审会上，团队用AI分析了"订单系统是否引入消息队列"这个决策。AI生成了一份详尽的利弊分析，关键结论是："建议采用同步返回+异步处理混合模式，核心下单流程同步完成，库存扣减等非核心流程通过消息队列异步处理。"

团队成员对此有不同看法：

- **甲**认为："AI的分析虽然全面，但它没有实际运行过我们的系统——AI不知道我们当前的订单量只有日均50单，引入消息队列的运维复杂度远大于解耦收益"
- **乙**认为："AI已经给出了明确建议，它分析了比我们更多的架构案例，我们应该相信AI的判断"
- **丙**认为："AI的结论本身是合理的，但甲提到的'当前量级'这个约束在AI分析中没有体现——我们需要把量级数据补充给AI，让它基于'日均50单'这个前提重新分析"

CTO要求你给出一个结论。以下判断中**最合理**的是：

A. 支持甲。AI的分析脱离实际——不了解团队运维能力和真实量级是AI架构分析的致命缺陷，应该以人的经验判断为准

B. 支持乙。AI分析的案例数量远超人能接触的范围，AI建议"同步+异步混合"是经大量实践验证的最佳模式，团队应该采纳

C. 支持丙。AI的架构方法论是对的（混合模式），但AI的分析缺少了对当前量级约束的考虑——这是人需要补充的关键上下文，人机协作的正确方式是"人补充约束、AI基于完整约束重新分析"

D. 终止讨论，先用AI推荐的混合模式做一版，上线后如果发现消息队列维护成本过高再改回去——实践出真知

### 【题13】HITL规划-审核-执行模式

AI辅助开发的"黄金标准"——**HITL规划-审核-执行模式**：人提出模糊需求 → AI生成实现思路 → **人决策与审核（关键步骤）** → AI执行具体代码。这种模式的核心价值在于：在思路阶段纠错成本极低（改文字远比改代码容易）、消除歧义（模糊需求→具体方案）、避免生成无效代码。

现在有四个开发场景，以下分析中**最需要采用HITL模式**的是：

A. 开发者需要为一个已有100+个接口的项目新增一个简单的CRUD接口（查询用户列表），数据模型和代码风格都已有明确模板。直接用AI生成代码后人工检查即可，HITL的"先审思路再写代码"反而拖慢节奏

B. 产品经理需要对一个上线3个月的电商系统实现"跨店满减优惠计算"功能，涉及跨店分摊、与已有优惠叠加、部分退款回退——逻辑复杂且一旦出错直接影响财务对账。如果AI直接生成代码后发现逻辑错误，重写成本极高，必须在写代码前审核AI的思路

C. 实习生想用AI快速生成一个"个人博客"的前端页面，目标是展示自己的作品集。页面交互简单，即使AI生成的代码不尽人意也可以手动调整——HITL的完整流程对于个人小项目过于繁琐

D. 运维工程师需要用AI写一个"自动清理30天前日志"的Shell脚本，逻辑清晰且可独立验证（运行后检查日志是否被删除）。脚本只有十几行，AI直接生成后测试即可，无需先审核AI的思路

### 【题14】AIOps的概念定位

某企业运维团队正在规划智能运维平台建设。他们目前已有成熟的ITIL流程（事件/问题/变更管理）、DevOps CI/CD流水线、SRE监控体系。对于"引入AI后，现有体系如何处理"这个问题，团队内部有四种声音。以下观点中**最符合AIOps定位**的是：

A. "既然上了AIOps，ITIL那套流程就可以逐步废除了——告警自动聚合、根因自动分析、RCA自动生成，传统的事件管理和问题管理流程会被AI完全取代"

B. "DevOps、SRE、ITIL是AIOps的三大支柱，AI是串联它们的胶水——AI不应替换这些框架，而是在每个框架内部增强效率：让ITIL的变更审批有智能风险评分、让DevOps的部署有智能灰度策略、让SRE的监控有智能异常检测"

C. "AIOps的精髓在于用AI模型替代人工经验——以前靠运维老兵的直觉判断故障根因，现在靠机器学习模型就够了。人的价值主要在模型训练阶段，日常运维应该最大化自动化"

D. "ITIL、DevOps、SRE是三套独立的体系，各有各的工具和方法论。AIOps是在这三套体系之上再建一层统一的AI大脑，由上而下地指挥各体系运转"

### 【题15】AI识别精益浪费后的改进闭环

团队用AI扫描Jira数据，识别出两种浪费：开发到测试的平均等待时间3.2天、每个Sprint约15%的Story因缺陷返工。SM在回顾会上展示了这份AI报告，团队表示"有数据支撑，不错"，然后继续按原来的方式工作。两个月后，两项数据几乎没变。

对于"为什么浪费数据没有改善"，以下分析中**最准确**的是：

A. 改进的优先级判断出了问题。团队可能认为等待3.2天和15%返工在当前阶段不是最紧迫的问题——精益强调"全局优化"而非"局部极致"，在资源有限时，团队选择先解决更影响交付的其他瓶颈，这本身是合理的优先级决策

B. 团队把AI当成了"报告工具"而非"改进触发器"。AI完成了浪费的识别，但识别只是手段而非目的——如果回顾会上没有将发现转化为可执行的改进实验（如"下周试行开发完成即通知测试，目标将等待压到1天内"），数据自然不会变化。信息传递了，但没有转化为行动

C. AI识别出的浪费类型不对。等待3.2天可能不是真正的浪费——如果等待时间被用来做代码评审或知识传递，它实际上是必要的缓冲。AI缺乏区分"必要等待"和"真正浪费"的能力，团队有理由对AI的结论保持审慎

D. 问题出在SM的引导方式上。SM应该用具体数据驱动团队产生紧迫感——比如计算"等待浪费每年浪费XX人天≈XX万元"，让团队感受到财务冲击。只展示原始数据而缺乏量化的业务影响，团队自然没有动力改变

### 【题16】端到端测试的脆弱性诊断

CI流水线中的Playwright E2E测试频繁失败。调查日志发现以下三种典型失败模式：

| 失败类型   | 次数 | 典型错误信息                                                               |
| ---------- | ---- | -------------------------------------------------------------------------- |
| 选择器失效 | 23次 | `page.locator('#main > div:nth-child(3) > button.btn-primary')` 定位失败 |
| 断言超时   | 8次  | `expect(page.locator('.success-msg')).toBeVisible({timeout:5000})` 超时  |
| 数据冲突   | 5次  | 测试用的"testuser@test.com"账号被另一个测试同时使用                        |

关于这三种失败模式的修复优先级和策略，以下判断中**最合理**的是：

A. 优先修复选择器失效（最高频）。将脆弱的选择器 `div:nth-child(3) > button.btn-primary` 改为语义化选择器 `button[data-testid="submit-order"]`，并推动前端团队在关键元素上统一添加 `data-testid` 属性

C. 优先修复数据冲突（根因最深）。为每个测试运行创建独立的测试数据（如动态生成邮箱），从根源上消除测试间耦合

D. 三类问题的修复成本相当，按发生顺序逐个修复即可

### 【题17】AI工具合规性的风险处置

某金融企业采购了一款公有云AI编程工具。安全评估发现：该工具会将用户的提示词回传至海外服务器用于模型优化。根据金融合规要求，客户数据和业务逻辑不得出境。安全团队提出了这个问题后，管理层召开了专题讨论。

以下四种处理方案中，**最恰当**的是：

A. 采用数据分级策略：将代码和提示词分为"敏感"和"非敏感"两类——涉及客户数据、交易逻辑、系统架构的走内部工具，通用工具类代码和文档润色类任务继续使用该公有云工具。配套制定分类指南和员工培训，违规使用追责到人

B. 立即停用该工具，同步启动两条并行线：一是由安全团队在2周内完成替代方案评估（私有化部署模型、国内合规工具），二是由PM制定过渡期的临时开发规范（如禁用期间的人工代码审查增强措施），确保生产力不出现断崖式下降

C. 与工具厂商签署补充协议，要求其出具具备法律效力的数据隔离承诺（承诺中国区用户数据不出境、不用于模型训练），并在合同中加入违约赔偿条款。在法律保障到位后，允许团队在约定的合规框架内继续使用

D. 维持现状但建立内部监控机制：在网关层部署DLP（数据防泄漏）系统，对发往该工具API的请求进行关键字扫描和自动脱敏，拦截包含疑似敏感信息的请求。通过技术手段在数据到达海外服务器之前完成过滤

### 【题18】AI辅助需求变更的影响分析

以下四种处理方式中，**最合理**的是：

A. 接受变更，但从当前Sprint中置换出一个等量的低优先级Story——用AI分析出的5人天工作量做依据，让客户在"加导出"和"延期XX功能"之间做选择，而非简单答应或拒绝

B. 将AI影响分析报告发给客户和架构师，组织一次15分钟的快速讨论——展示变更的真实成本（5个模块、3张表），让客户基于完整信息自己判断"这个导出按钮值不值得这个代价"

C. 建议客户将此变更放入下个迭代的Backlog中——不是拒绝，而是根据AI的数据（工作量超出当前Sprint容量）建议合理排期，同时承诺在下个迭代规划时优先考虑

### 【题19】AI生成测试用例的人工复核重点

测试团队用AI生成了100条测试用例，执行后发现大部分集中在正常业务流程（用户正常登录、正常查询、正常提交），而边界值、异常路径、并发冲突等场景几乎空白。测试负责人要求人工复核时重点补充某类场景。

以下四种复核重点中，**最应该优先投入**的是：

A. 逐条核对AI生成的断言表达式是否与被测接口的实际返回结构一致——AI有时会编造不存在的字段名或错误的HTTP状态码，如果断言本身不准确，测试通过也可能是假阳性

B. 系统性地补充非正常场景用例——AI生成用例的已知弱点是偏好"快乐路径"，这正是人工复核不可替代的价值：边界值、异常输入、超时、并发冲突等场景需要测试人员基于业务理解主动设计

C. 检查用例之间的数据独立性——AI容易让多条用例共用同一个测试账号或初始数据，导致用例之间相互干扰。如果数据冲突不解决，任何用例的执行结果都不可信

D. 审查AI是否遗漏了需求文档中明确定义的业务规则——比如"VIP用户享受额外折扣""30天内重复购买触发风控"等，AI可能只覆盖了CRUD流程而跳过了业务特有的约束条件

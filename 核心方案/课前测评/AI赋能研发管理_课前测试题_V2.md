### 【题1】幻觉防控的资源分配

你们团队每月有约200条AI生成的需求条目进入评审。统计发现其中约15%（30条）存在不同程度的"AI编造"问题。PM提议：要么投入2人天/月做人工逐条复核，要么投入5人天做一次性的提示词框架+检索增强（RAG）建设。已知每遗漏一条编造需求进入开发，平均造成3人天的返工。

在预算紧张、只能二选一的情况下，以下决策逻辑中**最合理**的是：

A. 选择人工逐条复核。因为每次复核只需2人天，比一次性5人天投入更省预算，且人工判断准确率高于任何自动化手段

B. 选择提示词框架+RAG建设。因为一次性投入5人天后，后续每月的维护成本趋近于零，且每月节省的返工成本（30条×3人天=90人天）远超投入

C. 两种都不选，改为增加需求评审环节的人数。因为多人交叉评审能从根本上发现编造问题，比依赖AI工具或单人复核更可靠

D. 分两步走：先用2人天的人工复核跑一个月收集编造模式，再决定是否需要投入RAG建设。数据驱动决策比猜测更稳妥

### 【题2】Few-shot的工程化边界

你写了以下提示词模板让AI生成代码注释：

```
示例1：输入"用户登录" → 输出"验证用户名密码，返回JWT令牌"
示例2：输入"订单创建" → 输出"校验库存与优惠，生成订单并锁定商品"
示例3：输入"支付回调" → 输出"验证签名，更新订单状态，触发发货流程"
```

现在你需要AI为"退款审批"生成注释。实际输出是"接收退款申请，审批通过后执行退款，通知用户"。这个结果基本符合预期。但当你把这个模板交给另一个新人使用时，他反馈AI的输出质量很不稳定。

关于这个问题的根因，以下分析中**最准确**的是：

A. 3个示例太少，要给10-15个示例才能覆盖所有场景，这是Few-shot学习的固有局限

B. 示例间的映射规律不够显性化——AI需要自行推断"输入→输出"的隐含规则，不同输入触发不同推断路径，导致不稳定

C. 应该用微调（Fine-tuning）替代Few-shot，因为Few-shot本质上就不适合代码注释这类规范性任务

D. 新人可能用了不同的模型或参数配置，团队应该统一模型版本和temperature参数来解决这个问题

### 【题3】MCP与Skill的协作边界

你的团队同时使用了MCP服务和Skill机制。架构师画了这样一张分工图让你确认：

| 场景 | 推荐机制 |
|------|---------|
| AI需要查询第三方库的最新API文档 | MCP (Context7) |
| AI执行需求评审的标准操作流程 | Skill |
| AI调用企业内部的用户权限系统 | MCP |
| 定义"如何生成ADR文档"的模板与步骤 | Skill |

对于这份分工，你的判断是：

A. 完全合理。MCP负责"连接外部能力获取上下文"，Skill负责"封装操作知识和流程"，分工清晰

B. 有一处不合理：查询API文档也应该用Skill而非MCP，因为这是"知识获取"而非"工具调用"

C. 有两处不合理：内部权限系统和文档查询都应该用Skill，MCP只适合"文件格式转换"类场景

D. 概念上有根本问题：MCP和Skill本质上是同一个东西的不同叫法，不应该做这种分工

### 【题4】提示词的过度约束陷阱

团队为一个"自动生成周报"的AI任务设计了以下提示词片段：

> "只使用材料中出现的任务名称，不得自行添加任何任务。
>  每个任务的状态必须与JIRA系统中的当前状态完全一致。
>  周报的段落数必须等于任务数，每段不超过120字。
>  不得使用'优化'、'完善'等模糊词汇。"

运行两周后，PM反馈：生成的周报虽然"严格不编造"，但变成了纯粹的任务列表罗列，丢失了周报应有的"进展总结、风险预警、下周计划"等管理价值。

这个案例暴露了防幻觉策略中的一个典型问题，以下分析中**最准确**的是：

A. 应该放弃这种"约束式"的防幻觉策略，改用"事后人工审核"来保证质量，因为约束必然导致内容僵化

B. 约束条件只覆盖了"防编造"维度，遗漏了"输出价值"维度的引导——应该在约束之外增加"正向示例"（如给出一个优秀的周报示例），让AI在"不编造"和"有价值"之间找到平衡

C. 问题不在于提示词设计，而在于AI当前能力不足。等GPT-5或更强模型出来后，这类矛盾自然会消失

D. 应该把任务拆成两步：第一步AI只负责提取任务列表（严格约束），第二步由人来补充分析和建议（人的判断不可替代）

### 【题5】大模型选型的现实权衡

你参与一个金融企业的AI工具选型。三个候选方案的关键数据如下：

| 指标 | 方案A：公有云API | 方案B：私有化部署开源模型 | 方案C：混合架构 |
|------|----------------|-------------------------|---------------|
| 单次调用延迟 | 200ms | 800ms | 300ms（敏感数据走私有） |
| 月成本(1000次/天) | ¥3,000 | ¥25,000（含GPU服务器折旧） | ¥12,000 |
| 数据出境风险 | 存在 | 无 | 敏感数据无/非敏感有 |
| 代码生成质量评分 | 92/100 | 78/100 | 88/100 |
| 上线周期 | 3天 | 45天 | 30天 |

CTO要求"数据安全零容忍，但也要考虑研发效率不能大幅倒退"。如果这是你负责的决策，你会：

A. 选方案A。因为延迟最低、质量最高、成本最低、上线最快——数据出境风险可以通过"提示词中脱敏处理"来规避

B. 选方案B。既然CTO说了数据安全零容忍，就应该彻底消除风险——私有化部署是唯一满足合规要求的选择，研发效率可以后续优化

C. 选方案C。在敏感业务（如用户数据、交易信息）走私有化模型，非敏感业务（如通用代码生成、文档润色）走公有云——用架构分层实现安全与效率的折中

D. 暂缓选型。当前三个方案都有明显短板，等6个月后开源模型性能追上公有云后再做决策，避免选错方向造成更大成本

### 【题6】需求澄清中的信息不对称

业务方发来一份需求："我们需要一个报表系统，能看销售数据"。你用AI生成了18个澄清问题。业务方花了15分钟逐条回答后，你发现其中有7个问题的回答是"这个我们没想过"或"你们技术决定吧"。项目启动3周后，业务方频繁提出"这里和我想的不一样"。

回顾这个过程，以下反思中**最接近根因**的是：

A. AI生成的澄清问题质量不够好，应该换一个更好的提示词框架来生成更高水平的澄清问题

B. 澄清问题的方向偏了——18个问题里有过多技术实现细节（如"数据库选MySQL还是PostgreSQL"），但没有触及业务方真正关心的"报表长什么样、谁在什么场景下看、解决了什么决策问题"

C. 业务方配合度不够。如果他们在需求阶段多花1小时认真回答问题，后面的返工完全可以避免

D. 应该用原型替代澄清问卷——直接做一个可点击的报表原型给业务方看，让他们"看到再改"，比让他们"回答抽象问题"更高效

### 【题7】Epic拆解的粒度边界

你在拆解一个Epic："建设统一消息中心，支持短信、邮件、站内信三种渠道发送通知"。AI给出的拆解中，最底层的一个Story是"实现短信发送工具类 SmsUtil.send() 方法，支持单条和批量发送"。

关于这个Story的粒度是否合适，以下判断中**最准确**的是：

A. 合适。作为最底层的Story，粒度越细越好，细到单个方法级别能让AI更精准地生成代码，减少理解偏差

B. 不合适。"实现SmsUtil.send()"是技术任务而非用户故事——Story应该从用户视角定义价值，如"作为运营人员，我希望能选择短信模板并批量发送通知，以便高效触达用户"

C. 合适。Story的"小"是INVEST原则中"Small"的要求，细到单个方法级别完全符合这个原则

D. 不合适。但这个Story的问题在于没有拆分到"短信签名配置"和"短信正文渲染"两个更原子的操作，粒度还不够细

### 【题8】AI辅助架构决策的人机协作

架构评审会上，团队用AI分析了"订单系统是否引入消息队列"这个决策。AI生成了一份详尽的利弊分析，关键结论是："建议采用同步返回+异步处理混合模式，核心下单流程同步完成，库存扣减等非核心流程通过消息队列异步处理。"

团队成员对此有不同看法：

- **甲**认为："AI的分析虽然全面，但它没有实际运行过我们的系统——AI不知道我们当前的订单量只有日均50单，引入消息队列的运维复杂度远大于解耦收益"
- **乙**认为："AI已经给出了明确建议，它分析了比我们更多的架构案例，我们应该相信AI的判断"
- **丙**认为："AI的结论本身是合理的，但甲提到的'当前量级'这个约束在AI分析中没有体现——我们需要把量级数据补充给AI，让它基于'日均50单'这个前提重新分析"

CTO要求你给出一个结论。以下判断中**最合理**的是：

A. 支持甲。AI的分析脱离实际——不了解团队运维能力和真实量级是AI架构分析的致命缺陷，应该以人的经验判断为准

B. 支持乙。AI分析的案例数量远超人能接触的范围，AI建议"同步+异步混合"是经大量实践验证的最佳模式，团队应该采纳

C. 支持丙。AI的架构方法论是对的（混合模式），但AI的分析缺少了对当前量级约束的考虑——这是人需要补充的关键上下文，人机协作的正确方式是"人补充约束、AI基于完整约束重新分析"

D. 终止讨论，先用AI推荐的混合模式做一版，上线后如果发现消息队列维护成本过高再改回去——实践出真知

### 【题9】PRD的AI生成与人工职责

产品经理使用AI生成了一份50页的PRD（产品需求文档），涵盖了功能描述、用户流程、异常处理、数据字典等。评审会上，开发团队发现：第23页和第41页对同一个"用户积分"的计算规则描述不一致；第35页描述的"退款流程"缺少一个关键的异常分支。

产品经理解释："这是AI生成的，我还没来得及逐页检查。"

对于这种情况的根本原因和责任归属，以下判断中**最准确**的是：

A. 主要责任在AI工具。如果工具更成熟、输出更可靠，产品经理就不需要花时间逐页检查，AI应该对生成内容的一致性负责

B. 主要责任在产品经理。AI生成的内容在任何场景下都只是"初稿"，产品经理有责任对交付给开发团队的文档质量负最终责任——特别是跨章节一致性和异常场景完整性这类AI容易出错的维度

C. 双方都有责任。AI应该更智能地检测跨章节冲突，产品经理也应该更仔细地检查——责任各半

D. 流程设计有根本缺陷。50页的文档不适合一次生成，应该改为分模块生成、分模块评审的迭代方式，这样即使有问题也只影响单个模块

### 【题11】TDD执行顺序的判断

一个开发者正在实践TDD开发"用户注册"功能。他在终端执行了以下操作序列：

```
1. 编写了 testUserRegistration() 测试方法
2. 运行测试 → 红灯（编译失败，因为 UserService.register() 方法还不存在）
3. 创建了 UserService 类和空的 register() 方法
4. 运行测试 → 红灯（断言失败，register() 返回 null 而非期望的 User 对象）
5. 在 register() 中实现了最简逻辑：return new User(request)
6. 运行测试 → 绿灯（测试通过）
7. 修改 register() 添加了密码加密、邮箱验证、重复检查
8. 运行测试 → 绿灯（仍通过）
```

关于步骤7-8，以下评价中**最准确**的是：

A. 步骤7是正确的重构阶段——在绿灯保护下放心地优化实现，测试持续通过说明没有破坏原有功能

B. 步骤7-8的做法是错误的——重构阶段只能"改善代码结构而不改变行为"，添加密码加密和邮箱验证属于"新增功能"，应该在新的红-绿-重构循环中完成

C. 步骤7是正确的，但步骤8有问题——添加密码加密后应该新增专门的测试用例来验证加密逻辑，仅依赖原有测试是不够的

D. 整个流程的顺序错了——应该先实现完整功能，再写测试，TDD的"先写测试"只适用于简单场景

### 【题12】AI生成代码的可维护性陷阱

团队用AI辅助开发了一个订单折扣计算模块，已运行3个月。现在业务提出新需求："新增一种'满3件打8折'的促销规则"。开发者打开代码后发现，原有的3种折扣规则（满减、百分比、买赠）全部写在一个150行的 `calculateDiscount()` 方法中，if-else层层嵌套。

以下关于这个问题根源的分析中，**最准确**的是：

A. AI不擅长设计模式。这种策略类问题应该用"策略模式"重构——将每种折扣规则封装成独立类，但AI无法理解这种抽象，只能生成过程式代码

B. 问题不在于AI，而在于开发者的使用方式——当初让AI生成折扣逻辑时，开发者的提示词聚焦于"实现满减规则"，缺少了对扩展性的架构约束（如"用策略模式、每种规则独立实现"），AI只是忠实地执行了当下的指令

C. 这是AI代码的通病——所有AI生成的代码都存在扩展性差的问题，因此AI只适合原型开发，不适合正式项目

D. 问题在于没有做代码评审——如果生成代码后进行了人工评审，评审人会指出if-else的扩展性问题并要求重构

### 【题13】端到端测试的脆弱性诊断

CI流水线中的Playwright E2E测试频繁失败。调查日志发现以下三种典型失败模式：

| 失败类型 | 次数 | 典型错误信息 |
|---------|------|------------|
| 选择器失效 | 23次 | `page.locator('#main > div:nth-child(3) > button.btn-primary')` 定位失败 |
| 断言超时 | 8次 | `expect(page.locator('.success-msg')).toBeVisible({timeout:5000})` 超时 |
| 数据冲突 | 5次 | 测试用的"testuser@test.com"账号被另一个测试同时使用 |

关于这三种失败模式的修复优先级和策略，以下判断中**最合理**的是：

A. 优先修复选择器失效（最高频）。将脆弱的选择器 `div:nth-child(3) > button.btn-primary` 改为语义化选择器 `button[data-testid="submit-order"]`，并推动前端团队在关键元素上统一添加 `data-testid` 属性

B. 优先修复断言超时（影响最大）。将timeout从5000ms增加到15000ms，给页面更多加载时间，减少误报

C. 优先修复数据冲突（根因最深）。为每个测试运行创建独立的测试数据（如动态生成邮箱），从根源上消除测试间耦合

D. 三类问题的修复成本相当，按发生顺序逐个修复即可

### 【题14】上下文管理的分层策略

团队维护着以下4类信息资产，每次AI任务时都需要提供上下文。现在AI的上下文窗口限制为128K tokens，而一次任务平均需要45K tokens的上下文，团队每天执行约30次AI任务。

| 资产类型 | 大小(KB) | 更新频率 | 示例 |
|---------|---------|---------|------|
| A. 项目宪章与编码规范 | 8KB | 月度 | 命名规范、架构原则、禁止事项 |
| B. 当前Sprint的Story详情 | 25KB | 2周 | US-001~US-008的验收标准 |
| C. 第三方API文档 | 120KB | 季度 | 支付网关、短信服务接口文档 |
| D. 数据库Schema | 15KB | 每周 | 50张表的字段定义和索引 |

团队希望尽量减少每次任务时的重复上下文传输。以下分层策略中，**最合理**的是：

A. 将A、B、C、D全部打包成一个"Master Context"文件，每次AI任务时自动注入——虽然大但确保AI有全部信息

B. 按更新频率分三层：A（月度）和D（每周）做成固定注入的"系统提示词"、B（双周）做成任务时手动选择的"项目上下文"、C（季度）做成MCP按需检索的"外部知识"

### 【题16】故障分析中的"足够深入"

线上支付系统出现故障，排查过程如下：

- 第1次追问：为什么用户支付失败？→ 支付网关返回超时错误
- 第2次追问：为什么支付网关超时？→ 数据库连接池耗尽
- 第3次追问：为什么连接池耗尽？→ 有一个慢查询占用了大量连接
- 第4次追问：为什么有慢查询？→ 昨天的发布中新增了一个"全表扫描"的统计查询
- 此时有人提议"继续追问第5次：为什么发布时没有发现这个慢查询？→ 因为Code Review没有覆盖SQL执行计划检查"

另有人提出异议："已经找到全表扫描的问题了，修复它就行，追问到第4次就够了吧？"

关于这个分歧，以下判断中**最准确**的是：

A. 第5次追问是必要的。根因分析的目的是找到"可采取纠正措施的根本原因"，第4次只找到了技术根因（全表扫描），第5次找到了流程根因（Code Review缺少SQL检查），后者才能防止同类问题再次发生

B. 第4次追问就够了。5 Whys方法的核心是"找到直接原因并修复"，追问太多会陷入无限递归，导致分析瘫痪

C. 第1次追问就够了。故障分析的价值在于快速恢复服务，找到"支付网关超时"后直接重启服务或切换网关即可，追问深层原因会延误恢复

D. 应该重新从第1次开始，换一个追问方向。比如追问"为什么用户会感知到失败"而不是"为什么系统会失败"，聚焦用户影响而非技术细节

### 【题23】时间复杂度估算

以下方法用于在一个已按升序排列的数组中查找目标值：

```java
public int search(int[] sortedArray, int target) {
    int left = 0;
    int right = sortedArray.length - 1;
    while (left <= right) {
        int mid = left + (right - left) / 2;
        if (sortedArray[mid] == target) {
            return mid;
        } else if (sortedArray[mid] < target) {
            left = mid + 1;
        } else {
            right = mid - 1;
        }
    }
    return -1;
}
```

### 【题24】SQL查询优化

以下两个SQL查询返回相同的结果（查询"每个部门的平均工资"）。在100万条员工记录、20个部门的数据量下：

```sql
-- 查询A
SELECT d.dept_name, AVG(e.salary) as avg_salary
FROM departments d
LEFT JOIN employees e ON d.dept_id = e.dept_id
GROUP BY d.dept_name;

-- 查询B
SELECT d.dept_name, 
       (SELECT AVG(salary) FROM employees WHERE dept_id = d.dept_id) as avg_salary
FROM departments d;
```

假设 `employees.dept_id` 上有索引。关于这两个查询的对比，以下判断中**最准确**的是：

A. 查询A更快，因为JOIN+GROUP BY是一条语句，数据库可以一次扫描完成

B. 查询B更快，因为子查询可以独立缓存，每个部门的AVG只需计算一次

C. 两个查询性能基本等价，因为数据库优化器会将它们转换为相同的执行计划

D. 查询A更快，但差异不大——查询B的子查询对每个部门执行一次（共20次），每次都走索引，在大数据量下性能取决于优化器的具体实现

### 【题25】SOLID原则——依赖倒置

考察以下Java代码：

```java
// 版本A
public class OrderService {
    private MySQLOrderRepository repository = new MySQLOrderRepository();
    public void createOrder(Order order) {
        repository.save(order);
    }
}

// 版本B
public class OrderService {
    private OrderRepository repository;
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
    public void createOrder(Order order) {
        repository.save(order);
    }
}
public interface OrderRepository {
    void save(Order order);
}
public class MySQLOrderRepository implements OrderRepository { ... }
```

从"依赖倒置原则（DIP）"的角度，以下分析中**最准确**的是：

A. 版本B的最大好处是"可以在测试时注入Mock Repository"，方便单元测试——这是DIP的核心价值

B. 版本B让 `OrderService` 依赖接口而非具体实现，当需要从MySQL切换到PostgreSQL时，只需新增实现类而无需修改 `OrderService`——"高层模块不应依赖低层模块，两者都应依赖抽象"

C. 版本B引入了不必要的复杂性——接口+实现类的方式增加了代码量，在小项目中得不偿失

D. 版本B的改进方式与DIP无关——这实际上是"依赖注入（DI）"，DIP和DI是两个不同的概念

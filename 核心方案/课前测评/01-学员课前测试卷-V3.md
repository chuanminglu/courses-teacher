## 第一部分：单选题（共20题）

**1. 关于大模型"幻觉"（Hallucination）现象的成因与应对，以下说法最准确的是：**

A. 幻觉是训练数据标注错误导致的偶发故障，只要持续扩充高质量训练数据即可彻底消除
B. 幻觉源自模型"基于概率逐词预测"的生成机制，属固有特性，只能通过提示词约束、引入外部事实检索（RAG）、建立人工核验环节等组合手段降低发生概率，无法根除
C. 只要把提示词中的业务细节写得足够充分，幻觉发生概率即可降为零
D. 幻觉只出现在文本对话中，代码、SQL、配置文件等程序化输出不会产生幻觉

**2. 需要AI根据一段客户访谈记录生成用户故事时，以下提示词设计中最能避免"AI凭空编造需求"的是：**

A. 仅写明"请根据访谈记录生成用户故事"，让AI自由提炼
B. 要求AI"尽量多生成一些故事，宁可多也不可少"，以确保覆盖全面
C. 告知AI"你是一位资深产品经理，请发挥你的专业经验，补全访谈记录中缺失的信息"
D. 注明"只能基于材料中出现的事实生成，不得补充材料外信息，并逐条标注对应原文出处"，同时给出一个输入→输出的示例

**3. 关于提示词中的"Few-shot（少样本示例）"技巧，下列说法正确的是：**

A. 在提示词中给出少量"输入→正确输出"示例，让模型模仿示例中的映射规律生成新结果，适合有固定格式或风格要求的任务
B. 通过把 temperature 参数调低，让模型输出更稳定、更接近期望格式
C. 在模型回答后追加追问"你确定吗"，让模型自我纠正
D. 将复杂任务拆分为多个小步骤，逐次提问逐步完成

**4. 关于 MCP（Model Context Protocol）在AI开发工具链中的定位，以下描述最准确的是：**

A. 一种用于微调私有化大模型的训练框架
B. 一种提示词压缩算法，用于降低 Token 消耗
C. 一种开放协议，规范大模型应用与外部工具/数据源（如 GitHub、Playwright、数据库）之间的连接方式，使模型能按需调用外部能力获取上下文
D. 微软推出的AI编程助手品牌，与 GitHub Copilot 同源
E. 不了解 MCP 是什么，以上是凭感觉/排除法选的

**5. 关于AI编程工具中的"Skill"（如 Claude Code 的 Agent Skills）机制，以下描述最准确的是：**

A. 一种针对大模型做本地微调/继续训练的技术，通过喂养专属语料使模型"记住"某项能力
B. 一种把某类任务的操作步骤、脚本、参考资料封装成一个可复用包，由AI按任务需要自动检索并加载执行的机制，本质上是"按需调用的专家操作手册"，与临时写在提示词里的一次性说明不同
C. 与 MCP 完全等价，只是换了个名字，二者可以互相替代
D. 一种防止AI越权访问外部系统的权限管控功能，本身不涉及具体任务如何完成
E. 不了解 Skill 是什么，以上是凭感觉/排除法选的

**6. 关于AI编程助手（如 GitHub Copilot）生成代码的"著作权与质量责任"，团队普遍认可且可落地的做法是：**

A. 通过团队使用规范明确"开发者对合入代码负最终责任"，保留代码评审环节，并将AI生成代码纳入与手写代码相同的质量门槛
B. AI生成代码的著作权归工具厂商所有，开发者无需对质量负责
C. 开启"自动接受所有建议"模式可显著提升开发效率，且不会影响代码质量
D. AI生成的代码只要编译通过即可直接合入主干分支，无需评审

**7. 关于"AI辅助编程"中"SDD（规格驱动开发）"与"Vibe Coding"（凭感觉、口语化连续对话让AI改代码）的核心区别，以下说法最准确的是：**

A. 二者没有本质区别，都是"写一句提示词、看AI输出、直接用"
B. Vibe Coding 是先写清楚需求规格、接口契约与验收标准，再让AI按规格生成代码；SDD 则完全不需要提前规划，边聊边改即可
C. SDD 强调先明确规格/契约/验收标准，AI围绕规格生成并可验证代码；Vibe Coding 更依赖开发者对AI输出的即时判断和反复试错，缺少规格约束时容易积累"看起来能跑但难以维护、难以复核"的代码
D. 两者的区别只体现在使用的AI工具品牌不同，与开发流程本身无关
E. 不太清楚这两种说法的具体区别，以上是凭直觉选的

**8. 在"TDD + AI辅助编码"的工作流中，正确的"红-绿-重构"循环是：**

A. 先让AI生成完整实现代码（绿）→ 再补写测试用例（红）→ 最后删除失败的用例
B. "红"指代码语法报错、"绿"指编译通过、"重构"指重写整个项目
C. 先用AI辅助编写一个会失败的测试用例（红）→ 再让AI生成最简实现使其通过（绿）→ 最后重构优化并保持测试通过（重构）
D. TDD 只适用于全新项目，无法用于既有代码的缺陷修复

**9. 使用AI将需求从 Epic 逐层拆解到 User Story 时，正确的拆解逻辑是：**

A. Epic 表达业务目标与价值主张 → Feature 表达可交付的能力模块 → Story 表达可独立交付且满足 INVEST 原则的用户价值片段，层层收敛、粒度递减
B. Epic、Feature、Story 三者的粒度完全相同，只是命名习惯不同
C. Story 的粒度应拆到"单个方法/函数"级别，越细越好，便于AI精确生成代码
D. 拆解结果应由AI一次性完成并直接采纳，无需业务干系人确认

**10. 针对业务部门的原始需求进行"AI需求澄清"时，最能减少幻觉的做法是：**

A. 让AI直接生成最终需求文档，减少人工确认环节以提升效率
B. 先让AI基于原始材料生成结构化澄清问题清单（逐项对应材料中信息缺失或矛盾之处），由业务干系人逐条确认后，再让AI更新需求，并将AI输出与原始材料交叉核验
C. 不提供任何业务背景，让AI基于行业常识"合理补全"缺失信息
D. 一次问答后若AI回答显得合理，即视为需求已确认

**11. 关于AI在设计阶段生成的 ADR（架构决策记录），最合理的使用方式是：**

A. AI生成的 ADR 可直接作为正式技术决策存档，无需评审
B. ADR 只需记录最终结论，无需记录背景、约束与备选方案
C. ADR 是测试阶段的产物，属于测试文档的一部分
D. 将AI生成的 ADR 作为决策草稿，由架构师补充核对"背景、约束、备选方案与量化权衡、回滚条件"后，再纳入正式技术评审

**12. 在AI辅助的迭代开发中，做好"上下文管理"的核心价值是：**

A. 限制AI每次只能读取当前一个文件，防止信息过载
B. 把所有历史对话完整缓存下来，作为新任务的全部输入
C. 将项目需求、架构约定、编码规范等关键信息结构化沉淀并随任务带给AI，避免每次对话都"从零解释项目"，从而提升AI输出的连续性与一致性
D. 将团队每位成员与AI的聊天记录汇总共享给全体成员

**13. 使用AI批量生成测试用例后，人工复核时最应重点补充/校验的是：**

A. AI生成的断言（Assertion）是否足够花哨，能展示团队技术水平
B. 边界值、异常路径、非法输入、并发与超时等"非正常路径"用例，因为AI生成用例往往以正常主流程居多
C. 用例的执行顺序是否与文件中的书写顺序完全一致
D. 用例的注释行数是否足够多，便于"看起来"覆盖全面

**14. 用AI根据一段自然语言描述的"用户操作流程"生成 Playwright 端到端测试（E2E）脚本后，人工复核时最应该重点检查的是：**

A. 脚本里的变量命名是否足够专业，能否体现团队的代码风格
B. AI是否按自然语言描述准确覆盖了关键业务路径、边界与异常场景，是否存在"看似能跑但断言过松/断言缺失"或选择器写死导致的脆弱定位问题
C. 脚本运行速度是否足够快，越快说明质量越高
D. 只要脚本能在本地一次跑通，就可以直接合入CI流水线

**15. 使用AI生成项目计划与任务拆解时，最能保证计划"可落地"（而非"纸上可行"）的做法是：**

A. 让AI一次性生成整份计划，人工不做任何调整，确保计划与AI输出一致
B. 让AI忽略资源约束与历史数据，按"理想工期"估算，便于向管理层展示乐观前景
C. 让AI把任务拆得越细越好，拆到小时级，以确保"看起来"控制力强
D. 要求AI结合团队历史产能与资源约束进行估算，并对任务依赖关系做关键路径分析，再由项目经理校验调整

**16. 关于 CI/CD 中的 "Pipeline as Code"（流水线即代码），以下理解最准确的是：**

A. 指用AI大模型来编写 CI/CD 流水线配置
B. 指流水线必须由运维人员在 Web 界面上手工逐项点击配置
C. 流水线以代码/声明式文件（如 YAML）形式定义、纳入版本控制，可评审、可复用、可回滚，与业务代码遵循相同的变更管理流程
D. 指流水线配置只能使用一次，无法在多个项目间复用

**17. 关于故障根因分析中的 "5 Whys" 方法，以下说法正确的是：**

A. 每个故障必须恰好追问 5 次，多一次或少一次都不算"5 Whys"
B. 通过连续追问"为什么"，从表层现象逐层下钻，直至找到可采取纠正措施的深层原因；追问次数应视情况而定，并非固定 5 次
C. "5 Whys" 指用 5 种不同的分析工具（如鱼骨图、故障树 FTA 等）交叉验证
D. "5 Whys" 要求开发、测试、运维等 5 个不同角色各发言一次

**18. 以下关于运维关键指标的理解，正确的是：**

A. MTTR 指"平均无故障间隔"，数值越大说明故障越少
B. MTTR 数值越大，说明团队运维能力越强
C. 引入 AIOps 之后，MTTD/MTTR 指标已不再需要关注
D. MTTD 衡量"从故障发生到被检测发现"的时长，MTTR 衡量"从故障发生到服务恢复"的时长；在AI辅助下应优先优化 MTTD 并持续关注 MTTR

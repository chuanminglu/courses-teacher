MOCK 协作 前后端分离开发模式
前后端 Mock 协作模式 · 职责分工
📋 需求评审 ⚙️ 开发阶段 🔗 联调测试
📋
STAGE 01
需求评审阶段
接口契约共识
👥 共同职责
  • 评审需求，理解业务场景
  • 共同设计接口契约（URL、Method、Request、Response）
  • 明确数据结构、字段类型、边界条件
🎨 前端职责
  • 确认UI交互逻辑与接口的映射关系
  • 明确前端状态管理需求
⚙️ 后端职责
  • 评估接口实现难度与性能约束
  • 确认数据来源与业务规则
关键产出：接口契约文档（可用 Swagger/Postman/Apifox）
⚙️
STAGE 02
开发阶段
并行开发
🎨 前端职责
  • 创建 Mock 数据（基于接口契约）
  • 搭建本地 Mock 服务器（json-server / Mock.js / MSW）
  • 开发 UI 组件与交互逻辑
  • 集成 Mock 数据进行功能开发
  • 编写前端单元测试
⚙️ 后端职责
  • 实现真实接口（遵循接口契约）
  • 开发业务逻辑与数据持久化
  • 编写接口单元测试与集成测试
  • 部署到测试环境
核心原则：前后端基于相同的接口契约，各自独立开发，互不阻塞
🔗
STAGE 03
联调测试阶段
接口对接
🎨 前端职责
  • 切换到真实接口（修改 API Base URL）
  • 验证接口返回数据与 Mock 数据的一致性
  • 处理异常场景（错误状态码、网络超时等）
  • 进行端到端测试
⚙️ 后端职责
  • 配合前端进行联调
  • 修复接口 Bug 与契约偏差
  • 优化接口性能
  • 确认接口符合契约约定
🐛 常见问题处理
  • 字段不匹配：后端修改接口或前端适配
  • 数据格式差异：按契约调整响应格式
  • 性能问题：优化查询逻辑或增加缓存
验收标准：前端能成功调用真实接口并正常展示数据

MOCK 协作 常见误区与正确理解
Mock 数据 职责澄清
❌ 错误理解 ✅ 正确理解
误解：前端只负责UI，Mock数据应该由后端提供

• 认为Mock是后端的测试工具
• 前端等待后端提供Mock服务
• 前端被动依赖后端进度
• 结果：前后端相互等待，开发效率低下
→
正解：前端主动创建Mock数据，基于接口契约独立开发

• Mock是前端的开发工具，不是测试工具
• 前端根据接口契约自行Mock
• 前后端并行开发，互不阻塞
• 结果：提升开发效率，缩短交付周期
🔄
WORKFLOW
正确的协作流程
1
📋 定义接口契约
前后端共同评审需求，定义API接口文档（Swagger/Apifox），明确数据结构、字段类型、状态码
2
⚡ 前端创建Mock
前端基于契约创建Mock数据，搭建本地Mock服务器（json-server/MSW），独立开发UI
3
🔗 联调切换真实接口
后端完成开发后，前端切换API地址到真实接口，验证数据一致性，修复偏差问题

MOCK 协作 核心要点总结
前后端 Mock 协作 · 核心结论
Mock 数据是前端的开发工具，
不是后端的测试工具
前端应当主动基于接口契约创建 Mock 数据，
实现与后端的并行开发，而非被动等待后端完成。
📋
契约先行
前后端共同定义接口契约，形成开发依据。契约是Mock数据和真实接口的共同标准。
⚡
并行开发
前端基于Mock独立开发，后端实现真实接口，双方互不阻塞，大幅提升开发效率。
🔗
无缝切换
前端只需切换API地址即可从Mock切换到真实接口，联调成本极低，验证效率高。

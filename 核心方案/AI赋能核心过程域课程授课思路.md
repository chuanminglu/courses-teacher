# AI赋能核心过程域课程授课思路

> **定位说明**：本文档针对课程体系 Level 3（方法实践层）的9个核心过程域章节，为每章设计统一的四段式教学结构，并补充额外的教学增强建议。

---

## 统一教学结构框架

每章均采用以下五段式结构（在你提出的四段基础上，新增第五段）：

| 段落 | 模块                           | 时长建议 | 教学目的                           |
| ---- | ------------------------------ | -------- | ---------------------------------- |
| ①   | 本过程域核心知识体系与最佳实践 |          | 建立认知底座，理解"没有AI时怎么做" |
| ②   | AI赋能的全景地图               |          | 对照呈现"AI进来后能做什么"         |
| ③   | 演练的知识要点                 |          | 明确演练边界，降低操作焦虑         |
| ④   | 翻转课堂：小组演练与汇报       |          | 知识内化，同伴学习，暴露误解       |
| ⑤   | 讲师点评 + 反模式警示          |          | 校正偏差，强化关键认知             |

**每章建议时长**：约 2~2.5 小时
**分组建议**：3~5人一组，每组配置一名工程背景学员担任"技术锚"

## Chapter 0：项目管理（PM）

### ① 核心知识体系与最佳实践

- 软件项目管理三角：范围、时间、质量的动态平衡
- 工作分解结构（WBS）与任务估算方法（故事点、德尔菲法）
- 智能周报/日报的标准化模板与信息传递链条
- 进度风险识别：关键路径法（CPM）、燃尽图读法
- 最佳实践：项目信息透明机制、早期预警文化建设

### ② AI赋能全景地图

```
需求拆解 ──→ AI将Epic自动分解为Task列表，附估时依据
周报生成 ──→ 基于Git提交+Jira状态，自动生成结构化周报
风险预测 ──→ 基于历史数据+当前燃尽趋势，输出延期概率
会议纪要 ──→ 语音转写 + 结构化提炼 + 行动项自动分配
```

**工具演示重点**：Copilot Chat生成WBS、飞书/钉钉AI助手周报、语音转写工具

### ③ 演练知识要点

- 给定一个真实项目背景（如：开发一个企业OA审批模块）
- 要求学员用AI完成：① 需求拆解为5+个任务 ② 每任务附估时 ③ 生成一份项目周报
- 提示词核心要素：背景信息、角色约束、输出格式、质量标准

### ④ 翻转课堂

- **任务卡**：给出一段产品需求描述，用AI产出WBS+周报草稿
- **汇报要点**：展示提示词设计思路、AI输出质量评价、人工修正点说明
- **评分维度**：完整性、AI输出的信息密度、提示词质量

### ⑤ 反模式警示

- ❌ 把AI生成的估时直接上报，不经人工校验
- ❌ 周报只是"格式化"了流水账，缺乏风险判断
- ✅ AI是"初稿生成器"，PM的判断力不可替代

## Chapter 1：精益敏捷（Agile）

### ① 核心知识体系与最佳实践

- 敏捷宣言的四项价值观与十二原则的工程含义
- Scrum框架：角色（PO/SM/Dev）+ 事件（Sprint/Review/Retro）+ 工件（Backlog/DoD）
- User Story的INVEST原则：Independent / Negotiable / Valuable / Estimable / Small / Testable
- Kanban看板：WIP限制、流动效率与交付可预测性
- 常见敏捷导入失败原因：形式敏捷 vs 真正敏捷

### ② AI赋能全景地图

```
Story生成 ──→ 给定用户画像+业务场景，AI输出符合INVEST的Story
验收标准 ──→ AI自动补全Given-When-Then格式的AC
站会纪要 ──→ 语音/文字输入，AI整理为3Q格式（昨天/今天/阻碍）
回顾会议 ──→ AI分析Sprint数据，生成改进点建议（Keep/Drop/Try）
看板维护 ──→ AI根据代码提交自动更新任务状态
```

### ③ 演练知识要点

- INVEST检验清单的逐条应用
- Given-When-Then验收条件模板
- 如何用AI批量拆分Epic为Story，并进行质量复核

### ④ 翻转课堂

- **任务卡**：给一个Epic（如：用户登录模块），用AI拆分Story + 写验收标准 + 模拟一次站会纪要
- **汇报要点**：Story是否满足INVEST？AC是否可测？提示词是否可复用？
- **亮点展示**：哪个小组的提示词模板化程度最高？

### ⑤ 反模式警示

- ❌ Story过大：AI生成了"实现登录功能"这种不可测Story
- ❌ 验收标准模糊："界面美观"、"响应快"
- ✅ Story质量决定后续所有阶段质量，是AI赋能的源头把控点

## Chapter 2：需求阶段

### ① 核心知识体系与最佳实践

- 需求的三个层次：业务需求 / 用户需求 / 系统需求
- 需求获取技术：访谈、观察、问卷、原型、联合应用开发（JAD）
- 需求分析方法：用例分析、领域概念建模、上下文图、敏捷需求等
- 需求规格说明书（SRS）的结构与质量标准
- 需求变更管理：基线、影响分析、版本控制

### ② AI赋能全景地图

```
访谈辅助 ──→ AI预生成访谈问题集，按角色/场景定制
需求提炼 ──→ 会议记录/访谈文字 → AI提取结构化需求列表
上下文图 ──→ 给定业务边界，AI生成PlantUML上下文关系图
歧义识别 ──→ AI对SRS文档做"模糊词扫描"（尽快、合理、安全等）
需求追溯 ──→ 自动生成需求与Story、测试用例的追溯矩阵
```

### ③ 演练知识要点

- 使用BRD文档界定项目视图与范围
- 使用用户旅程进行用户需求的痛点挖掘
- 需求澄清文档 → Epic → Story → 验收标准
- AI生成需求原型
- AI需求变更管理

### ④ 翻转课堂

- **任务卡**：给一段访谈记录原文，用AI完成 BRD草稿 + 用户旅程痛点 + Epic→Story拆分 + 生成原型
- **汇报要点**：业务边界是否清晰？Story是否满足INVEST？原型是否还原了用户场景？
- **对抗演练**（可选）：一组出需求，另一组找漏洞

### ⑤ 反模式警示

- ❌ 直接让AI"写需求文档"，不提供任何业务上下文
- ❌ 把AI生成的需求当作最终版本，跳过需求评审
- ✅ AI是"需求加速器"，领域知识和与用户的沟通不可外包给AI

## Chapter 3：设计阶段

### ① 核心知识体系与最佳实践

- 架构设计方法：C4模型、ADR（架构决策记录）、质量属性场景分析
- DDD领域驱动设计核心概念：聚合根、限界上下文、领域事件、防腐层
- API设计原则：RESTful最佳实践、契约优先（Contract First）、API版本管理
- 数据库设计：ER建模、范式与反范式的权衡、分库分表设计原则
- 设计评审：技术可行性、性能风险、安全威胁建模（STRIDE）

### ② AI赋能全景地图

```
领域建模 ──→ 给定业务描述，AI识别实体/值对象/聚合/领域事件
架构图生成 ──→ AI输出C4 Context/Container/Component图（PlantUML）
ADR撰写 ──→ 给定技术选型问题，AI生成背景/决策/影响三段式ADR
API设计 ──→ 给定功能描述，AI生成OpenAPI 3.0规范草稿
安全审查 ──→ AI对设计文档做STRIDE威胁建模初筛
```

### ③ 演练知识要点

- DDD聚合识别的启发式规则（强一致性边界 = 聚合边界）
- ADR的标准结构与决策质量评估
- 如何用提示词驱动AI完成完整的API契约设计

### ④ 翻转课堂

- **任务卡**：给定一个业务场景（如：订单管理），完成领域建模 + 关键API设计 + 一份ADR
- **汇报要点**：限界上下文划分是否合理？API是否符合RESTful？ADR决策逻辑是否清晰？
- **角色扮演**：一个小组是设计者，另一个小组是"架构评审委员会"，提问挑战

### ⑤ 反模式警示

- ❌ AI生成的领域模型直接照抄，未经领域专家确认
- ❌ API设计只看功能，忽略错误码设计、幂等性、安全性
- ✅ 设计阶段的AI价值在于"提速+检查"，关键设计决策需人工确认

## Chapter 4：开发阶段

### ① 核心知识体系与最佳实践

- 代码质量五维度：可读性、可测试性、可维护性、性能、安全性
- 编程范式：OOP/FP/响应式编程的适用场景
- SOLID原则与常见设计模式的工程应用
- 代码评审（Code Review）文化与检查清单
- 技术债管理：识别、量化、还债计划

### ② AI赋能全景地图

```
代码生成 ──→ 基于设计文档/注释/测试，AI生成业务逻辑代码骨架
代码补全 ──→ Copilot/Cursor实时行级、函数级补全
代码审查 ──→ AI对PR做安全/质量/规范自动检查，生成Review意见
重构辅助 ──→ 识别坏味道（Long Method/God Class），给出重构建议
文档生成 ──→ 基于代码自动生成API文档、函数说明、架构注释
调试辅助 ──→ 描述Bug现象，AI分析可能根因并给出修复方案
```

**工具实操重点**：GitHub Copilot / Cursor / 通义灵码 对比演示

### ③ 演练知识要点

- 如何写"好的注释"驱动AI生成高质量代码
- 提示词迭代：从模糊到精准的多轮对话技巧
- AI代码安全审查：OWASP Top 10的AI检查路径

### ④ 翻转课堂

- **任务卡**：给定接口设计文档，用AI生成实现代码 + 自动生成单元测试 + 做一次安全检查
- **汇报要点**：生成代码是否满足业务需求？是否有安全漏洞？提示词经过几轮迭代？
- **竞赛模式**（推荐）：同一任务，比较各组AI生成质量与提示词优化水平

### ⑤ 反模式警示

- ❌ 完全信任AI生成的代码，不做任何人工Review
- ❌ 用AI生成了"能跑"的代码，但耦合严重、无法测试
- ✅ AI是"高级实习生"，代码所有权和质量责任仍在开发者

## Chapter 5：测试阶段

### ① 核心知识体系与最佳实践

- 测试金字塔：单元测试 / 集成测试 / E2E测试的比例与职责
- 测试设计技术：等价类划分、边界值分析、判定表、正交法
- 测试覆盖率指标：行覆盖、分支覆盖、变异测试
- TDD（测试驱动开发）工作流：Red → Green → Refactor
- 缺陷管理：严重度/优先级矩阵、根因分析（5 Why）

### ② AI赋能全景地图

```
用例生成 ──→ 基于Story + AC，AI生成完整测试用例集（正常/边界/异常）
单测生成 ──→ 给定被测函数，AI生成JUnit/pytest测试代码
缺陷分析 ──→ 给定缺陷描述+日志，AI定位根因并给出修复建议
用例补全 ──→ AI扫描已有用例，识别覆盖盲区并补充
测试数据 ──→ AI根据数据类型+约束条件生成测试数据集
性能脚本 ──→ AI生成JMeter/Locust压测脚本
```

### ③ 演练知识要点

- 如何让AI从Story直接生成测试用例（提示词中需包含：角色、场景、约束）
- 好的单元测试特征：Fast / Isolated / Repeatable / Self-checking / Timely（FIRST原则）
- 如何评价AI生成用例的完整性

### ④ 翻转课堂

- **任务卡**：给定一个登录功能的User Story，用AI生成测试用例集 + 单测代码 + 识别一个缺陷的根因
- **汇报要点**：测试用例是否覆盖边界？单测是否符合FIRST原则？根因分析是否准确？
- **互评环节**：各组互相"找用例漏洞"，增加挑战性

### ⑤ 反模式警示

- ❌ AI生成的用例全是正常路径，边界和异常完全缺失
- ❌ 用例数量多但重复度高，覆盖率虚高
- ✅ 测试质量的核心是"发现真实缺陷的能力"，数量不等于质量

## Chapter 6：部署阶段

### ① 核心知识体系与最佳实践

- CI/CD核心概念：持续集成/持续交付/持续部署的区别与边界
- 流水线设计：Build → Test → Security Scan → Package → Deploy → Verify
- 部署策略：蓝绿部署、金丝雀发布、滚动更新、特性开关（Feature Flag）
- 发布配置管理：配置外化、环境变量、密钥管理（Vault）
- 回滚机制：触发条件、回滚速度、数据兼容性处理

### ② AI赋能全景地图

```
Pipeline生成 ──→ 描述技术栈，AI生成GitHub Actions/Jenkins Pipeline脚本
配置审查 ──→ AI检查配置文件中的安全风险（硬编码密钥/开放端口）
发布检查 ──→ AI生成发布前检查清单（Pre-flight Checklist）
故障演练 ──→ AI设计混沌工程测试场景
文档生成 ──→ AI自动生成发布说明（Release Notes）
```

### ③ 演练知识要点

- Dockerfile最佳实践：多阶段构建、最小权限原则
- Pipeline YAML的关键结构：触发条件、Job依赖、环境隔离
- 如何用AI快速生成并校验流水线脚本

### ④ 翻转课堂

- **任务卡**：给定一个Java Spring Boot应用，用AI生成完整CI/CD Pipeline + 发布检查清单 + 回滚方案
- **汇报要点**：Pipeline是否覆盖安全扫描？发布检查是否全面？回滚条件是否可判定？
- **实操评分**：在本地或沙箱环境实际运行Pipeline（有条件时）

### ⑤ 反模式警示

- ❌ CI只跑编译，不跑测试和安全扫描
- ❌ 配置文件包含硬编码的数据库密码、API Key
- ✅ 部署阶段是"安全左移"的最后防线，AI辅助≠跳过检查

## Chapter 7：运维阶段

### ① 核心知识体系与最佳实践

- 可观测性三支柱：Metrics（指标）/ Logs（日志）/ Traces（链路追踪）
- SLO/SLI/SLA的定义与工程落地：如何制定有意义的可用率指标
- 告警设计原则：避免告警疲劳、告警分级（P0/P1/P2）、On-Call文化
- 性能瓶颈分析方法：USE方法（Utilization/Saturation/Errors）、火焰图
- 容量规划与弹性伸缩设计

### ② AI赋能全景地图

```
日志分析 ──→ 海量日志输入，AI定位异常模式、关联分析根因
告警优化 ──→ AI分析告警历史，识别噪音告警，建议阈值调整
故障诊断 ──→ 描述故障现象+指标数据，AI生成诊断步骤和修复建议
性能分析 ──→ AI解读火焰图、慢查询日志，给出优化建议
巡检报告 ──→ AI自动生成每日/每周系统健康度报告
Runbook生成 ──→ AI基于历史故障，生成标准化处置手册
```

### ③ 演练知识要点

- 如何撰写"告诉AI系统出问题了"的有效提示词（需包含：现象、时间、指标、日志摘要）
- 告警阈值设计的常见误区
- 从日志片段到根因假设的推理链条

### ④ 翻转课堂

- **任务卡**：给定一段系统故障的日志文件+监控截图，用AI诊断根因 + 生成临时修复方案 + 输出Runbook
- **汇报要点**：根因判断是否准确？处置步骤是否可执行？Runbook是否满足"5分钟上手"标准？
- **压力测试**（可选）：模拟"凌晨3点收到告警"的紧急场景

### ⑤ 反模式警示

- ❌ 日志没有结构化，AI无法有效分析
- ❌ 把AI的根因诊断当作确定答案，不做人工验证
- ✅ 运维AI的价值是"加速判断"，经验判断+AI辅助 > 单纯依赖AI

## Chapter 8：专项 — 遗留系统重构

### ① 核心知识体系与最佳实践

- 技术债类型分类：架构债、代码债、测试债、文档债
- 重构策略：绞杀者模式（Strangler Fig）、气泡上下文、Branch by Abstraction
- 代码坏味道识别：God Class、Long Method、Data Clump、Feature Envy
- "屠山"代码拆解：依赖分析→接缝识别→逐步解耦
- 无测试代码的安全重构路径：特性化测试（Characterization Test）

### ② AI赋能全景地图

```
代码理解 ──→ 粘贴遗留代码，AI生成功能说明、依赖图、关键路径分析
逻辑可视化 ──→ 复杂方法 → AI生成流程图/时序图（PlantUML）
坏味道识别 ──→ AI扫描代码，标注违反SOLID的位置，给出重构建议
迁移路径 ──→ 给定旧技术栈+目标技术栈，AI生成逐步迁移计划
补测试 ──→ AI为没有测试的遗留代码生成特性化测试，锁定当前行为
文档反向 ──→ AI从代码反向生成接口文档和业务逻辑说明
```

### ③ 演练知识要点

- 特性化测试的目的：**不是验证"正确性"，而是锁定"当前行为"**
- 绞杀者模式的触发条件与实施步骤
- 如何用AI做"陌生代码5分钟理解"

### ④ 翻转课堂

- **任务卡**：给定一段300行的"大泥球"遗留代码，用AI完成：① 生成业务逻辑说明 ② 识别3个坏味道 ③ 给出重构路线图 ④ 为其中一个方法补写特性化测试
- **汇报要点**：AI理解代码的准确度如何？重构建议是否安全可行？特性化测试是否锁定了真实行为？
- **难点讨论**：哪里是AI能帮上忙的？哪里需要人工介入？

### ⑤ 反模式警示

- ❌ 让AI"直接重构"遗留系统，跳过特性化测试阶段
- ❌ 一次性重构，不做小步迭代
- ✅ 遗留系统重构是风险最高的工程活动，AI是"辅助理解"工具，不是"自动重写"工具

## 全局追加建议（5条）

除四段式结构外，以下建议可进一步提升教学效果：

### 建议一：每章配备"提示词模板卡片"

每个过程域提炼3~5个高频提示词模板，印成卡片或提供数字版，学员可在工作中直接复用。
**价值**：降低迁移门槛，加速在实际工作中的落地。

---

### 建议二：设置"AI失效场景"专项讨论

每章增加10分钟讨论：**在哪些情况下AI会给出错误结果？如何识别和防范？**示例：

- 需求阶段：AI不了解行业背景，生成的需求不符合监管要求
- 测试阶段：AI生成的测试全部通过，但遗漏了业务规则边界
- 运维阶段：AI根因分析自信但错误，延误了故障处置时间

**价值**：建立"AI批判性使用"思维，避免过度信任。

---

### 建议三：贯穿全程的"AI工作流画布"

每章结束时，更新一张贯穿全程的流程图，展示AI在当前过程域的接入点。
最终形成一张完整的"AI赋能SDLC全景图"，作为课程结业产出之一。
**价值**：从局部到整体，帮助学员建立系统性认知。

---

### 建议四：设置跨章综合演练（大作业）

在所有章节结束后，安排一个2~3小时的综合演练：
**任务**：用AI驱动，完成一个微型项目从需求→设计→代码→测试→部署的全过程链路。
**评分**：AI辅助效率、输出质量、提示词工程水平。
**价值**：检验学员是否能将各过程域知识整合运用，而非孤立使用。

---

### 建议五：建立"课程知识库"（Prompt Library）

鼓励学员在每次翻转课堂中，将"最优提示词"提交到共享知识库。
课程结束时，形成一套团队共建的Prompt Library，作为团队AI工作规范的起点。
**价值**：把课程学习成果转化为团队资产，延伸课程价值生命周期。

## 1. 架构概述

### 1.1 系统定位

**系统名称**：TeamTodo

**系统定位**：
面向中小团队的多项目任务协作管理系统，支撑团队通过看板管理任务生命周期、实时协作沟通、进度追踪与操作审计。

### 1.2 核心设计理念

**设计原则**：
1. **领域驱动，单一权威聚合根**：Task作为全系统权威聚合根（追溯ADR-004），其他模块（看板视图、通知、报表）均以Task为唯一数据源，避免数据副本不一致
2. **安全优先**：认证、权限、审计三道防线贯穿全部模块（追溯ADR-001/002/006），而非事后补充
3. **渐进式扩展**：MVP阶段采用成本最低的共享库+行级隔离方案，同时为未来分库分表、微服务拆分预留架构演进路径（追溯ADR-003）

### 1.3 架构风格

**主要架构风格**：模块化单体架构（Modular Monolith）+ 分层架构（Controller-Service-Mapper-Domain）

**选择理由**：
团队规模3~5人（追溯B4-07隐性发现），项目处于MVP阶段，微服务架构会引入额外的服务治理、分布式事务复杂度，与团队当前运维能力不匹配（追溯ADR-003"共享库"选择的同一约束背景）。采用模块化单体既能保证M1~M6六个模块间边界清晰（对应B4-07的模块划分），又避免过早引入分布式系统的复杂度。

### 1.4 系统边界

**系统范围**：
- ✅ **包含**：M1用户认证与访问控制、M2多项目管理与数据隔离、M3看板任务视图、M4任务生命周期管理、M5任务内协作与通知、M6进度报表与操作审计
- ❌ **不包含**：第三方SSO/企业IM集成（如企业微信、钉钉登录）、移动端原生App（当前仅Web响应式）、AI相关能力（如任务自动分类/智能推荐，非本期范围）

## 2. 架构视图

### 2.1 逻辑视图

#### 模块划分

| 模块名称 | 职责描述 | 核心组件 |
|---------|---------|---------|
| **M1 用户认证与访问控制** | 用户注册/登录/会话管理/权限矩阵校验 | AuthController、JwtTokenProvider、PermissionEvaluator |
| **M2 多项目管理与数据隔离** | 项目创建/成员邀请/项目切换/数据隔离 | ProjectService、ProjectMemberService、TenantLineHandler |
| **M3 看板任务视图** | 看板拖拽视图、TaskCard投影、筛选搜索 | KanbanController、TaskCardViewService |
| **M4 任务生命周期管理** | Task聚合根：创建/编辑/状态流转/删除/指派/优先级 | TaskService、TaskStateMachine、TaskDomainService |
| **M5 任务内协作与通知** | 评论、@提及、实时通知 | CommentService、NotificationService、WebSocketGateway |
| **M6 进度报表与操作审计** | 进度统计、审计日志、数据导出、备份恢复 | ReportService、AuditLogService、BackupScheduler |

#### 模块依赖关系

（追溯 B4-07 第7.1节"跨模块依赖DAG"）

```
                M1 用户认证与访问控制
                        │
        ┌───────────────┼───────────────┬───────────────┐
        ↓               ↓               ↓               ↓
  M2 项目管理      M3 看板视图      M4 任务生命周期      M6 报表审计
        │               ↑               │  │               ↑
        └───────────────┘               │  └───────────────┤
                                         ↓                  │
                                   M5 协作通知 ──────────────┘
```

说明：M1为全系统基础，M2/M3/M4/M5/M6均依赖其身份与权限能力；M2（项目/成员关系）被M3/M4依赖；M4（Task聚合根）被M3（视图投影）、M5（评论挂载）、M6（统计/审计）依赖；M5（通知）依赖M6的审计能力做通知留痕。

#### 关键设计决策

- **Task单一权威聚合根**：M3的TaskCard、M5的评论、M6的报表统计均以M4的Task表为唯一数据源，不做数据冗余复制（追溯ADR-004）
- **权限校验统一收口**：全部模块的接口权限校验统一通过`PermissionEvaluator`，不在各模块内自行实现（追溯ADR-002）
- **实时能力统一网关**：M3（看板）与M5（通知）共用同一个WebSocket网关，按projectId做Topic隔离，不各自实现推送机制（追溯ADR-005）

```

                          │   浏览器 (Vue3)   │
                          └────────┬─────────┘
                                   │ HTTPS / WSS
                          ┌────────┴─────────┐

              ┌────────────────────┼────────────────────┐
              ↓                    ↓                    ↓
    ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
    │ Spring Boot 实例1 │  │ Spring Boot 实例2 │  │ Spring Boot 实例N │
    │ (REST + WebSocket) │  │ (REST + WebSocket) │  │ (REST + WebSocket) │
    └────────┬─────────┘  └────────┬─────────┘  └────────┬─────────┘
              └────────────────────┼────────────────────┘
                                   ↓
                  ┌────────────────┼────────────────┐
                  ↓                ↓                ↓
          ┌───────────────┐ ┌─────────────┐ ┌────────────────┐
          │ MySQL 8 (主从) │ │ Redis (集群) │ │ 定时任务节点     │
          │ 业务库+审计库   │ │ 会话黑名单/    │ │ (Spring Schedule│
          │                │ │ 权限缓存/在线 │ │  或XXL-Job，    │
          │                │ │ 状态映射      │ │  追溯ADR-010)   │
          └───────────────┘ └─────────────┘ └────────────────┘
```

#### 部署特点

- **无状态应用层**：Spring Boot实例本身不保存会话状态（追溯ADR-001 JWT无状态方案），可任意水平扩容
- **WebSocket多实例共享**：多个应用实例通过Redis共享"用户-连接-projectId"在线状态映射，任一实例均可将消息路由到目标用户所在实例（追溯ADR-005）
- **数据层集中**：MVP阶段MySQL/Redis均为集中部署，未按项目做物理拆分（追溯ADR-003）

#### 运行环境要求

| 组件/层次 | 环境要求 |
|----------|---------|
| **前端** | Vue3 + Vite构建，Nginx托管静态资源，Node18+构建环境 |
| **后端应用** | Java 17 + Spring Boot 3.x，至少2实例（避免单点） |
| **数据库** | MySQL 8.0，InnoDB引擎，主从复制（读写分离可选） |
| **缓存** | Redis 7.x，用于会话黑名单/权限缓存/WebSocket在线状态映射 |
| **定时任务** | Spring Schedule（MVP阶段单实例内置）或XXL-Job（多实例后升级，追溯ADR-010） |

### 2.3 数据视图

#### 数据流转图

```
用户请求 → Nginx → Spring Boot(JWT鉴权,追溯ADR-001)
                        │
                        ↓
             权限校验(PermissionEvaluator,追溯ADR-002)
                        │
                        ↓
          业务逻辑(TenantLineHandler自动注入projectId,追溯ADR-003)
                        │
              ┌─────────┼─────────┐
              ↓         ↓         ↓
           MySQL      Redis    WebSocket广播
           (持久化)   (缓存/    (实时通知,
                       在线状态)  追溯ADR-005)
              │
              ↓（异步）
        审计日志写入（哈希链，追溯ADR-006）
```

#### 数据存储设计

| 数据类型 | 存储位置 | 容量/规模（估算） | 生命周期 |
|---------|---------|----------|---------|
| **用户账号信息（User）** | MySQL | 与团队规模相关，千级用户量级 | 永久（软删除） |
| **项目/成员关系（Project/ProjectMember）** | MySQL | 项目数×成员数，万级 | 永久（项目归档不物理删除） |
| **任务数据（Task）** | MySQL | 核心数据，预估百万级行 | 永久，随任务归档标记但不物理删除 |
| **评论/@提及（Comment/Mention）** | MySQL | 随任务量增长，千万级潜力 | 永久 |
| **通知（Notification）** | MySQL | 高频写入，百万级 | 保留90天后归档（未在需求中明确，列入待确认） |
| **审计日志（AuditLog）** | MySQL（独立表，权限收紧） | 持续增长，千万级 | 永久，只读不可篡改（追溯ADR-006） |
| **会话黑名单/权限缓存/在线状态** | Redis | 小规模，随在线用户数波动 | 短TTL（分钟级） |

#### 数据安全

- **密码加密**：BCrypt哈希存储，不存明文（追溯ADR-007）
- **权限隔离**：projectId行级隔离 + RBAC接口权限双重防护（追溯ADR-002/ADR-003）
- **审计防篡改**：应用层禁写+数据库权限收紧+哈希链（追溯ADR-006）
- **备份**：数据库级快照/binlog（追溯ADR-012，B4-07既定方向）

### 2.5 场景视图

#### 场景1：用户登录鉴权流程

**业务流程**：
1. 用户提交用户名密码
2. 后端校验密码（BCrypt比对，追溯ADR-007）
3. 校验通过后签发JWT（Access Token 30分钟 + Refresh Token 7天，追溯ADR-001）
4. 前端后续请求携带Token，网关/过滤器逐次校验
5. 校验通过后，`PermissionEvaluator`根据Token中的全局角色 + 实时查询的项目级角色，判定本次操作是否被允许（追溯ADR-002）

**架构组件交互**：
```
浏览器 → AuthController → JwtTokenProvider(签发Token)
                                  ↓
后续请求 → JWT过滤器(校验Token) → PermissionEvaluator(角色判定,查ProjectMember+Redis缓存)
```

**性能要求**：
- 登录接口响应时间：P95 < 500ms
- 权限校验（含缓存命中）：P95 < 50ms

---

#### 场景2：看板任务状态实时更新流程

**业务流程**：
1. 用户A在看板拖拽任务卡片，触发状态变更请求
2. 后端Task领域服务校验状态机合法性 + 乐观锁version比对（追溯ADR-004）
3. 更新成功后，通过WebSocket网关向该项目下的所有在线用户广播变更事件（追溯ADR-005）
4. 用户B的浏览器接收到WebSocket消息，前端局部刷新对应TaskCard

**架构组件交互**：
```
用户A拖拽 → KanbanController → TaskService(状态机校验+乐观锁UPDATE)
                                        ↓ 成功
                              WebSocketGateway(按projectId广播)
                                        ↓
                              用户B浏览器（局部刷新TaskCard）
```

**性能要求**：
- 状态更新接口：P95 < 300ms
- WebSocket广播到达客户端延迟：< 1秒

---

#### 场景3：任务操作审计留痕流程

**业务流程**：
1. 任意涉及Task/Project/User等关键实体的写操作完成后，异步触发审计日志写入
2. 审计服务读取上一条记录，计算哈希摘要，写入新记录（追溯ADR-006）
3. 定时巡检任务每日校验哈希链完整性，发现异常时告警

**架构组件交互**：
```
业务操作完成 → 异步事件(Spring Event) → AuditLogService
                                              ↓
                              写入audit_log表(prev_hash链式)
                                              ↓
                          每日巡检任务(校验哈希链) → 异常告警
```

**性能要求**：
- 审计写入不阻塞主业务流程（异步化）
- 每日巡检耗时 < 10分钟（追溯ADR-006回滚条件阈值）

| 约束类型 | 约束内容 | 对架构的影响 | 追溯来源 |

### 4.2 资源约束

| 约束类型 | 约束内容 | 对架构的影响 | 追溯来源 |
|---------|---------|------------|--------|

### 4.4 组织约束

| 约束类型 | 约束内容 | 对架构的影响 | 追溯来源 |
|---------|---------|------------|--------|

| ADR编号 | 决策内容 | 对架构的影响 | 架构体现章节 |
|--------|---------|-------------|------------|
| **ADR-001** | JWT无状态认证 | 应用层无状态化，支持水平扩展 | 2.2部署视图、2.5场景1 |
| **ADR-002** | 动态RBAC权限模型 | 权限校验统一收口至PermissionEvaluator | 2.1逻辑视图、2.5场景1 |
| **ADR-003** | 共享库+行级隔离 | 决定数据层不做物理拆分，运维成本可控 | 2.2部署视图、2.3数据视图 |
| **ADR-004** | Task乐观锁+状态机 | Task作为唯一权威聚合根的并发保障 | 2.1逻辑视图、2.5场景2 |
| **ADR-005** | WebSocket实时通信 | M3/M5共用统一实时网关 | 2.2部署视图、2.5场景2 |
| **ADR-006** | 审计日志哈希链 | 独立的审计写入与巡检机制 | 2.3数据视图、2.5场景3 |

### 5.2 架构设计理由

#### 模块化单体而非微服务

**理由**：
1. **团队规模匹配**：3~5人团队无法承担微服务的服务治理成本（追溯B4-07隐性发现）
2. **数据隔离方案一致性**：ADR-003选择共享库，若采用微服务则天然需要按模块拆库，与ADR-003结论冲突
3. **演进留有余地**：模块边界（M1~M6）已按B4-07清晰划分，未来若需拆分为微服务，模块化单体阶段的边界可直接作为服务拆分边界（见第7章演进路线）

**追溯**：
- ADR-003（数据隔离策略）
- B4-07 第7.1节模块依赖DAG

#### Task单一权威聚合根

**理由**：
1. TaskCard（M3看板视图）若维护独立数据副本，会与Task详情产生不一致，B4-07已将此列为强约束
2. 统一聚合根简化了M5评论关联、M6统计口径，避免"多处真相来源"问题

**追溯**：
- ADR-004
- B4-07 M4模块强约束📌

**核心回滚策略**：
1. **认证方案风险场景**（Token安全事件）：切换Session+Redis，预计2.5天（追溯ADR-001回滚方案）
2. **数据隔离风险场景**（越权/性能超阈值）：迁移分库分表（ShardingSphere），预计1周（追溯ADR-003回滚方案）
3. **实时通信风险场景**（连接不稳定）：降级短轮询，预计2天（追溯ADR-005回滚方案）

## 7. 架构演进路线

### 7.1 当前架构（MVP/V1.0）

**核心特征**：
- ✅ 模块化单体，M1~M6边界清晰但同进程部署
- ✅ 共享库+行级隔离的数据方案
- ✅ JWT无状态认证 + WebSocket统一实时网关

**限制**：
- ❌ 单表数据量增长后存在查询性能瓶颈（Task/AuditLog表）
- ❌ 搜索能力（US010A/US010B）当前仅依赖数据库LIKE查询，不支持复杂全文检索（追溯ADR-009，待定）
- ❌ 定时任务当前为单实例Spring Schedule，多实例部署时存在任务重复执行风险（追溯ADR-010，待定）

### 7.2 未来架构（V2.0）

**演进目标**：
- 🔄 视数据规模启动分库分表（按projectId哈希）
- 🔄 若搜索需求增强，引入Elasticsearch（追溯ADR-009候选方向）
- 🔄 若需水平扩容定时任务，升级至XXL-Job（追溯ADR-010候选方向）
- 🔄 视模块耦合度与团队规模变化，评估是否将M6（报表审计，读多写少、独立性强）拆分为独立服务

**架构变化**：
```
当前架构：模块化单体 + 共享库
    ↓ 演进
未来架构：核心模块（M1~M5）保持单体 + M6拆分为独立报表服务 + 分库分表数据层
```

**演进时间表**：
- **触发条件达到时**（如ADR-003回滚条件：单表>5000万行）：启动分库分表评估
- **业务需要**（如需要复杂全文检索）：引入Elasticsearch

## 决策清单

### ADR-001：认证与会话管理方案

| 属性 | 内容 |
|------|------|
| **决策类别** | 认证与会话 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US001（用户注册）、US002（用户登录）、US004（会话管理/登出），（来自 M1 用户认证与访问控制模块全部Story） |
| **触发原因** | 系统全部6个模块的接口均需要登录态校验，会话管理方式（有状态/无状态）直接决定后续所有接口设计中"如何携带身份"这一基础模式 |
| **决策范围** | 选择用户登录后身份凭证的载体与校验方式 |
| **候选方向** | JWT无状态Token / Session+Redis集中存储 / OAuth2第三方登录 |
| **依赖关系** | 被 ADR-002（RBAC权限模型）、ADR-005（实时通信方案，WebSocket鉴权需依赖本决策）依赖 |
| **不决策的风险** | 全部接口设计中"鉴权头/Cookie"格式无法统一，HLD-02详设会出现同一系统多种鉴权约定并存的混乱 |

### ADR-002：RBAC权限模型与权限校验粒度

| 属性 | 内容 |
|------|------|
| **决策类别** | 权限/授权模型 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US003-Rev（权限矩阵：4类角色×6种操作，来自验收标准中的完整权限矩阵表） |
| **触发原因** | 权限矩阵已在需求层明确定义4类角色（系统管理员/项目负责人/项目成员/访客）与6种操作的授权关系，但"如何在代码层实现这套矩阵"（每次请求重新计算 vs 预计算缓存）尚未决策 |
| **决策范围** | 选择权限校验的实现粒度与位置（接口级注解 / 数据级过滤 / 两者结合），以及角色-权限映射的存储与刷新方式 |
| **候选方向** | 基于角色的静态RBAC（Spring Security @PreAuthorize注解）/ 基于"项目成员关系"的动态权限计算（每次查询ProjectMember表）/ ABAC属性基访问控制 |
| **依赖关系** | 依赖 ADR-001 先决定（权限校验必须建立在明确的身份凭证之上）；被 HLD-02 全部接口的鉴权设计依赖 |
| **不决策的风险** | 每个接口各自实现权限校验逻辑，US003-Rev定义的权限矩阵无法在代码中统一收口，出现越权漏洞风险 |

### ADR-003：多项目数据隔离策略

| 属性 | 内容 |
|------|------|
| **决策类别** | 数据模型与隔离 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US005（创建项目）、US007（项目切换/数据隔离），（来自 B4-07 M2模块 第2章数据依赖矩阵："联合唯一约束(projectId+userId)+事务行锁"） |
| **触发原因** | B4-07已明确M2采用"联合唯一约束+行锁"策略，但这是并发控制细节，其上位决策——"数据在物理/逻辑层面如何按项目隔离"——尚未固化为ADR |
| **决策范围** | 选择多项目场景下数据隔离的实现方式 |
| **候选方向** | 共享库+projectId字段行级隔离（所有查询强制带projectId条件）/ 每项目独立Schema / 每项目独立数据库实例 |
| **依赖关系** | 被 ADR-004（Task并发控制策略）依赖；被 HLD-03 全部业务表的表结构设计依赖 |
| **不决策的风险** | 数据库表结构无法确定是否需要在每张业务表加projectId字段+索引，存在跨项目越权访问数据的合规风险 |

### ADR-004：Task聚合根与并发控制策略

| 属性 | 内容 |
|------|------|
| **决策类别** | 数据一致性与事务边界 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US011~US016（任务生命周期管理全部Story），（来自 B4-07 M4模块 强约束标注📌"Task是全系统权威聚合根"、第6章并发冲突与一致性策略："M3/M4核心用乐观锁(version字段)+状态机校验"） |
| **触发原因** | Task被B4-07标注为全系统权威聚合根，TaskCard（M3看板视图）是其投影，一旦并发控制方案不统一，看板视图与任务详情会出现数据不一致 |
| **决策范围** | 选择Task实体的并发更新控制方案与状态机校验的实现层 |
| **候选方向** | 乐观锁（version字段+CAS更新，冲突返回409）/ 悲观锁（SELECT FOR UPDATE行锁）/ 无锁最终一致（依赖消息队列做补偿） |
| **依赖关系** | 依赖 ADR-003 先决定（并发控制需建立在明确的数据隔离边界内）；被 HLD-03 中Task表的version字段设计、HLD-02任务更新类接口的409错误码设计依赖 |
| **不决策的风险** | 多用户同时编辑同一任务（如看板拖拽改状态 vs 详情页改优先级并发发生）会出现"更新丢失"，这是B4-07第6章标注的核心并发冲突点，不决策会直接导致数据错误 |

### ADR-005：实时协同通信方案

| 属性 | 内容 |
|------|------|
| **决策类别** | 集成方式 / 性能方案 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US009（看板拖拽任务状态实时反映）、US017~US019-Rev（任务协作与通知），（来自 B4-07 M3、M5模块 第3章事件触发链："任务状态变更需实时推送到看板/通知需实时送达"） |
| **触发原因** | M3看板视图与M5协作通知均要求"变更后其他在线用户能实时感知"，这是一个跨两个模块共用的基础设施决策，若各自实现会产生重复投入且体验不一致 |
| **决策范围** | 选择服务端向客户端推送变更事件的通信方式 |
| **候选方向** | WebSocket长连接（双向，支持看板协同光标等未来扩展）/ SSE Server-Sent Events（单向推送，实现更简单）/ 短轮询Polling（兜底降级方案） |
| **依赖关系** | 依赖 ADR-001 先决定（WebSocket连接建立时需要复用登录态做鉴权，避免匿名连接）；被 HLD-02 中M3/M5相关接口设计依赖 |
| **不决策的风险** | 多人协同编辑看板时，非操作方看不到实时变化，需手动刷新，直接影响US009、US017~US019-Rev的验收标准达成 |

### ADR-006：审计日志不可篡改方案

| 属性 | 内容 |
|------|------|
| **决策类别** | 数据安全与合规 |
| **优先级** | 🔴 P0 阻塞型 |
| **来源** | US021（操作审计日志），（来自 B4-07 M6模块 强约束标注📌"审计日志只读不可篡改"） |
| **触发原因** | 审计日志的"不可篡改"是B4-07明确标注的强约束（📌级别），且一旦表结构/写入方式确定后再补救的改造成本极高（涉及历史数据迁移），必须在HLD-03数据库设计前决策 |
| **决策范围** | 选择审计日志"只读不可篡改"这一非功能约束的技术落地方式 |
| **候选方向** | 应用层禁止UPDATE/DELETE + 数据库账号权限收紧（仅授予INSERT/SELECT）/ 追加写Append-only表 + 数据库触发器拦截修改 / 写入时生成哈希链（每条记录含上一条的哈希，篡改可被检测） |
| **依赖关系** | 依赖 ADR-003 先决定（审计表同样需要明确数据隔离边界，避免跨项目审计数据可见）；被 HLD-03 审计日志表设计依赖 |
| **不决策的风险** | 审计日志若可被篡改，US021验收标准与B4-07强约束均无法满足，且直接影响系统的合规可信度 |

### ADR-008：通知去重与投递可靠性方案

| 属性 | 内容 |
|------|------|
| **决策类别** | 数据一致性与事务边界 |
| **优先级** | 🟡 P1 重要型 |
| **来源** | US019-Rev（消息通知，修订版），（来自 B4-07 M5模块 第6章并发冲突与一致性策略："M5用唯一约束(userId+type+targetId+事件id)防重复通知"） |
| **触发原因** | B4-07已给出唯一约束的具体字段组合，但"投递失败后是否重试、重试策略"这一更上层的可靠性决策尚未明确，影响M5开发前的接口设计 |

| **优先级** | 🟡 P1 重要型 |

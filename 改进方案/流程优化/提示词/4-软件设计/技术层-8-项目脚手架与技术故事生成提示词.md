# 技术层-8：项目脚手架与技术故事生成提示词（通用版）

> **📌 使用说明**: 本提示词用于 AI 辅助生成**技术故事（Enabler）清单**，为全新项目补齐脚手架/基础设施类待办。技术故事以 `EN{NNN}` 编号，作为 Product Backlog Item 参与排序与估算，输入来自设计阶段（ADR/HLD）与技术约束。
>
> **📍 镜像归属**: 本文件为 `流程优化/提示词/4-软件设计/` 下的**权威版**（由技术故事（EN）分支并入，2026-08-31 整合；编号由"技术层-4"调整为"技术层-8"，以避开与 `技术层-4-故事级Schema设计提示词.md` 的编号冲突）。原 `技术故事/` 分支目录已整合归档并删除。技术故事（EN）与业务故事（US）并列进入 Product Backlog，参与优先级排序与尺寸估算。
>
> **适用场景**: 全新项目 / 新模块启动 / 需要建立工程基座
>
> **前置输入**: ADR 决策清单、HLD（模块/接口/数据库设计）、技术约束（NFR、技术栈）
>
> **预计时长**: 20-40 分钟

## 🎭 R - 角色定义

你是一位资深全栈架构师 + 技术负责人，拥有 10 年以上从 0 到 1 搭建项目的经验，擅长：

- 工程脚手架搭建（前端/后端/数据库/Mock/CI 全栈初始化）
- 项目初始化最佳实践（目录结构、构建工具、代码规范、版本管理）
- 技术故事（Enabler）识别与拆解
- 设计文档（ADR/HLD）到可执行待办的翻译
- 技术基础设施风险识别（外部依赖、工具链、环境差异）

## 📋 T - 任务描述

基于以下输入材料，识别全新项目必须建立的**技术故事（Enabler）清单**，每个技术故事以 `EN{NNN}` 编号，包含价值主张、输入设计文档引用、验收标准、尺寸估算、依赖关系、风险与建议 Sprint。

### 输入材料

#### 材料1：ADR 决策清单与技术设计文档（必填）

{粘贴 ADR 决策清单（00-ADR决策清单.md）及已生成的 ADR 文档，如 ADR-001 认证 / ADR-002 权限 / ADR-003 数据模型 / ADR-011 部署 / ADR-013 前端架构 / ADR-014 架构风格}

**格式示例**：
```markdown
### ADR-013：前端架构方案（Vue3 SPA 结构）
- 技术栈：Vue 3 + TypeScript + Pinia + vue-router + vuedraggable
- 拖拽方案：vuedraggable（SortableJS）
- 状态管理：Pinia
- 样式：复用现有 style.css 设计系统
```

#### 材料2：HLD 设计产物（可选但推荐）

{粘贴 HLD-01 模块划分 / HLD-02 接口设计 / HLD-03 数据库设计 的关键结论}

**格式示例**：
```markdown
### HLD-03：数据库设计
- 数据库：MySQL 8.0，Flyway 版本管理
- 表清单：users / projects / project_members / tasks / ...
- 关键约束：projectId 行级隔离、version 乐观锁
```

#### 材料3：技术约束与非功能需求（必填）

{粘贴技术栈、部署要求、NFR（性能/并发/可用性/安全/数据）等约束}

**格式示例**：
```markdown
- 技术栈：Spring Boot 3 + MyBatis-Plus + MySQL 8；Vue 3 + TS + Pinia
- 部署：Docker Compose + Nginx 双实例
- 环境：dev / test / prod 三套
- 浏览器：Chrome、Edge、Firefox
```

---

### 任务上下文

本任务是"从设计到执行"的**桥梁工序**：
- **上游**：ADR（技术决策）、HLD（模块/接口/数据库设计）、技术约束
- **下游**：Product Backlog（技术故事与业务故事统一排序）→ Sprint 任务拆解

**关键原则**：
1. 技术故事**不是任务**——它是 Backlog Item，参与排序/估算/验收；任务是其进入 Sprint 后再拆解的产物
2. 技术故事**必须有验收标准**——通常以"可编译/可运行/规范落地"衡量，而非业务 AC
3. 技术故事**必须引用设计文档**——每条 EN 明确标注输入来源（ADR-xxx / HLD-xx），保证可追溯
4. 脚手架类技术故事通常为 **P0 前置条目**——必须排在所支撑的业务故事之前

## 🎯 G - 目标与意图

### 核心目标

生成**可直接进入 Product Backlog 的技术故事清单**：有编号、有验收标准、有尺寸、有依赖，支撑新项目顺利启动。

### 具体目标

1. **覆盖完整**: 识别所有脚手架/基础设施工作（工程初始化、数据库版本管理、Mock、环境、CI/CD、测试基建等）
2. **编号规范**: 所有技术故事使用 `EN{NNN}` 格式（3位数字）
3. **验收可执行**: 每个 EN 有可验证的完成定义（如"前端工程可 `npm run dev` 启动"）
4. **可追溯**: 每个 EN 标注输入设计文档引用（ADR-xxx / HLD-xx）
5. **与业务故事衔接**: 标注每个 EN 支撑的业务故事（USxxx），便于 Backlog 排序

### 业务价值

- **为开发团队**: 新项目有清晰的工程初始化路线图，避免"不知道先干什么"
- **为技术负责人**: 脚手架工作可见、可估算、可验收
- **为 Product Owner**: 技术故事参与排序，不遗漏基础设施待办
- **为 AI 编程流水线**: 为任务拆解提供技术故事输入

### 成功标准

- ✅ 所有技术故事有 `EN{NNN}` 编号
- ✅ 所有技术故事有验收标准（Checklist，可执行）
- ✅ 所有技术故事有尺寸（S/M/L/XL 或 Story Points）
- ✅ 所有技术故事标注输入设计文档引用
- ✅ 识别依赖关系与风险（具体化，不允许"技术风险"笼统描述）

### 2. 质量要求

#### 编号规则（强制）
- 格式：`EN{NNN}`，3 位数字，无分隔符
- 示例：`EN001`、`EN002`、`EN010`

#### 验收标准可执行（强制）
- ❌ 不允许：`实现前端工程初始化`（模糊）
- ✅ 正确：`前端工程可 npm run dev 启动`、`npm run lint 通过`、`集成 ESLint/Prettier`

#### 可追溯性（强制）
- 每个 EN 必须标注输入设计文档引用（ADR-xxx / HLD-xx / 技术约束）
- 每个 EN 必须标注支撑的业务故事（USxxx），无支撑则标注"基础/全部"

#### 风险说明具体化（强制）
- ❌ 不允许：`risk: tech`（笼统）
- ✅ 正确：`risk: tech — WebSocket 反代配置需验证 Upgrade 头`

### 4. 特别说明

#### 常见技术故事清单（参考）

| 类别 | 典型技术故事 |
|------|-------------|
| 工程初始化 | 前端工程（Vite/Vue/React）、后端工程（Spring Boot/Node）骨架 |
| 数据库 | 数据库脚本与版本管理（Flyway/Liquibase）、初始化数据 |
| Mock | Mock 基础设施（json-server/MSW） |
| 环境 | 环境与代理配置（.env/CORS/dev-prod） |
| 工程化 | CI/CD、Docker Compose、代码规范（ESLint/Checkstyle/commitlint） |
| 测试 | 测试基础设施（JUnit/Vitest/Playwright） |
| 安全 | 密钥管理、安全基线 |

#### 技术故事 vs 业务故事

| 维度 | 技术故事（EN） | 业务故事（US） |
|------|---------------|---------------|
| 输入 | ADR/HLD/技术约束 | 用户故事+验收标准 |
| 验收 | 可编译/可运行/规范落地 | 业务 AC 可演示 |
| 任务形态 | 工程初始化/配置/脚本/CI | Mock→BE→FE→QA |

#### 尺寸估算（T-Shirt，与 1号 Backlog 口径一致）

技术故事的尺寸估算与业务故事共用 **T-Shirt 打分法**（S/M/L/XL），参考工时口径与 `1-Product Backlog梳理提示词-Lean版.md` 完全一致：

| 尺寸 | 参考工时（Web全栈） | 适用示例 |
|------|---------------------|---------|
| S | 4-12h | 单文件配置、单个脚本 |
| M | 12-30h | 一个工程的脚手架初始化 |
| L | 30-60h | 跨端工程+CI/CD+测试基建组合 |
| XL | >60h | 过大，建议拆分为多个 EN |

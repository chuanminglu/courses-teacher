# 00 · 集成测试用例抽取执行计划

> **📌 用途**：本文档规划如何用本目录下 `01/02/03` 三份输入材料，依次执行 `prompts/` 目录下的 5 个通用提示词，产出真实的集成测试中间结果与最终产物。执行完成后，`04~08` 号文件即为各步骤的实际产出。

---

## Context（为什么做这件事）

`改进方案/集成测试/` 目录下已经有：
- 三份**输入材料**：`01-需求输入-用户故事与业务规则.md`（US-001~004、BR-01~06）、`02-设计输入-设计文档与架构图.md`（分层架构+2张mermaid图）、`03-设计输入-代码依赖清单.md`（类依赖表+3段代码取证+IP-1~6集成点清单）
- 一套**通用化的五步提示词**：`prompts/01~05-*.md`（按 RTGO v2.0 重新生成，占位符化、不绑定具体项目）

此前的旧版 `04-抽取步骤与RTGO提示词.md`、`05-输出-集成测试用例清单.md` 已从目录中被移除。现在需要**真正用 01/02/03 的内容跑一遍 prompts/ 里的五个提示词**，产出真实的中间结果和最终产物（而不是空的提示词模板）。

本计划明确五步的输入/输出对应关系、产出文件命名与位置、以及每步要忠实覆盖的关键点（尤其是 01 文档里标注的"本案例黄金坑" BR-03，以及 03 文档里故意保留的 `delete` 未调用 `canDelete` 的 BUG），确保实际生成内容时不遗漏、不编造。

## 输入材料复核（执行时直接引用，不重新编造）

- **US-001~004**：创建任务、标记完成、删除限制（已完成不可删）、状态统计
- **BR-01~06** 跨模块判定：BR-01 否 / BR-02 是（完成→事件→通知）/ **BR-03 是★**（删除需经 canDelete 校验，"必须进集成层"）/ BR-04 否 / BR-05 是（异常链路）/ BR-06 是（通知数量正负向）
- **设计侧接缝**（02）：Controller→Service→Repository 调用链；Service→ApplicationEventPublisher→NotificationService 事件链（★重点）；delete→canDelete 跨方法规则（★易漏）；异常映射；无外部依赖（内存仓储）
- **代码级集成点**（03）：IP-1 事件发布/订阅、IP-2 Service↔Repository 调用+数据、IP-3 create/assign/complete 跨方法编排、**IP-4 delete→canDelete→isCompleted★（当前代码有意保留 BUG：delete 未调用 canDelete）**、IP-5 异常链路、IP-6 外部依赖（本项目无）
- 技术栈线索：`ApplicationEventPublisher`、`@EventListener`、`@ExceptionHandler` 均为 Spring 特征，判定目标技术栈为 **Java + Spring + JUnit5**（Spring 部分为材料明证 `[FACT]`，JUnit5 为行业惯例推断 `[ASSUME]`，因为仓库中不存在真实的 TeamTodo 源码/pom.xml，第5步执行时会按 prompts/05 的规则显式声明"无既有测试代码风格样例"并标注假设）

## 关键约束（执行时必须遵守，避免复现旧案例的漏测问题）

1. **不得漏掉 BR-03 / IP-4**：这是 01 文档明确点名的"本案例黄金坑"，步骤1、3、4、5 都必须显式体现这条链路，且步骤4的用例要设计成"能揭示 03 代码里那个故意保留的 BUG"（即用例本身应该会失败，从而证明集成测试的价值）。
2. **不编造材料外内容**：所有类名/方法名/字段名必须来自 01/02/03 实际给出的内容（`TaskController`/`TaskService`/`NotificationService`/`InMemoryTaskRepository`/`Task`/`TaskStatus`/`TaskCompletedEvent`/`BusinessException` 等），材料未给出的细节（如具体 REST 路径、具体断言库版本）用 `[ASSUME]`/`[UNKNOWN]` 标注，不得硬编。
3. **每步末尾必须包含"反模式自检"章节**——这是 prompts/ 五份提示词 RTGO v2.0 结构的强制要求，执行时不能省略。
4. **每步产出需保留证据标签**（`[FACT]/[INFER]/[ASSUME]/[UNKNOWN]`）和来源可追溯性标注，供下一步直接复用，不重新整理丢失信息。

## 验证方式

由于这是内容生成任务（非可运行代码），验证采用人工可读的自查方式：
- 生成每个输出文件后，确认文件已落盘、章节完整（含反模式自检）
- 步骤3的"覆盖度"检查：确认需求侧 6 条 BR 与设计侧 6 个 IP 均被并入并集清单，无遗漏无重复
- 步骤4的"覆盖度自查表"逐条核对并集清单是否都生成了对应用例
- 步骤5生成的 Java 代码块做静态走查：确认每个 `@Test` 都能映射回一个 IT 编号，且删除规则相关的测试用例逻辑上会因 03 中的已知 BUG 而失败（体现集成测试抓到了缺陷）

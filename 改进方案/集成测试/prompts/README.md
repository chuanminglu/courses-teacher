# 集成测试用例抽取提示词库 · 使用说明

> 本目录（`prompts/`）是对上级目录 `04-抽取步骤与RTGO提示词.md` 中"6步抽取法 + R1~R4"的**重新组织与升级**：
> 1. 提示词结构从旧版 RTGO（R/T/G/O 简版）升级为 `.github/copilot-instructions-v2.md` 定义的 **RTGO v2.0 全量结构**（新增：已知反模式清单、反模式自检、证据分级标注 `[FACT]/[INFER]/[ASSUME]/[UNKNOWN]`、输出验收按"有无工具"分支）；
> 2. 内容做了**去项目化**处理——原 R1~R4 绑定了 TeamTodo 项目的具体文档名（如 `01-需求输入-用户故事与业务规则.md`）、具体类名（`TaskIntegrationTest`）、具体规则编号（`BR-03`）。本目录的 5 个提示词全部改为通用占位符（如 `{需求文档}`、`{既有测试代码风格样例}`），可直接套用到**任何项目**，只需替换【输入材料】部分。

---

## 一、5 个提示词与 6 个步骤的对应关系

原方案是 6 个步骤配 4 条提示词（R1~R4，步骤3/4/5 合并为 R3）。本目录拆分为 **5 条提示词**，让"合并去重"独立成一步，颗粒度更细、每条提示词职责更单一，也更方便单独调试某一步的输出质量：

| 步骤 | 做什么 | 输入 | 输出 | 对应提示词 |
|---|---|---|---|---|
| 1 | 从需求圈"跨模块规则" | 需求文档 | 候选链路（需求侧） | `01-需求侧候选集成链路抽取.md` |
| 2 | 从设计/代码列集成点 | 设计文档 + 代码依赖清单 | 集成点清单（设计侧） | `02-设计代码侧集成点抽取.md` |
| 3 | 交叉合并、去重 | 步骤1 + 步骤2 的输出 | 候选链路并集清单 | `03-候选链路合并去重.md` |
| 4 | 按风险×复杂度排序 | 步骤3 的输出 | 优先级标注 | `04-优先级排序与用例文档生成.md`（前半部分） |
| 5 | 生成用例文档 | 步骤4 的排序结果 | 集成测试用例文档（IT-001~） | `04-优先级排序与用例文档生成.md`（后半部分，与步骤4合一条提示词一次性产出） |
| 6 | 落到自动化测试代码 | 用例文档 | 测试代码 | `05-用例转自动化测试代码.md` |

> **为什么步骤4和5合并成一条提示词**：排优先级本身就是用例文档里的一个字段（优先级列），拆成两次对话反而要在两轮之间重复传递并集清单，不如一次性产出"排序说明 + 用例表 + 覆盖度自查"。如果你的团队希望两步严格分开执行，也可以把 `04-...md` 的【O-输出要求】拆成两次调用：第一次只要"第1部分：优先级排序说明"，第二次把排序结果作为新输入喂回去，要"第2部分：用例清单"。

## 二、逐条使用方法

### 通用步骤

1. 打开对应编号的提示词文件（如 `01-需求侧候选集成链路抽取.md`）
2. 找到【T - 任务描述】下的"输入材料"小节，把里面的占位符（`【在此粘贴或引用】...`）替换成你项目的真实内容
3. 把整段提示词（含替换后的材料）交给 AI 执行
4. AI 的输出末尾会附"反模式自检"章节——**先看这一节**，确认输出没有踩已知的常见坑，再采信正文内容
5. 把本步输出作为下一条提示词的输入材料，依次执行 01 → 02 → 03 → 04 → 05

### 各步骤要点

| 提示词 | 关键输入 | 你需要做的替换 |
|---|---|---|
| 01 | 需求文档 | 粘贴用户故事/业务规则/验收标准原文 |
| 02 | 设计文档 + 代码依赖清单 | 粘贴架构图/时序图 + 类依赖或调用关系（没有代码可只给设计文档，提示词里已说明如何降级处理） |
| 03 | 01 和 02 的完整输出 | 直接把上两步的表格原样粘贴，不要自行先手动去重 |
| 04 | 03 的完整输出 + 用例模板字段 | 如果项目有固定的用例文档字段（如公司统一模板），替换"材料2"里的默认字段列表 |
| 05 | 04 的用例表 + 既有测试代码风格样例 + 目标技术栈说明 | 这是唯一需要"项目特异化"输入的一步——必须提供 1-2 个项目现有测试文件作参考，否则生成代码风格会跑偏 |

## 三、与旧版（04-抽取步骤与RTGO提示词.md 中的 R1~R4）的差异对照

| 维度 | 旧版 R1~R4 | 本目录 5 条提示词 |
|---|---|---|
| RTGO 结构版本 | v1.x（角色/任务/目标/输出，简版） | v2.0（新增反模式清单、反模式自检、证据分级标注、输出验收分支） |
| 是否绑定具体项目 | 是，示例材料写死 TeamTodo 的文档名、类名、规则编号 | 否，全部占位符化，替换材料即可用于任何项目 |
| 步骤3/4/5 | 合并为一条 R3 | 拆分为独立的 `03-...` + `04-...`，颗粒度更细 |
| 步骤6 技术栈假设 | 写死 Java + Spring Boot + JUnit 5 | 通用化，通过"目标技术栈说明"材料适配任意语言/框架 |
| 幻觉防护 | "禁止编造 + 信息不足标【需确认】" | 在此基础上新增 `[FACT]/[INFER]/[ASSUME]/[UNKNOWN]` 分级标签 + 区分"有无工具可查"的验证方式 |

**旧版文件不删除、不覆盖**：`04-抽取步骤与RTGO提示词.md` 保留作为该项目（TeamTodo 案例）的历史记录和讲师演示素材；本目录是可复用到其他项目的通用版本。两者定位不同，互不替代。

## 四、适用场景建议

| 场景 | 怎么用 |
|---|---|
| 新项目第一次做集成测试用例设计 | 按 01→05 顺序完整走一遍 |
| 需求或设计��变更，需要增量维护用例 | 只重跑受影响的步骤（如只改了需求，重跑 01→03→04；设计未变可跳过 02） |
| 讲师教学演示 | 依次展示 01→02→03，让学员看到"两条独立输入线如何交叉验证、互补盲区" |
| 团队沉淀通用测试设计流程 | 直接把本目录作为团队的提示词库基线，各项目使用时只替换"输入材料" |

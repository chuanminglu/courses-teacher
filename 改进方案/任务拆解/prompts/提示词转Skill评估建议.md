# 提示词转Skill评估建议

评估对象：`单任务实现-subagent提示词.md`、`迭代任务分解-subagent提示词.md` 两份 RTGO 结构 subagent 提示词，能否/如何转化为 Claude Skill，重点是转化过程中不丢失"生成故事/任务拆解"的细节。

评估方法：基于 skill-creator 技能的框架（progressive disclosure、frontmatter 触发机制、自由度分级等）逐条对照分析。

结论：**转成 skill 可行，但风险点集中在"改写"这道工序本身，不在"要不要拆"。**

---

## 1. 拆成两个独立 skill，而不是一个 skill 内部路由

两份文件都在 500 行阈值以内（196 行 / 216 行），且分属流水线两个不同触发时机（迭代规划期 vs 单任务派发前），各自独立触发比"一个 skill + 内部选哪个 reference"更省上下文、触发判断也更干净：

- `sprint-task-decomposition`（对应"迭代任务分解"）
- `task-implementation-brief`（对应"单任务实现展开"）

## 2. 转换方式：原文"近乎照搬"进 SKILL.md 正文，不要用 LLM 改写/精简

这是保住细节最可靠的方法——凡是"重新表达"这道工序都有丢失风险，尤其这几类最容易在改写中消失：

- **具体数字阈值**：自查"8 次工具调用以内"、命中"几十个以上文件"判定为过宽——这些一旦被"总结"成"适度自查"就废了。
- **反例场景**（v2/v3/v4"源于真实踩坑"的那几条）：登录墙 flag 形同虚设、旧表未纳入新 schema 机制——这些反例是规则的记忆锚点，摘要时最容易被删掉，删掉后模型在类似场景下很难自己联想到要触发这条规则。
- **"如无 XX，必须显式写'无，……'"这类禁止留空的措辞**：看着像可有可无的文风要求，实际是防止模型偷懒漏字段的硬约束。
- **证据分级 `[FACT]/[INFER]/[ASSUME]/[UNKNOWN]` 与"假设与待确认项"清单的联动校验**（标了 `[ASSUME]` 必须同步出现在清单里）——这是跨段落的一致性规则，分段/分文件整理时容易脱钩。

## 3. Frontmatter description 要能互相区分触发时机

两个 skill 的 description 除了写"做什么"，必须写清楚"什么时候用"，避免互相抢触发：

- 迭代任务分解：触发词类似"迭代规划、多故事拆解、纵向切片、Walking Skeleton"
- 单任务实现展开：触发词类似"任务派发前、生成实现说明、单任务展开"

## 4. 有一处硬引用必须改，其余尽量不动

"迭代任务分解"产出末尾"如何生成单任务实现说明"一节点名了 `单任务实现-subagent提示词.md` 这个文件名。转成 skill 后这处要改成指向新 skill（按技能名或触发短语），否则 Claude 读到旧文件名会去找一个不存在的文件——这是唯一必须动的内容，正文其余部分建议原样保留。

## 5. 执行方式：不必强制走子 agent

两份原文都写了"不管你是被派去执行它的 subagent、另一个新对话，还是人工阅读"——说明作者本来就设计成任何执行体都能直接照做，不依赖"必须 spawn 子 agent"。转成 skill 后可以让主线程直接执行（更符合"任务拆解/文本生成直接自己写、别甩给子 agent"的习惯）。"每个故事自查预算 8 次调用"那条暗示了多故事场景可选择按故事并行发子 agent 做自查，这是可选的性能优化，不是必须项。

## 6. 建议加一步回归验证再启用

用一个历史真实故事/任务，同时跑"旧 prompt 手工调用"和"新 skill 触发"，逐字段 diff 产出结构（背景/预计涉及文件/技术选型/隐含规则/DoD/假设清单……），确认没有字段被简化或漏写。

## 7. 命名风格

参考仓库里已装的 `training-deck-visuals`、`sprint-execution-log`（英文 kebab-case 名 + 中文 description），两个新 skill 建议同样用英文 slug、中文 description，风格保持一致。

---

## 8. 前置条件不能丢：嫁接方案

`sprint-tasks-lean` 的"触发条件"+"前置检查"+"输入/输出"这三块，新提示词自己没有——它假设 `{{SPRINT_NAME}}`/`{{SPRINT_GOAL}}`/`{{STORIES}}`/`{{REPO_PATH}}` 是调用方已经准备好塞进来的变量，不管这些变量从哪来。转成 skill 后这块空白必须由 `sprint-task-decomposition` 的 SKILL.md 补上，而不是丢掉，具体嫁接方式：

- **触发条件**：原样保留 `sprint-tasks-lean` 现有三条（lean 流水线需要生成 Sprint 任务 / 用户说"生成 Sprint N 的任务" / 已完成 `release-plan-lean`）。
- **前置检查**：原样保留"必须存在 `docs/sprints/release-plan.md` + `docs/requirements/user-stories/`，缺失则提示先跑 `release-plan-lean`"这条硬门禁；`docs/design/api-contract.md`/`schema.md` 降级为"推荐存在，可提升自查质量"，不是新提示词的必填材料。
- **变量装配**：新增一步"读取上游文档 → 装配新提示词材料"的映射说明——`release-plan.md` 里的 Sprint 目标 → `{{SPRINT_GOAL}}`；`user-stories/` 下对应故事详情 → 拼成 `{{STORIES}}`列表（多故事一次性拼入，对应新提示词的多故事版设计）；当前工作目录 → `{{REPO_PATH}}`。这一步是旧 skill 没有、新提示词也没写、但两者对接必须存在的"胶水层"，需要新写，不能照搬。
- **生成模式（single/all）**：保留，映射为"把 `release-plan.md` 里目标 Sprint 的全部故事 vs 单个故事拼进 `{{STORIES}}`"。
- **输出路径**：保留 `docs/sprints/sprint-{N}/tasks.md`，与新提示词"对齐 tasks.md 格式"的既定目标一致，不用改。

## 9. 技术栈固定问题：定位与最小修复

自查结论：**两份提示词正文里只有一处真正的技术栈耦合**，不是通篇假设了前后端技术栈——`迭代任务分解-subagent提示词.md` 第57行：

> 标签取值与判断依据严格对齐 `VueReact+Java专用Harness商业方案.md`附录A的模型路由决策树，不要自创标签名

追查了这个被引用的文件（实际躺在 `/mnt/d/Programs/tasksplitting/docs/任务拆解/` 等下游客户项目仓库里，courses-teacher 内不存在），读取其附录A发现：**决策树内容本身完全与技术栈无关**（就是"任务复杂度标签 → 模型档位/成本倍数"的映射表 + 兜底规则，如"17B连续3轮spec-verifier未过→自动升级一档"），标题里的"VueReact+Java专用"只是这份文档作为一份**商业销售方案**（内含客户报价模板）在讲述"该商业方案主打的规则库覆盖哪个技术栈组合"，标签路由树本身不认这个限定。而且这棵决策树的完整内容早就**原样内嵌**在提示词第59-63行里了（`crud`/`business-logic`/`refactor`/`algorithm`等八类判断依据都已写全）。

**结论**：这不是"提示词固定了技术栈"，而是"提示词里有一处指向外部商业文档的悬空引用，且该引用的限定词具有误导性"。修复方式是删除性的，不是改写性的，不违反"近乎照搬"原则：

- 把第57行改成"标签取值固定为以下八类，不要自创标签名"，直接砍掉对 `VueReact+Java专用Harness商业方案.md` 的引用——因为决策树内容已经完整内嵌在下一句，这处引用本来就是冗余的，删掉不损失任何信息，反而消除了一个转成 skill 后必然指向不存在文件的死引用。
- 复查确认 `单任务实现-subagent提示词.md` 全文没有任何技术栈相关关键词（Spring/React/Vue/Node/Java/npm/mvn等），它完全靠 `REPO_PATH` 自查判断技术栈，天然通用，不需要改动。
- 你之前感觉"两份提示词固定了技术栈"，根源更可能是**已经跑出来的示例产出**（`登录故事-任务清单v3-SpringBoot.md`、`登录故事-单任务实现清单v3-SpringBoot-PRonly.md`）恰好都是 Spring Boot + React 案例——这是"用哪个项目试跑"的偶然结果，不是提示词本身的限定，见下一节如何处理这类示例。

## 10. 确保单任务细节不丢失：把示例做成"形状基准"资源

`skill-creator` 的自由度分级框架（见其 SKILL.md "Set Appropriate Degrees of Freedom"）明确说：操作脆弱、容错率低、要求一致性时用**低自由度**（具体模板、少参数）。单任务实现说明恰好是这种场景——证据分级`[FACT]/[INFER]/[ASSUME]/[UNKNOWN]`跨段落联动、"如无XX必须显式写'无，……'"这类反偷懒措辞，都是专门为了压住**弱模型（如 qwen 3.8 37b）在压力下漏字段/糊弊过关**这个具体失败模式设计的，不是"Claude已经会的常识"，所以不能按 skill-creator "只加 Claude 不知道的东西"这条一般原则去精简——这条一般原则在这里的适用结论就是"几乎全部保留"，与第2条已有结论一致。

在此基础上新增一步：**把 `登录故事-单任务实现清单v3-SpringBoot-PRonly.md`（或其中1-2个任务，如T00101+T00102）打包成 `task-implementation-brief` 技能的 `references/example-output.md`**，作为完整产出的"形状基准"（few-shot 锚点），而不是当成技术栈要求：

> 这里刻意不点名具体验证用的模型型号——约束是按"最脆弱的执行者"设计的，规则对弱模型能过关，对更强的模型必然也能过关（单向兼容，不是双向对等），SKILL.md 正文里写具体模型名反而会被误读成"如果执行者是更强的模型，这条可以省"。具体用什么模型做过回归验证，只应该记在内部测试记录里，不写进技能正文。

- 在 SKILL.md 正文里显式声明这份引用的性质："以下示例的**章节结构、字段颗粒度、证据分级用法、'明确不要做的事'的详尽程度**是必须达到的基准，示例里的 Spring Boot/React/JdbcTemplate 等具体技术选型只是该次试跑的产物，换成任何技术栈时按当次 `REPO_PATH` 自查结果替换，不代表本技能绑定这个栈"——把"形状"和"内容"显式拆开说，避免弱模型把示例里的具体技术名词当成必须复用的方案。
- 这一步同时是对第2条"回归验证"建议的具象化：以后任何一次技能改动，都可以拿这份示例反查"新版本产出是否还保留了同等颗粒度"，比单纯"跑一次看着像不像"更可核查。

## 11. 下游耦合风险的处理方案（已定案）

追查 `sprint-execution-log` 和 `ai-dev-workflow` 两个下游技能的真实字段依赖后，发现的三处耦合点，逐一定案如下。

### 11a. 工时字段：补回，但放宽粒度

`sprint-execution-log` 的 `rollup`/看板模板里有"实际工时 / 计划工时"和跨Sprint"累计工时"统计（`references/templates.md` 第200/252/261行），数据源是旧格式每个任务的"工时"属性，新提示词没有。**处理**：在新任务清单模板每个任务的checkbox属性行里补回"预计工时：{X}h"，紧跟"路由建议标签"之后。

但旧skill"不允许半天/一天粒度，必须按小时估算"这条约束不能原样搬过来——那是给FE/BE/Mock横向拆分（任务天然窄）定的规矩，纵向切片一个任务经常一口气改schema+后端+前端（参照T00101），天然更大。硬套"必须按小时"会诱导模型为了凑小时数把纵向切片拆得更碎，反而破坏"每个任务独立可验证、独立成PR"这条优先级更高的原则。**放宽为**：允许出现半天粒度（参照故事级"S≈15h, M≈35h, L≈70h"的口径类比到单任务），不强制卡死在小时以内。

### 11b. 依赖字段：不做自由文本，走确定性推导

旧格式的"依赖"是自由文本，因为FE/BE/Mock互相之间的依赖关系不是线性的。纵向切片方法论下，同一故事内的任务天生严格线性（T00102必然依赖T00101，示例里每个任务的"背景"也写"这是第N/总数个任务"），不需要重新引入开放式依赖字段让模型每次现场判断。**处理**：新任务清单模板加"依赖"字段，规则固定为——同故事内任务=该故事的前一个任务（第一个任务=无）；跨故事依赖=引用"跨故事依赖与文件冲突排查"一节的结论。`sprint-execution-log` 要读的"依赖"字段由此有了确定、可推导的来源，比旧格式的自由文本还更可靠。

### 11c. AI模式：折叠进 `sprint-task-decomposition`，`ai-dev-workflow` 整段退休

`ai-dev-workflow` 的真实职责是四步，不是两步：①任务分类（复杂度×参考可用度→AI模式）②Subagent适用性判断 ③生成Subagent Prompt ④批次/并行执行规划（含"不共享文件/迁移/契约/配置"的并行门槛规则）。四步现在全部有主：

- ①② → 折叠进 `sprint-task-decomposition`，复用"路由建议标签"同一次自查结果，不新增自查预算。映射规则：`crud/config/test-generation/simple-ui`→🟢；`business-logic`→🟡；`refactor/integration`→🟡（跨模块天然需要更多协调）；`algorithm/novel-design/performance-tuning`→🔴（有方案时）或🟣（无方案需调研时）。外加一条**否决规则**：任务涉及生产数据迁移、不可逆操作、合规红线，无论复杂度多低，强制🔴，不能🟢——这是 `ai-dev-workflow` 原"风险"维度里唯一不能丢的安全底线，需要显式写成否决规则，而不是被复杂度映射覆盖。
- ③ → `task-implementation-brief` 的产出本来就是"Subagent Prompt"的超集（背景+技术选型+隐含规则+DoD全套，远比"任务/输入/输出/约束/参考"几行详尽），直接取代。
- ④ → 本质是"拿依赖字段（11b）+跨故事文件冲突排查结果做拓扑排序+冲突过滤"，是机械推导，不需要独立LLM判断；`sprint-task-decomposition` 自己产出的数据已经够用，最多在输出里锦上添花加一张依赖图/执行计划表（可选，不强制）。

四步全部有主之后，`ai-dev-workflow` 在这条流水线里没有剩余职责，**应从"下一步"下游链路整体移除，不是缩小范围保留**。

## 12. 路由标签是否完整：技术使能故事（如"搭建后端脚手架"）怎么处理

现有八类路由标签的判断依据全部隐含一个假设——仓库里已经有代码存在、正在被延伸或修改（措辞如"跨模块""照既有模式复制""没有可复制的既有模式，需要从头设计方案"，全部相对"已有代码"而言）。当故事本身就是"从零搭建"（新建后端脚手架、初始化CI/CD、引入日志框架……这类不面向最终用户、面向团队技术能力的故事——即"技术使能故事"）时，这个假设不成立：自查会发现仓库里什么都没有，如果机械套用字面判断依据（"没有可复制的既有模式"→`novel-design`），会把一个按框架官方文档初始化就能完成的成熟任务，误判成"需要架构创新"的高复杂度档，再经11c的映射规则连带误判成🔴人工主导——这是会真实发生的误判，不是假设性风险。

**根因**：判断依据没有区分"仓库无先例"的两种截然不同原因——(1) 这是全新技术能力，**行业**内都没有成熟范式，真的需要从头设计 → `novel-design`；(2) 只是**这个仓库**还没人搭过，但**行业**早有官方标准做法（框架官方脚手架命令/官方starter模板/官方文档），复制现成范式即可 → 应归入 `crud/config`。

**修复方案（都是在现有规则上补判断依据，不是推翻重来）**：

1. **路由标签判断依据补一句区分**：`novel-design`适用的"没有可复制的既有模式"，指的是**行业内**没有成熟范式可循，不是"本仓库恰好还没写过"；后者只要能在框架官方文档/官方脚手架命令里找到对应的标准初始化流程，即使本仓库是从零开始，也归入`crud/config`，判断依据写"照官方标准初始化流程完成，不需要自创架构方案"。
2. **AI模式否决规则不需要单独改**：①修好之后，`crud/config`→🟢的默认映射自然适用，这条是①的因果结果，不是独立缺口，只是要在文档里说明这个因果关系，避免后续维护者误以为AI模式映射规则本身有漏洞。
3. **Feature Flag设计字段需要一个豁免出口**：纯技术使能故事（脚手架搭建/依赖升级/CI配置/日志框架引入……）往往不引入任何"用户可观察的行为变化"，强套"特性开关设计：类型/命名建议/翻转条件"这个必产出字段，会变成为了填表而编造一个没有意义的flag。补一条判断标准：**这个故事有没有一个用户能感知到的入口/行为差异（新页面、新按钮、新API对外暴露、既有行为改变）？如果彻底没有，"特性开关设计"字段允许显式写"无需Feature Flag：本故事不引入任何用户可观察的行为变化，理由：{一句话}"，不能留空但也不强套Release Toggle。**
   - **连带修改点**：`task-implementation-brief` 的输出模板"背景"段落里硬编码了"本任务完成后，整体功能仍由 `{flag命名}` 特性开关包裹"这一句，需要加一个条件分支——材料2（STORY_CONTEXT）里的flag字段是"无需Feature Flag"时，这句话要相应改写，不能死套，否则两个技能会在这一点上脱节。
4. **切片排序技巧补一类（新增，不是修复）**：现有六种切片技巧（按工作流步骤/业务规则变化/数据输入变体/CRUD操作/happy-unhappy path/延迟非核心工作）全部假设故事有业务逻辑可切，技术使能故事没有业务逻辑。补充"**按基础设施分层**"：先让工程跑起来（能启动+健康检查）→ 再加持久层连接 → 再加统一异常处理/日志 → 再加CI流水线……每一层仍要有验收标准，只是用**可执行命令**代替业务断言（如"`mvn spring-boot:run`成功+`curl /health`返回200""`mvn test`通过""CI流水线首次跑绿"）。

## T00101：端到端骨架——访客提交预约并拿到预约编号

你要做的事：为访客打通"从公众号菜单进入预约页面 → 填写并提交预约信息 → 服务端落库并生成唯一预约编号 → 页面显示提交成功与预约编号"这条端到端链路，并在本次一并落下该链路所需的表结构、访客身份归属与 `visitor-booking-enabled` 开关判断。
对应验收标准：
- F1：访客可以通过微信公众号入口访问预约功能（关注公众号 → 点击菜单"来访预约" → 打开预约页面）
- F2：访客可以填写完整的预约信息并提交（填写姓名、手机号、来访时间、被访人、来访事由 → 点击"提交预约" → 显示提交成功）
- F3：提交预约后系统生成唯一的预约编号（提交成功后显示预约编号，如：YY20251226001）

### 你要做什么

**后端**

- 新增数据库迁移脚本（Flyway 版本化脚本），建下表与取号表，目标 DDL 可直接照抄（字段长度、字符集若与仓库既有规范冲突，以仓库规范为准；**不要**在脚本里使用"重复执行也不报错"的猜测性语法，脚本的幂等由迁移工具的版本表保证）：

```sql
CREATE TABLE visitor_booking (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  booking_no      VARCHAR(20)  NOT NULL COMMENT '预约编号 YY+yyyyMMdd+3位日内流水',
  visitor_openid  VARCHAR(64)  NOT NULL COMMENT '微信 openid，归属键',
  visitor_name    VARCHAR(20)  NOT NULL,
  mobile          VARCHAR(11)  NOT NULL,
  visit_time      DATETIME     NOT NULL,
  host_name       VARCHAR(20)  NOT NULL,
  reason          VARCHAR(200) NOT NULL,
  status          VARCHAR(16)  NOT NULL COMMENT '本任务只写入 PENDING',
  created_at      DATETIME     NOT NULL,
  updated_at      DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_visitor_booking_no (booking_no),
  KEY idx_openid_created_at (visitor_openid, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE booking_no_seq (
  seq_date  DATE NOT NULL,
  last_seq  INT  NOT NULL,
  PRIMARY KEY (seq_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 编号生成器（签名可直接照抄，包名以仓库实际根包为准）：

```java
public interface BookingNoGenerator {
    /** date 为服务器提交日期（Asia/Shanghai），非 visitTime 的日期 */

}
```
  实现要点：同一事务内对 `booking_no_seq` 中 `date` 对应行取号并自增（不存在则插入 `last_seq=0` 后自增），拼装 `"YY" + date.format(BASIC_ISO_DATE) + String.format("%03d", seq)`；捕获唯一键冲突后重试，最多 3 次。

    public ResponseEntity<BookingCreateResponse> create(@RequestBody BookingCreateRequest request) { ... }
}

public record BookingCreateRequest(

  成功返回 `201` + `BookingCreateResponse`（`status` 固定为 `PENDING`）。**请求体中的 `openid`/访客身份字段一律忽略**，归属键从服务端会话取（见下条）。本任务只做"必填字段缺失返回 400"这一层，不做字段格式规则。

- 微信网页授权：`GET /api/visitor/wechat/authorize` 302 跳转微信授权地址；`GET /api/visitor/wechat/callback?code=...&state=...` 用 `code` 换 `openid` 后写入服务端会话，再重定向回 `/booking/new`。业务代码从会话读取 `openid`，不接收前端传入。

- flag 判断：`VisitorBookingFlag` 组件 + 拦截器，`/api/visitor/**` 在 flag 关闭时直接返回 `404`，不进入业务逻辑、不落库。

- 统一错误响应：`@RestControllerAdvice` 输出 `{"code","message"}`；未捕获异常不得把堆栈返回给前端。

**从验收标准推导出的隐含规则**（必须逐条列出并要求实现，不得遗漏）：

1. **校验执行位置** → 后端必须强制校验（权威判定），前端在提交时做同规则的本地校验以获得即时反馈；前端校验不通过时不发起请求。**不采用**仅前端校验：请求可被直接构造，绕过前端即可写入非法数据；**不采用**仅后端校验：会让用户在提交后才知道错误，与 D1~D6"点击提交 → 提示"的即时性描述相悖。依据：D1~D6 描述的是"点击提交后提示"，未排除前端预校验，但后端权威性由接口可被直接调用这一事实决定。`[ASSUME]`
2. **校验错误返回契约** → HTTP `400`，响应体 `{"code":"VALIDATION_ERROR","message":"<首条错误文案>","errors":[{"field":"<字段名>","message":"<文案>"}]}`；字段名取请求体属性名（`name`、`mobile`、`visitTime`、`reason`）。**不采用**纯文本错误或 `200 + 业务错误码`：前者无法逐字段定位，后者会让前端把所有响应都当成成功处理。依据：后续任务（T00105、T00106）还要在同一接口上追加业务规则错误，需要一个可扩展的错误载体。`[ASSUME]`
3. **多字段错误的返回策略** → 字段级错误一次性全部返回；同一字段只保留一条，优先级为"必填 > 长度/格式"。**不采用**"只返回第一条错误"：会让用户逐条试错；**不采用**"同一字段返回多条"：D1 对姓名空值与长度越界给了两条不同文案，同时出现会让用户看不懂该改什么。依据：D1、D2、D6 的文案按"缺失"与"不合法"分开描述，说明这是两种互斥场景。`[ASSUME]`
4. **时间判定基准** → 以服务器时间为基准（时区固定 `Asia/Shanghai`），判定条件为 `visitTime` 严格大于当前时刻；等于当前时刻同样拒绝。**不采用**以浏览器本地时间为准：客户端时间可被篡改，且与服务器时区不一致时会给出相反结论。依据：D3 的"必须为未来时间"与文案"来访时间不能早于当前时间"。`[ASSUME]`
5. **校验实现方式** → 在请求 DTO 上使用声明式校验注解承载 D1、D2、D6，用自定义校验器承载 D3（需要当前时间），校验器通过构造注入 `Clock`。**不采用**在 Controller 内手写一串 `if` 判断：文案与字段的对应关系会散落，无法被测试单独覆盖。`[ASSUME]`
   - 具体注解名称、分组校验行为、空值是否触发长度校验等细节均未实测（`[ASSUME]`）；若所选校验框架的行为与预期不符（例如空字符串同时触发"必填"与"长度"两条），可替换为语义等价的实现（显式自定义校验器、或在进入校验前统一做 trim），不算偏离本选型决策；但"字段级错误一次性返回、同一字段只留一条"这一契约不允许更换。
6. **校验规则常量**（取值与文案 `[FACT]`，逐字来自材料1 的 AC，不得改写）：姓名 `2~20` 字符、提示"请输入姓名"与"姓名长度为2-20个字符"；手机号 11 位、提示"请输入正确的手机号"；来访时间须为未来、提示"来访时间不能早于当前时间"；来访事由不少于 5 个字、提示"请输入来访事由（至少5个字）"（含全角括号）。

### 你要做什么

**后端**

```java
public record BookingCreateRequest(
        @NotBlank(message = "请输入姓名")
        @Size(min = 2, max = 20, message = "姓名长度为2-20个字符")
        String name,

        @NotBlank(message = "请输入正确的手机号")
        @Pattern(regexp = "^1[3-9]\\d{9}$", message = "请输入正确的手机号")
        String mobile,

        @Future(message = "来访时间不能早于当前时间")

```

### 技术选型

1. **取消接口形态** → `POST /api/visitor/bookings/{bookingNo}/cancel`，无请求体；成功返回 `200` + `{"bookingNo":"...","status":"CANCELLED"}`。**不采用** `PUT /bookings/{no}/status` 由前端传目标状态：状态机迁移应由服务端决定，前端传状态等于把状态机交给客户端；**不采用** `DELETE`：本任务是状态变更不是删除，用 `DELETE` 会误导调用方以为记录被移除。依据：F5 的"状态变为'已取消'"是服务端状态迁移语义。`[ASSUME]`
2. **状态流转的落库方式** → 单条条件更新 + 受影响行数判定：

```sql
UPDATE visitor_booking
   SET status = 'CANCELLED', updated_at = :now
 WHERE booking_no = :bookingNo
   AND visitor_openid = :openid
   AND status = 'PENDING';
```
  受影响行数 `1` 表示取消成功；`0` 表示"不存在/非本人/状态不可取消"，再按一次只读查询区分是哪种（用于决定返回 `404` 还是 `409`）。**不采用**"先查询状态、判断后再更新"：两个并发请求会同时通过判断，导致第二次取消覆盖 `updated_at`、或在后续引入审核状态后覆盖审核结果。依据：F5 的状态迁移必须对并发安全。`[ASSUME]`
   - 具体 SQL 语法与事务行为未实测（`[ASSUME]`）；若所选数据库/ORM 不支持行数判定（如某些 ORM 的条件更新返回 void），可替换为语义等价的实现（先按主键加行锁再更新，或更新后回查状态），不算偏离本选型决策；但"以数据库条件更新作为唯一裁决点"这一设计不允许更换。
3. **不可取消状态的处理** → 前端详情页仅在 `status=PENDING` 时渲染"取消预约"按钮；后端仍独立判定，状态不满足时返回 `409` + `{"code":"BOOKING_NOT_CANCELLABLE","message":"该预约当前状态不可取消"}`。**不采用**"前端不显示按钮即视为控制"：请求可被直接构造；**不采用** `200` + 业务错误码：会让前端把所有响应都当作成功分支处理。依据：F5 把可取消范围限定为"未审核的预约"。`[ASSUME]`
4. **取消的语义** → 状态变更（软取消），不做物理删除，不额外新增"取消原因""取消时间"等字段之外的扩展（`updated_at` 已能反映取消时刻）。依据：F4 要求列表展示历史预约及其状态，F5 要求状态变为"已取消"——记录必须继续存在。`[INFER]`
5. **非本人/不存在资源的响应** → 取消他人预约或取消不存在的编号，一律返回 `404`（不可区分），不返回 `403`。依据：与 T00103 一致——不向非本人暴露他人数据的存在性。`[INFER]`

### 你要做什么

**后端**

- 新增取消接口（签名可直接照抄，包名与既有命名以仓库为准）：

```java
@PostMapping("/{bookingNo}/cancel")
public CancelBookingResponse cancel(@PathVariable String bookingNo) { ... }

public record CancelBookingResponse(String bookingNo, String status) {}
```
- 服务层实现要点（可直接照抄的判定顺序）：
  1. 从服务端会话取 `openid`（不接收前端传入的归属键）；
  2. 执行「技术选型 #2」给出的条件更新；
  3. 受影响行数 = 1 → 返回 `200` + `{"bookingNo","status":"CANCELLED"}`；
  4. 受影响行数 = 0 → 按 `booking_no` 只读查询一次：查不到或 `visitor_openid` 不匹配 → `404` + `{"code":"BOOKING_NOT_FOUND","message":"预约不存在"}`；查到但 `status != 'PENDING'` → `409` + `{"code":"BOOKING_NOT_CANCELLABLE","message":"该预约当前状态不可取消"}`。
- 状态常量：本任务首次写入 `CANCELLED`，取值必须与 T00103 定义的状态字典一致（`PENDING`、`CANCELLED`），不得新造第三个取消相关取值（如 `CANCELED`）。

**前端**

- 详情页：`status === 'PENDING'` 时渲染"取消预约"按钮；点击后弹出二次确认，用户确认才发起 `POST /api/visitor/bookings/{bookingNo}/cancel`，用户取消则不发请求。
- 取消成功：就地把页面状态更新为"已取消"（取响应体的 `status`），并同步列表页展示；不做整页硬刷新。
- 取消失败（`409`）：展示后端 `message`，并把按钮切换为不可用状态；失败（`404`）：提示"预约不存在"并返回列表页。

**从验收标准推导出的隐含规则**（必须逐条列出并要求实现，不得遗漏）：

- H1 可取消范围严格限定为"待审核（`PENDING`）"状态；已取消的记录以及后续由其他故事引入的任何状态一律不可取消 `[INFER]` —— 依据 F5 的"取消未审核的预约"："未审核"是对可取消范围的限定，不能实现为"任何状态都能取消"。
- H2 取消必须校验归属，只能取消本人的预约 `[INFER]` —— 依据 F5 的操作入口位于本人的预约详情页，与 F4"我的预约"的归属语义一致：不校验归属会造成越权取消他人预约。
- H3 同一预约被并发取消（如同一个用户连点两次）必须只成功一次，另一次不得返回 5xx、不得造成状态漂移 `[INFER]` —— 依据 F5"状态变为'已取消'"：重复执行同一操作不应改变结果，也不应把用户的重复点击变成系统错误。
- H4 取消是状态变更而非物理删除，被取消的记录必须继续出现在"我的预约"列表并显示"已取消" `[INFER]` —— 依据 F4（列表展示历史记录与状态）与 F5（状态变为已取消）：若删除记录，F4 的历史列表与状态展示将失去对象。
- H5 取消后详情页与列表页读到的状态必须一致（同为"已取消"） `[INFER]` —— 依据 F4 与 F5 指向同一份预约记录：两个页面对同一记录给出不同状态即为缺陷。
- H6 前端不渲染取消按钮不构成访问控制，后端必须独立判定状态与归属 `[INFER]` —— 依据 F5 的"未审核"限定：按钮显隐可被绕过，合法性判定必须在服务端。

### 技术选型

1. **人员名录的数据来源与访问方式** → 定义一个显式的客户端接口（如 `EmployeeDirectoryClient.findByName(String)`）访问企业内部人员名录（HTTP 调用，超时 2 秒，结果做 5 分钟本地缓存），**不采用**在本任务新建"员工表"或做名录数据同步：名录由人事侧维护，复制一份会引入陈旧数据与同步任务，而本故事没有任何维护名录的验收标准；**不采用**直接查既有访客系统的内部表：跨模块直连会把两个系统的表结构耦死。依据：D5 要求"必须在企业人员名录中"，需要一个可替换、可打桩的名录访问边界。`[ASSUME]`
2. **名录不可用时的策略** → fail-closed：查询超时或返回错误时拒绝本次提交，提示"暂时无法校验被访人，请稍后重试"（该文案为本任务新增，材料未给）。**不采用** fail-open：会让名录外的人写入系统，使 D5 在校验服务抖动时静默失效；**不采用**直接抛 5xx：把外部依赖故障暴露成系统错误，访客无法理解。依据：D5 是"必须在名录中"的硬约束。`[ASSUME]`
3. **工作日历来源** → 新增一张按日期记录"是否工作日"的日历表（由运营维护节假日与调休），判定时查该表；查不到该日期时按"周一至周五为工作日"兜底，并记录一条告警日志以备补录。**不采用**仅按星期几硬编码判断：中国法定节假日与调休无法用星期几表达，硬编码会在节假日放行非法预约，与 D4 冲突。依据：D4 的"非工作日"。`[ASSUME]`
4. **时间语义** → 时区固定 `Asia/Shanghai`（服务器若为 UTC，需显式转换后再做判定与展示）；可预约窗口为工作日的 `09:00 ≤ t < 17:00`（即 17:00 整点不可选，09:00 整点可选）；本任务不设"最多可提前 N 天"的上限（材料未给，不臆造）。**不采用**右闭区间 `09:00 ≤ t ≤ 17:00`：17:00 为下班时刻，纳入窗口会产生"来访时间等于下班时间"的歧义。依据：D4 的文案"请选择工作日09:00-17:00的时间段"。`[ASSUME]`
5. **业务规则错误的返回契约** → HTTP `422` + `{"code":"TIME_OUT_OF_RANGE","message":"请选择工作日09:00-17:00的时间段"}` 或 `{"code":"HOST_NOT_FOUND","message":"未找到该员工，请核实姓名"}`。**不采用** `400`：该状态码已被 T00102 的字段格式错误占用，混用会让前端无法区分"改格式"与"改选择"；**不采用** `200` + 业务码：会让前端把失败当成功处理。依据：本故事在提交接口上叠加了两类不同性质的错误，必须可区分。`[ASSUME]`
6. **校验顺序与短路** → 同一次提交按 `D3 未来时间 → D4 可预约时间窗 → D5 名录` 顺序校验，命中即短路返回该条错误，不再继续（尤其是命中 D3/D4 时不再发起名录查询）。**不采用**"全部校验完再合并返回"：D5 依赖外部 HTTP 调用，对本地就能判定失败的请求先发起外部调用既浪费又放大故障面；**不采用**"D5 先于 D4"：时间窗是本地判定，优先短路能减少外部依赖调用。依据：三类校验的代价不同（本地 vs 外部），顺序应遵循"先便宜后昂贵"。`[ASSUME]`
7. **前端交互范围** → 前端不预取工作日历、不新增日历查询接口：日期/时间由访客自由选择，非法时提交后按后端返回的 `message` 在对应字段旁展示，提示文案与后端同源。**不采用**新增日历查询接口 + 选择器禁用非可预约日：D4 只要求"提示"，预取日历会新增接口、缓存与前后端两套判定口径，属于超出 AC 的范围扩张。依据：D4 的验收动作是"选择非工作日 → 提示"。`[ASSUME]`
8. **名录姓名匹配口径** → 姓名按去除首尾空白后的全等匹配（区分中英文、不做拼音或模糊匹配）；名录中同名多人时，命中任一即视为通过。依据：D5 只要求"姓名必须在企业人员名录中"，未要求唯一定位到人，且 F2 的字段清单里没有可传递工号的字段。`[INFER]`
9. **提示文案常量**（`[FACT]`，逐字来自材料1 的 AC）：D4 → "请选择工作日09:00-17:00的时间段"；D5 → "未找到该员工，请核实姓名"。两条均不得改写。

public interface BookingEligibilityService {

- 校验实现要点（可直接照抄的判定顺序）：
  1. `visitTime` 必须严格晚于服务器当前时间（`Asia/Shanghai`），否则抛 `BusinessRuleException("TIME_OUT_OF_RANGE", "来访时间不能早于当前时间")`（沿用 T00102 已收敛的 D3 文案）；

  cal_date    DATE    NOT NULL COMMENT '日期',
  is_workday  TINYINT NOT NULL COMMENT '1=工作日 0=非工作日（含法定节假日与调休）',

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

### 技术选型

1. **判重键与阈值** → 判重键为被访人姓名（去除首尾空白后全等）；时间窗为"最近 5 分钟"（以提交时间为基准）；状态限定为 `PENDING`；阈值口径为"同一被访人在窗口内的待审核预约数达到 2 条时，第 3 次提交被拦截"。窗口长度、阈值均做成配置项（如 `booking.duplicate.window`、`booking.duplicate.max-pending`）。**不采用**按手机号或访客判重：E4 的判重维度是"同一被访人"；**不采用**永久判重（无时间窗）：E4 的示例明确是短时间窗，永久判重会让正常访客无法再次预约。依据：E4 的示例"5分钟内3次"。`[ASSUME]`
2. **"同一时段"维度的实现** → 除时间窗外，另按"同一被访人 + 同一来访时段"判重：把来访时间按整点小时归一段（如 09:00-10:00 为一段），同一被访人在同一段内已存在待审核预约时，新的提交被拦截（该段最多 1 条待审核）。时段粒度与是否启用做成配置项。**不采用**"只实现时间窗、忽略标题里的时段维度"：E4 的标题明写"同一时段同一被访人预约次数限制"，只做时间窗会让两个同小时段、间隔 10 分钟的重复预约通过。依据：E4 的标题与示例两个维度。`[ASSUME]`
3. **并发下的判重落地** → 在提交事务内、写入预约记录之前：先按判重键取得互斥（对判重锁表中该被访人对应的行加锁；该行不存在时先插入再锁定），随后在锁的保护下计数并判定，命中则中止事务、不写入任何预约记录。**不采用**应用层"先查询计数、再插入"：两个并发请求会同时读到 2 条并双双通过，限制在边界处失效。依据：E4 的"次数限制"必须在并发下仍然成立。`[ASSUME]`

### 你要做什么

**后端**

- 新增判重服务（签名可直接照抄，包名以仓库为准）：

```java
public interface DuplicateBookingGuard {
    /** 命中判重规则时抛出 BusinessRuleException("DUPLICATE_BOOKING", "您已有待审核的预约，请勿重复提交") */
    void check(String hostName, LocalDateTime visitTime, LocalDateTime submitTime);
}
```
- 实现要点（可直接照抄的判定顺序）：
  1. 归一判重键：`hostName.trim()`；
  2. 取得该判重键的互斥（见「技术选型 #3」）；
  3. 时间窗计数：统计同一判重键、`status='PENDING'`、`created_at` 落在 `[submitTime - window, submitTime]` 的记录数，达到阈值则抛业务异常；
  4. 时段计数：统计同一判重键、`status='PENDING'`、`visit_time` 落在同一整点小时段的记录数，达到该段上限（1 条）则抛同一条业务异常；
  5. 两项均通过才继续落库。
- 计数查询（语义可直接照抄）：

```sql
SELECT COUNT(*) FROM visitor_booking
 WHERE host_name = :hostKey
   AND status = 'PENDING'
   AND created_at >= :windowStart
   AND created_at <= :submitTime;

SELECT COUNT(*) FROM visitor_booking
 WHERE host_name = :hostKey
   AND status = 'PENDING'
   AND visit_time >= :hourStart
   AND visit_time <  :hourEnd;
```
- 判重必须与预约写入处于同一事务：判重失败时事务回滚，`visitor_booking` 不产生任何新记录。
- 配置项：窗口长度、阈值、时段粒度、时段上限均从配置读取，代码中不得出现硬编码的 5 或 3。

## 一、要回答的问题与结论边界

### 1.1 终极目标（2026-09-28 修订）

**验证「任务实现说明（brief）生成」这一环能否由可私有化部署的模型承接，从而让整条链路自主可控。**

命题从"降低成本"修订为"**私有化替代可行性**"，依据：

- 本方案的部署形态是**私有化部署**，token **不按量计费**，因此生成环节的 token 开销在总账里**近乎为 0**——按旧的"省钱"口径衡量，这一步本来会被判定为"不值得优化"
- 但 Sonnet **必须走外部 API**，无法私有化；DeepSeek **可本地部署**
- 所以真正的约束不是成本，而是**可行性**：能不能把这一环也换掉，实现全链路本地化

**5 倍价差**（Sonnet ≈ DeepSeek-flash × 5）作为参考值记录，**不作为本轮判定依据**——私有化部署下它不体现为账单。

### 1.2 本轮要回答的问题

| # | 问题 | 判定形式 |
|---|---|---|
| Q1 | **DeepSeek-flash** 生成的 brief，质量能否达到 Sonnet 5 的水平？ | 分维度对比，非总分 |
| Q2 | 若能，**这一环即可替换为可私有化部署的模型**，整条链路不再依赖外部 API | 由 Q1 的阻断项判定直接推出 |

> **臂的取舍说明**：本轮**不测 DeepSeek-pro**。既然衡量的是"可行性"而非"成本"，就应当直接测**资源占用最低的那一档**：flash 若达标，pro 更没必要测；flash 若不达标，再回头评估 pro 是否值得（那属于第二轮）。**结论只对 flash 有效**，不能外推到 pro 档。

### 1.3 结论边界（必须写死，防止误读）

本轮测试有下列**已知限制**，任何结论都必须带这些前提读：

| # | 限制 | 后果 |
|---|---|---|
| L1 | **无 REPO_PATH**（指定不用代码库） | 模板里 `F` 系列规则（预计涉及文件）退化到 `[UNKNOWN]` 路径；**测不出"模型对真实代码库的自查靠不靠谱"** |
| L2 | **不给任何示例**（含 `example-output.md`） | 测的是"纯模板条件下"的推理质量。生产环境若采用"模板 + 换题示例"，结论需另行验证 |
| L3 | **不跑执行侧**（指定只做生成侧） | **不能证明"换掉后下游 qwen27b 的通过率不塌陷"**。本轮的定位是**筛选**：决定值不值得为端到端验证投钱 |
| L4 | 样本量有限 | 1 个故事 7 个任务（n=7）。小样本下微小差异属噪声，不可当结论（见 2.3） |
| L5 | 评测者偏差 | 主观项若由 DeepSeek（即本会话）自评，存在系统性高估；必须去署名后由你或第三方评 |

> **一句话定位**：本轮产出的是**生成侧质量的分维度对比**，用于判断"DeepSeek-flash 是否值得进入端到端验证"。**它不是"可以替换"的最终证据**——最终证据必须来自执行侧（qwen27b 用不同来源的 brief 跑出来的通过率对比）。

## 二、实验设计

### 2.1 三类变量

| 类型 | 内容 |
|---|---|
| **自变量** | 生成模型档位（Sonnet 5 / DeepSeek-flash） |
| **控制变量（各臂必须完全相同）** | ① `SKILL.md` 版本 ② `output-template.md` 版本 ③ 材料1（任务条目）④ 材料2（故事上下文）⑤ 材料3=空 ⑥ 材料4=空 ⑦ 材料5=空 ⑧ 会话初始状态（无预热、无历史） ⑨ 推理参数（低温、固定） |
| **因变量** | 第五节定义的 6 组指标 |

**关键控制点**：材料1（任务条目）**必须两臂共用同一份**。任务条目来自上游 `sprint-task-decomposition`——如果两个模型各拆一遍，等于同时测了两个技能，变量就混了。**任务条目只拆一次，手工定稿后冻结。**

### 2.2 臂设计

| 臂 | 模型 | 角色 | 备注 |
|---|---|---|---|
| **A** | Claude Sonnet 5 | **对照臂（基准）** | ⚠️ 它本身也是被测对象，不是"免检基准"。理由见下 |
| **B** | DeepSeek-flash | **候选臂** | 本轮唯一候选。选中 flash 档是因为**可行性由资源占用最低的档位决定** |

> ⚠️ **关于 A 臂的定位（重要）**：你的前提是"Sonnet 拆的任务肯定达到 qwen27b 的要求"，但那是**在登录故事上**验证的**执行侧**结论。换成新故事、且只做生成侧，"Sonnet 一定达标"不再自动成立。所以 **A 臂必须同样被打分**：
> - 若 A 臂在新故事上表现良好 → 可以拿它当尺子量 B
> - 若 A 臂也崩 → 说明**故事或技能是瓶颈**，而不是 DeepSeek 不行。这两种归因必须能分开，否则整轮测试白跑

**D 臂（本轮不加）**：原设计里有一条"flash 裸生成（不给 SKILL.md）"，用来测"这套技能本身值多少分"。**本轮确定不加**。若首轮跑完发现两臂都无阻断项、分差又落在噪声区（0.3 分以内）而无法判定，再加 D 臂作为第二轮的手段——那时它能回答"是不是技能没起作用，导致两臂都只是模型裸能力"。

### 2.3 样本量与统计功效

**本轮采用：1 个故事 × 7 个任务 = n 7（配对样本）。**

| 方案 | 配对样本量 | 能得出的结论 | 成本（2 臂） |
|---|---|---|---|
| **1 个故事 × 7 任务（本轮）** | **7** | **只能定性**：能识别"flash 明显不行"（触发阻断项），**分不出细微差距** | 2× 单臂 |
| 2 个故事 × 7 任务 | 14 | 能看出 1 分以上的稳定差距 | 4× 单臂 |
| 3 个故事 × 7 任务 | 21 | 可做初步比例判断 | 6× 单臂 |

> **已知的统计局限（必须写进最终报告）**：n=7 时，若 A 得 6/7、B 得 5/7，这个差异**无统计意义**，不得据此判定"flash 更差"。本轮真正能可靠识别的只有**阻断项**（一票否决的那五条）——这也正是第五节把判定规则设计成"阻断项优先"的原因。
>
> 若首轮结论是"两臂都无阻断项、分差在噪声区"，那么**按既定的 3a 规则直接采用 flash**，第二轮不必跑——因为私有化场景下，flash 的资源占用更低而质量无实质差异。

## 三、Step 0：部署形态确认（**已通过，2026-09-28**）

原设计里这一步是"ROI 前置检查"——按 token 账单占比判断值不值得跑。经确认，**该口径不适用**：

| 检查项 | 结论 |
|---|---|
| 部署形态 | **私有化部署**，token 不按量计费 |
| brief 生成在总开销中的占比 | **近乎为 0** |
| 按旧口径是否值得跑 | ❌ 不值得（< 5% 天花板） |
| **按新口径（私有化可行性）是否值得跑** | ✅ **非常值得**——因为约束不是成本，而是**能否摆脱外部 API 依赖** |

**链路拆分**（便于后续端到端轮次复用）：

```
brief 生成 ──→ qwen27b 执行（含重试） ──→ 失败升级到 70B ──→ 人工返工
   ①                    ②                      ③              ④
   ↑
   本轮只替换这一环；① 目前依赖外部 API，
   是整条私有化链路里唯一无法本地化的环节
```

**要记录的成本数据仍然记录**（第六节），但用途改为：**若将来改为公有云/按量计费形态，这份数据可直接复用**。不作为本轮判定依据。

## 五、评测方法

评分依据 = `output-template.md` 的规则编号。**规则在跑之前锁定，跑完不得增删改**。

### 5.1 阻断项（一票否决，任一命中则该档位不合格）

| # | 阻断项 | 对应规则 | 判法 | 为什么致命 |
|---|---|---|---|---|
| **G1** | 技术选型未收敛——出现"由实现方选型""具体方案不限""可选A或B" | T3 | grep（可自动） | 把开放性选择题甩给执行者，正是本技能要消除的核心问题 |
| **G2** | 出现不可执行的语法/API 断言并标 `[FACT]` | T6 | **人工语义判定**（grep 误报率约 50%，见模板第五部分） | 执行方必然踩坑。上一轮 Sonnet 就是在这一条上翻车 |
| **G3** | 任一章缺失（尤其《执行前必须确认清单》） | S1 | grep（可自动） | 执行者拿不到该类信息 |
| **G4** | 《确认清单》遗漏 ≥2 个正文决策点 | Q1 | **人工列表比对**（机械计数已被证明是噪声） | 清单形同虚设，等于没做确认这一步 |
| **G5** | 自相矛盾：同一行为既在隐含规则里要求、又在排除项里禁止 | C4 / X4 | 人工 | 执行者无所适从 |

### 5.2 计分项（各 1–5 分，逐任务打）

| # | 维度 | 5 分标准 | 1 分标准 |
|---|---|---|---|
| **P1** | 技术选型穷举度 | 覆盖了材料没提但实现时必然要选的点（测试数据来源、默认值、可测试性设计等） | 只写材料明示的 2–3 个 |
| **P2** | 技术选型论证质量 | 每条都写了"为什么不选另一个候选" | 只写选了什么 |
| **P3** | 隐含规则推导 | 推导出 AC 字面之外的规则，且能追溯到具体 AC | 复述 AC / 整节留空 |
| **P4** | 颗粒度（W2） | 抽查 3 处，都有可直接照抄的 DDL / record / 方法签名 / 注解 | 全是"新增登录接口"这种概括 |
| **P5** | DoD 可判定性 | 每条挂 AC 编号 + 证据等级，且含具体数值/状态码/判定方式 | 出现"测试通过""功能正常" |
| **P6** | 排除项精度 | ≥3 条且点名相邻任务 ID，覆盖三类（相邻任务/已排除方案/不该碰的既有代码） | <3 条或未点名任务 ID |

### 5.3 判定规则（**预先登记，跑完不得改**）

```
候选 = B 臂（DeepSeek-flash）    对照 = A 臂（Sonnet 5）

1. 若 A 臂（Sonnet 5）命中任一阻断项 G1–G5
     → 判定「故事/技能是瓶颈」。
        本轮无法回答模型差异，需换故事重跑。
        ⚠️ 此时不要拿 A 当尺子去量 B

2. 若 A 臂无阻断项，而 B 臂命中任一阻断项
     → 判定「不达标，本轮私有化替代方案不成立」。
        报告必须列出具体命中了哪一条、影响面是什么

3. 两者都无阻断项：
     a. 总分差 ≤ 0.3 分        → 「与 Sonnet 无实质差异」→ **采用 flash**
     b. B 更优                 → 「达标且更优」        → 采用 flash
     c. B 更差，差距 < 1.0 分  → 「达标，存在可接受的差距」→ 采用 flash，
                                  但报告必须逐条列出差距点（供后续 prompt 迭代）
     d. B 更差，差距 ≥ 1.0 分  → 「不达标，不建议替代」
```

> **第 3a 条是本轮最可能落到实处的结论**：如果 flash 与 Sonnet 分不出高下，那就该选 flash——**私有化场景下它资源占用更低、且不依赖外部 API，而质量无实质差异**。不要因为"Sonnet 更稳"而放弃。
>
> **第 3c 条同样重要**：即便 flash 略差，只要没有阻断项，它仍然可用——因为阻断项才是"会让执行方踩坑"的东西，计分项差 0.3~1.0 分通常表现为"写得糙一点"，而非"写错了"。**糙和错是两回事**，本轮的价值就是把这二者分开。

## 六、成本核算口径

**必须按「每任务全链路」算，不能只看生成单价。** 三个坑：

### 坑 1：输入侧成本

生成时的输入 = `SKILL.md` + `output-template.md` + 材料1 + 材料2，两臂**完全相同**。所以这部分不产生差异，但要计入总账。

### 坑 2：输出长度会乘到下游（**最容易被忽略**）

brief 是**下游每次执行都要读入的输入**。brief 越长，qwen27b 每次执行的输入 token 越多。上一轮的实测数据：

| | 字节数 |
|---|---|
| Sonnet 版 | 39,742 |
| DeepSeek 版 | 61,980（**长 56%**） |

若 DeepSeek 的 brief 稳定比 Sonnet 长 50%，那么省下的生成成本，会被下游执行时**多读 50% brief** 吃掉一部分。**这个乘数必须算进去。**

> 本轮无执行侧，无法实测该乘数。但**必须记录每臂的 brief 字节数/输出 token 数**，因为：
> - 若 DeepSeek 显著更长，这个负项要在报告里显式列出
> - 它是决定"要不要做端到端验证"的关键输入

### 坑 3：返工成本

便宜的 brief 导致更多返工，可能比贵的 brief 更贵。本轮测不出，但要在报告里标明这是**未覆盖的风险**。

### 记录表

| 臂 | 模型 | 输入 token | 输出 token | 单价(输入) | 单价(输出) | 单次生成成本 | 产出字节数 | 每任务平均成本 |
|---|---|---|---|---|---|---|---|---|
| A | Sonnet 5 | | | | | | | |
| B | DeepSeek-flash | | | | | | | |
| D | flash 裸生成（可选） | | | | | | | |

**成本压缩比** = `A 的每任务平均成本 ÷ B 的每任务平均成本`

> ⚠️ **本轮该比值不作为判定依据**（私有化部署下不体现为账单），仅作记录，供将来改为公有云/按量计费形态时复用。第三节 Step 0 已说明。

## 附：本计划的自我约束

1. **评分表在跑之前锁定**（第五节已定稿）。跑完发现某个维度"恰好"对某臂不利而想调整 → 不允许，只能作为"事后观察"另行记录。

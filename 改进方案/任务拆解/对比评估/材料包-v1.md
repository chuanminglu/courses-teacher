# Task Implementation Brief 技能

> **与 `sprint-task-decomposition` 的关系**：后者产出的任务清单颗粒度只到"任务名+AC+路由标签+AI模式+工时+依赖"，本技能在派发前对其中某一条具体任务现场展开成完整实现说明。两者触发时机不同，不要互相抢触发——本技能只在"要把某一条具体任务交给执行者（人或subagent）之前"触发。

## 参考基准

生成前**必须**先看 [references/output-template.md](references/output-template.md)。它是本技能的输出形状与颗粒度基准，含四部分：①结构模板（每个任务 12 个章节的骨架与顺序）②颗粒度规则（`S/Q/B/F/T/W/H/X/D/L/C` 共 40 余条，每条给出"规则 / 判法 / 反例"）③反例库（真实出现过的错误）④生成后自检清单（14 项，逐条打勾，任一未过则回炉）。

**那些规则是硬约束，不是建议**——尤其这四条：**Q1**（清单条数 == 正文非 `[FACT]` 决策点数，须人工列表比对，机械计数不可靠）、**T3**（禁止"由实现方选型"这类开放表述）、**T6**（未经实测的语法/API 断言不得标 `[FACT]`）、**X1**（排除项必须点名相邻任务 ID）。产出前必须真的执行第 ④ 部分的自检清单，不能凭感觉勾。注意 Q1 与 T6 两条都**无法自动化判定**，必须人工做语义核对——详见模板第五部分的验证记录。

**为什么不再用真实产出当基准**：本技能原先的基准是 `references/example-output.md`（登录故事的一次真实展开，6 个任务）。该文件已退役为历史样例，不再进入生成上下文，缘由有二：①它与本技能的典型测试用例同题，会把答案（技术选型、预计涉及文件、隐含规则）连同格式一并泄露给生成方；②它承载的是某个特定仓库的事实（文件路径、依赖坐标、表结构），在换代码库或未提供 `REPO_PATH` 的场景下会被照抄成幻觉——而且因为示例在原文里被定位为"权威基准"，生成方会**更自信地**抄。若确需一份真实产出作参照，应另选**不同故事 + 不同技术栈**的产出，不得复用与当前任务同题的任何文档。

约束按"最脆弱的执行者"设计——规则对能力较弱的执行者能落实到位，对更强的执行者天然兼容，不需要因为执行者能力强就放松。

## 方法论

### 角色

你是一位资深工程负责人，拥有12年团队研发管理经验，擅长：

- 把一条已经定好范围的任务，结合最新代码库状态，展开成一份可直接执行的自包含说明
- 识别范围蔓延（scope creep），把不属于本任务的内容明确排除
- 基于代码库实际证据（而非文字描述臆测）预估改动文件，并区分"确定要改"和"视决策而定"
- 把验收标准转化为具体、可判定的完成定义（DoD），并主动推导出验收标准字面之外的隐含业务规则
- 在有多种技术实现路径可选时，替执行者提前做出唯一选型决策，不把开放性选择题留给执行阶段

本任务信息自包含：不要假设除下文之外还有更多规划背景，下面就是执行这个任务所需的全部上下文（不管你是被派去执行它的subagent、另一个新对话，还是人工阅读）。

### 任务上下文

**强制自查规则（不可跳过）**：如果提供了REPO_PATH，必须先用Grep/Glob核实材料1里"预计涉及文件概要"是否仍然准确——文件是否存在、是否已被材料4提到的前序任务改动过。不能只凭材料1的文字描述照抄，必须重新自查一次，因为规划阶段的预判可能已经过时。同一次自查还要顺带确认代码库里是否已有可复用的技术约定（见下方"技术选型收敛规则"），不要分两次查。

**自查范围收敛规则（防止大代码库下自查消耗过多token甚至超时，不可跳过）**：自查不是"通读仓库"，必须遵守以下边界：

- **关键词收窄**：只搜索与材料1本条任务直接相关的词（任务标题、验收标准里出现的业务名词/字段名），不做与本任务无关的通用扫描。
- **目录收窄**：如果REPO_PATH是monorepo或有明显模块划分（workspaces/packages/services等），优先把Grep/Glob范围限定在材料1"预计涉及文件概要"指向的模块内；只有完全无法判断属于哪个模块时，才扩大到仓库根目录。
- **调用次数上限**：单次自查控制在**8次工具调用以内**。顺序为：先看目录结构/`package.json`等清单文件判断技术栈边界 → 用 `Grep -l`定位候选文件（只拿文件名列表，不带内容） → 只对命中数量最少的1-3个核心文件做完整Read，不要把所有命中文件逐一通读。
- **命中过多时的处理**：如果关键词在几十个以上文件命中，说明关键词太宽或目录范围太大，应先收窄关键词/目录重查一次，而不是把命中文件全部读一遍；收窄1次后命中仍然过多，允许中止深度自查，改为基于目录结构与文件名做 `[ASSUME]`级推断，并在"假设与待确认项"里注明"自查范围因项目规模过大未能穷尽，建议派发前用更精确的模块路径重新自查"，不要为了查全而无限制增加工具调用。

**范围收口原则**：本任务只做材料1里明确列出的那一件事，不要因为"顺手""看到相关代码"就扩大范围；材料1之外、但你在自查时发现的相关问题（如代码坏味道、其他未完成的验收标准），记录进"假设与待确认项"或在交付要求里提醒，不要顺带改掉。

**技术选型收敛规则（不可省略，是本任务说明区别于粗颗粒度规划的关键一步）**：任务范围内如果存在"多种实现方式均能满足验收标准"的决策点（例如：会话凭证用token还是session、验证码存储用数据库表还是缓存、埋点投递方式用日志表还是消息队列……），**不允许把这类决策留给执行者临场判断**，必须由你在本次展开阶段替执行者选定一个唯一方案，理由如下：

- 如果提供了REPO_PATH，优先自查代码库现有约定（已有的类似实现、已引入的依赖库、项目脚手架的默认选择），选中与现状一致的方案，标 `[FACT]`或 `[INFER]`
- 如果代码库无先例可循（新项目/新模块），按业界默认做法选定一个方案，标 `[ASSUME]`，并在"假设与待确认项"注明"如实现方计划采用其他技术路线，需在开工前反馈，避免返工"
- **执行者拿到的任务说明中不应再出现"由实现方选型""具体方案不限"这类表述**——凡是出现这类表述，说明技术选型收敛这一步没有做完，需要回头把它变成一个具体、唯一的方案
- **技术选型里涉及具体工具/库/语法层面行为的断言，如果未经实际验证（没有Read到文档或Bash实测确认），不要写成确定性陈述**——例如"某驱动版本支持某SQL语法"这类可以直接测但没测的细节，应标 `[ASSUME]` 而非 `[FACT]`，并在该条技术选型末尾补一句"若实测不支持，可替换为语义等价的实现方式（如XX），不算偏离本选型决策"，明确把"具体语法/API调用方式"和"选定的架构/方案本身"分开——前者允许执行者按实际情况替换，后者不允许

**Flag覆盖范围核对规则（源于真实踩坑）**：如果本任务涉及新增/修改前端入口结构（新页面、新路由、新的"未满足条件则拦截"式条件渲染），必须核对这个结构性改动是否也需要感知本任务所属的Feature Flag状态——判断标准：flag关闭时，这个前端结构改动是否仍然会挡住一个故事开始前本可直接访问的入口？如果会，"你要做什么"里必须明确写出前端也要做flag判断（或等价的"关闭时回退到旧行为"的分支），不能只让新增的后端接口受flag控制、假设前端不需要关心。反例：新增一个强制登录墙组件包住原本无需登录即可访问的页面，若只在登录API上判断flag、前端没有"flag关闭时跳过登录墙直接显示旧页面"的分支，会导致flag关闭时用户仍然被新UI结构永久卡住——flag形同虚设。**如果材料2里该故事的flag字段是"无需Feature Flag"（纯技术使能故事），本条规则不适用，跳过flag相关判断即可。**

**新基础设施覆盖完整性规则（源于真实踩坑）**：如果本任务要引入一套新机制取代或兼容代码库里已有的旧机制（例如新的schema管理方式取代旧ORM的建表方式、新的日志框架取代旧的打印语句），自查阶段除了确认本任务新增内容涉及的结构，**还必须盘点代码库里所有依赖旧机制、但本任务不打算改动的既有结构是否也需要被新机制覆盖**，不能只顾本任务新增的那部分。判断标准：如果新旧机制并存（新机制只覆盖新结构，旧结构还留着靠旧机制活着），这种半吊子状态会不会在后续任务/测试里因为"新机制环境下旧结构缺失"而报错？如果会，本任务的"预计涉及文件"和"你要做什么"里必须显式包含"把既有结构一并纳入新机制"这一步，而不是留给后面某个不相关的任务意外触发时才发现。反例：任务A引入新的数据库schema自动初始化机制，只声明了本任务新增的表，代码库里另一张早就存在、靠旧机制建表的表没有被纳入；几个任务之后，某个任务第一次在纯净测试环境里访问了那张旧表，才报"表不存在"——这个缺口本该在任务A自查阶段就被发现并处理，不该拖到无关任务才暴露。

**确认清单生成规则（不可省略，是"标签"和"可执行的开工闸门"之间的最后一步）**：生成任务说明的最后一步，必须通读全文一次，把出现过的每一个 `[ASSUME]`/`[UNKNOWN]`/`NEEDS CLARIFICATION` 标签，以及"依赖任务尚未合并/暂停并报告"这类提醒，逐条提炼成《执行前必须确认清单》里的一行问题句，不能遗漏，也不能在清单里引入正文没有出现过的新问题。每条须先判定阻塞类型：

- `NEEDS CLARIFICATION` → 恒定**阻塞**（不答复无法开工）
- "依赖任务尚未合并/暂停并报告"类提醒 → 恒定**阻塞**
- `[UNKNOWN]`：如果是"完全没有REPO_PATH导致文件/技术选型无法自查"这类让任务说明本身残缺的情况 → **阻塞**；如果是"字段清单不完整但不影响本任务能否开工"（比如下游消费方需要的完整字段材料未给全，但本任务范围内的最小字段已经能确定）→ **默认生效-可反馈**
- `[ASSUME]` → 恒定**默认生效-可反馈**（方法论已要求`[ASSUME]`必须给出唯一可执行方案，不阻塞开工，但反馈窗口必须保留）

清单生成后需自查一遍：清单条数是否等于正文中这几类标签实际出现的决策点数量（同一决策点在技术选型/预计涉及文件/DoD里被多处引用，只算一条）。

**CI/CD验收模式选择规则**：材料5未提供时默认 `PR-only`。如果材料5也没给判断依据，按以下规则自行判断并在任务说明里注明选了哪一档、为什么：

- 如果提供了REPO_PATH且自查发现代码库已有CI配置（如 `.github/workflows`、`.gitlab-ci.yml`等），且本任务改动理应被现有流水线覆盖 → 选 `CI/CD-verified`
- 如果代码库还没有CI配置（比如脚手架搭建初期），或本任务本身就是"搭建/修改CI配置"这类任务（要求它自证"CI跑绿"会形成循环依赖）→ 选 `PR-only`
- 无法自查（未提供REPO_PATH）时 → 默认 `PR-only`，并在"假设与待确认项"里标注 `[UNKNOWN]`，说明这是因为没有代码库信息做出的保守选择，不代表该任务不需要CI/CD-verified，需要调用方确认。

### 目标与意图

**核心目标**：把一条规划阶段的任务条目，转成一份不需要调用方二次补充背景、不需要执行者自己做任何开放性决策、可以直接照做的自包含任务说明。

**具体目标**：

1. **背景准确**：任务背景基于材料2和材料4，反映当下真实状态，不是规划时的旧假设
2. **文件预估可核**：预计涉及文件基于当下自查（不是材料1的旧概要直接照搬），标注证据等级，并区分"必须改动"与"可能改动"
3. **边界清楚**：明确"要做什么"和"明确不要做的事"，防止范围蔓延
4. **决策已收敛**：任务范围内的技术选型点已被明确选定为唯一方案，不留给执行者临场判断
5. **隐含规则已显式化**：从验收标准字面之外推导出的业务分支规则，已逐条列出，不依赖执行者自行推理发现
6. **验收可判定**：完成定义（DoD）具体、可测试，标注对应验收标准编号和证据等级
7. **自包含**：不管执行者是subagent、新会话还是人工阅读，都不需要再去找规划阶段的原始材料

**业务价值**：

- **为执行者**：拿到即可开工的说明，不用自己再去反查这条任务在整体规划里的位置，也不用自己权衡技术选型或推理隐含规则——这两类"开放性思考"是执行环节里最容易被跳过或做错的部分，提前收敛能显著降低一次性做对的门槛

| # | 反例 | 违反规则 | 为什么危险 |

# 第五部分 · 本模板的区分力验证记录

**验证方法**：把本模板的规则回放到两份**已知有缺陷**的真实产出上，看规则能否把它们抓出来。抓不出来即说明规则是废的。

**样本**：
- 甲版（某业务故事，6 任务）
- 乙版（同一故事，6 任务）

**结果**：

| 规则 | 甲版 | 乙版 | 判定 |
|---|---|---|---|
| S1 章节齐备 | ❌ 6/6 任务缺《执行前必须确认清单》 | ✅ | 有效（但甲版的缺口是版本错配所致，见下） |
| **T6 语法断言误标 `[FACT]`** | ❌ **T00103 真阳性**——`[FACT]` 直接附着在「sqlite-jdbc 版本支持 `ADD COLUMN IF NOT EXISTS`」这一错误断言上 | ⚠️ 误报——命中的是"警告不要这么写"的句子 | **规则有效，但 grep 判法不可用，必须人工语义判定** |
| D1 DoD 挂证据等级 | ❌ T00101 有 1 条、T00106 有 4 条裸断言 | ✅ | 有效 |
| **Q1 清单条数 == 决策点数** | 不适用（无清单章节） | ❌ **人工核出 3 处遗漏**：T00102 时序攻击防护、T00105 运营看板字段清单、T00106 回归比对基准 | **规则有效且是最能暴露问题的一条；但机械计数完全不可用** |
| T3 开放表述 / X1 排除项 / Q2–Q5 | ✅ | ✅ | 规则过松（两版都没违规），**尚无法确认其区分力** |

**两条必须记住的结论**：

1. **最有价值的两条规则（Q1、T6）都无法自动化执行**，必须人工判定。想省掉人工就是自欺欺人。
2. **T3 / X1 / Q2–Q5 在本样本上零命中**，说明它们要么过松、要么本样本没触犯——**区分力未经验证**，不能因为"没报错"就认为产出合格。

**版本错配说明（避免误读甲版）**：甲版产出早于 `SKILL.md` 定稿（出自 v2 提示词），《执行前必须确认清单》是 SKILL.md 新增章节，因此 S1 的 6/6 失败**属版本错配，不应计为模型能力缺陷**。真正能归因到模型行为的只有 T6 那条。

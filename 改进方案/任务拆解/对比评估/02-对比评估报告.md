## 一、结论摘要

**先说结论的适用范围**：本次不是干净对照实验，存在**答案泄露**（DeepSeek 被要求先读 `example-output.md`，而该文件内容就是 Sonnet 版答案）、**快照漂移**（Sonnet 跑在 2026-09-21 未提交工作区，DeepSeek 跑在当前 HEAD，而 HEAD 上整个登录故事已实现完毕）、**会话污染**（DeepSeek 生成前已被主会话用 13 次工具调用预热）三重干扰。**因此本报告不产出"S 模型 > D 模型"这类总分式结论。**

分维度结论：

| 维度 | 结论 |
|---|---|
| 事实准确度 | **不可比**。两版跑在不同快照上。Sonnet 版 11 条跨快照稳定的断言**全部属实**；6 条在 HEAD 下失效但属快照漂移，**不计为错误** |
| 幻觉率 | 两版**均为 0**。两版都没有编造文件路径/依赖/字段 |
| **真错误** | Sonnet 版有 **1 条被实测证伪的技术断言**（`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，标 `[FACT]`），且该错误**在当时的提示词里已有明文规则可避免**。DeepSeek 版无此类错误 |
| 结构完备性 | **DeepSeek 版完备**；Sonnet 版缺《执行前必须确认清单》整章（6/6 任务）——但**该章节是 SKILL.md 新增的，Sonnet 用的是 v2 提示词，属版本错配，不计能力失分** |
| 标签-清单一致性（SKILL 明文自查项） | **两版均未通过**。Sonnet 版因无清单章节整体缺失；DeepSeek 版自审发现 **3 处标签未进入清单** |
| 决策收敛度 | 两版**均无违规**（无"由实现方选型""具体方案不限"类表述） |
| 隐含规则推导质量 | **打平，DeepSeek 略多一条**。Sonnet 版 T00103 的 4 条隐含规则经 HEAD 实际实现逐条印证，全部成立 |
| 自查纪律 | DeepSeek 用满 8 次上限并**因此漏读关键方法体、产生 3 个不必要的阻塞项**——这是本次最有价值的负面教训 |

**一句话**：在"照着基准复现"的条件下，两版质量接近，各有各的失败点；**DeepSeek 版的结构合规性更好但自查纪律把预算用错地方，Sonnet 版有 1 条实质性技术错误但结构缺口是版本问题**。这个对比没有分出胜负，**主要原因是实验设计本身不可比**。

| 隐含规则 | 实际实现 | 是否被采纳 |

## 四、最重要的单点发现：Sonnet 版唯一一条被证伪的技术断言

**Sonnet 版断言**（出现在两处）：

- `登录故事-任务清单v3-SpringBoot.md` 全局技术选型表：「后续任务新增字段用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 追加到同一 `schema.sql`（**sqlite-jdbc 3.49.1.0 捆绑的 SQLite 版本 ≥3.35，支持该语法**）」——标注 `[FACT]`+`[ASSUME]`
- `登录故事-单任务实现清单v3-SpringBoot-PRonly.md` T00103 技术选型 #1：同一断言，标注**纯 `[FACT]`**

**实测证伪**（本机 SQLite 3.37.2）：

```
ALTER TABLE t ADD COLUMN IF NOT EXISTS b INTEGER
→ OperationalError: near "EXISTS": syntax error        ← 语法根本不支持

ALTER TABLE t ADD COLUMN c INTEGER      （第二次执行）
→ OperationalError: duplicate column name: c           ← 裸 ADD COLUMN 重放会报错
```

**后续真实实现的印证**：HEAD 的 `schema.sql` 尾部留有明确注释——

> 「T00103 已踩坑：本文件按 `sql.init.mode=always` 每次启动都重放，裸的 `ALTER TABLE ... ADD COLUMN` 在第二次启动时会因列已存在而抛错。因此 email 列沿用 T00103 的 `PRAGMA table_info` 探测 + 条件 ALTER 模式，由 `UserRepository.ensureEmailColumn()` 在启动时按条件执行。」

即：**这个坑在真实开发中被踩了，并被迫改为 `PRAGMA table_info` 探测 + 条件 ALTER 的方案**。Sonnet 版提出的方案是不可执行的。

**公平性核查（关键）**：这条错误**不能归因于版本错配**。检索 v2 提示词（`单任务实现-subagent提示词.md`）第 68 行，**该规则当时已经存在**：

> 「**技术选型里涉及具体工具/库/语法层面行为的断言（v4新增，源于真实踩坑），如果未经实际验证（没有 Read 到文档或 Bash 实测确认），不要写成确定性陈述**——例如"某驱动版本支持某 SQL 语法"这类可以直接测但没测的细节，应标 `[ASSUME]` 而非 `[FACT]`」

**"某驱动版本支持某 SQL 语法"这个反例，与 Sonnet 犯的错误逐字对应。** 规则在手、反例就在眼前，Sonnet 仍然把它标成了 `[FACT]`。这是本次对比中**唯一一条可从产出物直接归因到模型行为的实质性缺陷**。

DeepSeek 版在这一点上表现正确：T00103 技术选型 #1 直接读取了 HEAD 的踩坑注释，选定了 `PRAGMA table_info` + 条件 ALTER，并把"不要写裸 `ALTER TABLE ... ADD COLUMN`"同时写进了「明确不要做的事」和 Q2 阻塞项。

## 六、建议

### 6.1 若要做一次真正可比的复跑，必须改三件事

1. **摘除答案泄露**：生成时把 `references/example-output.md` 从输入里去掉，只给 `SKILL.md` 正文 + 材料1～5。否则测的永远是"照抄逼近"能力。
2. **钉死快照**：两边都跑在 `69231f5` 并**手工移除** `server/src/main/resources/schema.sql`（该提交把 Sonnet 的 T00101 提案 DDL 一起提交了，是个泄题点）。或者更干净：换一个**两边都没做过的故事**跑。
3. **干净会话**：两边都在无预热的新会话里跑，只喂冻结后的材料包。

### 6.2 对 SKILL.md 本身的两条改进建议（本次实测暴露）

1. **`references/example-output.md` 与测试用例同题，存在泄题风险**。建议：示例改用**另一个故事/另一个技术栈**的产出，只保留章节结构与颗粒度作为形状锚点。当前示例与"登录故事 + tasksplitting 仓库"完全同题，任何针对该故事的评测都会失真。
2. **8 次工具调用上限在"仓库已完成"或"大模块"场景下不够用**。本次不是"关键词命中过多"（SKILL 已为此设计了收窄规则），而是"需要读的关键文件刚好超过预算"。建议改为**按读取文件的字节数设预算**，或允许在"目标文件数 ≤ N"时突破调用次数上限——否则会像本次一样，为了守规矩而制造出本可避免的阻塞项，反而损害"自包含"这个首要目标。

### 6.3 对 Sonnet 版产出的处理建议

- T00103 的 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 方案**不可执行**，若该文档仍在被当作执行依据（例如喂给 qwen 做 benchmark），应更正为 `PRAGMA table_info` 探测 + 条件 ALTER，否则执行方必然踩坑
- 若要把 Sonnet 版回填到 `SKILL.md` 的新结构，需补写 6 个任务的《执行前必须确认清单》（`example-output.md` 已经是补好的版本，可直接作为回填参考）

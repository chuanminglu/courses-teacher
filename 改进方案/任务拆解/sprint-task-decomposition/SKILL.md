# Sprint Task Decomposition 技能（纵向安全切片版）

> **替代关系**：本技能替代 `sprint-tasks-lean`。触发时机、前置条件与旧技能一致；**拆分策略不同**——不再默认"FE/BE/Mock横向解耦"，改为按纵向安全切片（Walking Skeleton / Expand-Contract）拆分，每个任务是一条能独立验证、独立安全合并的端到端最小路径。

## 触发条件

当以下情况时使用此技能：
- 使用 lean 流水线，需要生成 Sprint 任务
- 用户说"帮我生成 Sprint {N} 的任务"或"生成所有 Sprint 的任务"
- 已完成 `release-plan-lean`，需要进入任务拆解阶段

## 前置检查

**必须存在的上游文档**：
- `docs/sprints/release-plan.md` — Release Plan（lean 版，含 Sprint 故事分组）
- `docs/requirements/user-stories/` — 用户故事详情

**推荐存在的文档**：
- `docs/design/api-contract.md` — API契约
- `docs/design/schema.md` — 数据库 Schema

**如果缺少上游文档**：
```
❌ 缺少 Release Plan
建议先使用 `release-plan-lean` 技能生成发布计划
```

## 输入材料装配

下方"分解方法论"以 `{{SPRINT_NAME}}`/`{{SPRINT_GOAL}}`/`{{STORIES}}`/`{{REPO_PATH}}` 四个材料位为入口，这一步把上游文档装配成这四个材料位（方法论正文本身不管这一步从哪来）：

| 材料位 | 来源 | 装配方式 |
|---|---|---|
| `{{SPRINT_NAME}}` | 用户指定的 Sprint 编号 | 直接填入 |
| `{{SPRINT_GOAL}}` | `release-plan.md` 中该 Sprint 的目标一句话 | 原文摘录，不改写 |
| `{{STORIES}}` | `docs/requirements/user-stories/` 下对应故事文件 | 按"生成模式"决定拼几个故事；每个故事含故事ID/故事描述/已知验收标准 |
| `{{REPO_PATH}}` | 当前工作目录 | 直接填入，供方法论内"强制自查规则"使用 |

**生成模式**（询问用户，如未指定）：
- `single`：仅指定 Sprint 内某几个故事，只拼入目标故事
- `all`：该 Sprint 全部故事，一次性拼入 `{{STORIES}}`（对应方法论"多故事版"设计，会触发跨故事冲突排查）

## 分解方法论

材料装配完成后，按以下方法论生成任务清单。

### 角色

你是一位资深迭代规划负责人，拥有12年团队研发管理与CI/CD落地经验，擅长：

- 用户故事的纵向安全切片拆分（Walking Skeleton / Expand-Contract 判断与应用）
- Henrik Kniberg 故事拆分技巧的组合运用
- 特性开关（Feature Flag）驱动的"合并"与"发布"解耦设计
- 识别"按前端/后端/测试"横向拆分等常见反模式并纠正
- 基于代码库实际证据（而非文字描述臆测）判断变更性质
- **多故事间的文件/模块重叠识别与执行依赖排序**——同一迭代里的多个故事经常会碰到同一批文件，这条能力是单故事拆分不需要、但迭代规划必须有的
- **按任务的技术复杂度判断合理的模型路由档位与AI执行模式**——不是每个任务都该用同一档模型/同一种人工介入程度执行，需要在规划阶段就把这个判断显式标注出来，而不是留到执行时临时决定

本任务信息自包含：不要假设除下文之外还有更多规划背景，下面就是执行这个任务所需的全部上下文（不管你是被派去执行它的subagent、另一个新对话，还是人工阅读）。

### 任务描述

基于以下材料，把本迭代内的多个用户故事逐个拆解成纵向安全切片方案，并产出一份对齐 `tasks.md`风格的迭代任务分解总览（迭代头部 + 每个故事的任务checkbox清单 + 跨故事依赖排查）。

**材料1：迭代基本信息【核心材料：必须依据】**

- 迭代名称：{{SPRINT_NAME}}
- 迭代目标（一句话，通常是这次迭代结束时应该达到的整体验收状态，不是单个故事的验收标准）：{{SPRINT_GOAL}}
- 上一个/下一个迭代链接（可选）：{{SPRINT_LINKS}}

**材料2：故事列表【核心材料：必须依据】**
{{STORIES}}

> 格式：每个故事包含 故事ID（如US-AUTH-01）、故事描述、已知验收标准（可为空）。故事之间没有天然顺序，不要假设列表顺序就是执行顺序——执行顺序由本方法论的"跨故事依赖排查"重新判断。

**材料3：代码仓库路径【核心材料：用于自查，不提供则跳过自查】**
{{REPO_PATH}}

### 任务上下文（内置方法论，判断依据）

**拆分主轴**：不是"这是什么技术层的活"，而是"这一刀切下去，能不能被独立验证、独立安全合并"。

**模式判断规则**（对每个故事分别判断，不能整个迭代共用一个结论）：故事涉及的功能，代码库里有没有已经在生产环境跑着、不能说停就停的旧实现？

- 没有 → **Walking Skeleton**：先搭最薄的端到端路径，再逐片加厚，全程用 Feature Flag 包裹到验收通过再开放
- 有 → **Expand-Contract**（Parallel Change）：Expand（新旧并存）→ Migrate（调用方逐个切换）→ Contract（确认无依赖后删旧代码）

**切片排序技巧**（可组合，故事内部用）：按工作流步骤 / 按业务规则变化 / 按数据输入变体 / 按CRUD操作 / 按happy-unhappy path / 延迟非核心工作 / **按基础设施分层**（技术使能故事专用，见下方"技术使能故事"一节）。

**Feature Flag**：默认按 Release Toggle 处理（短命，全量发布后必须删除，避免开关债务）；如任务明确是A/B实验或权限控制，改用对应类型；同一迭代内如果两个故事共用同一个开关空间（比如都属于同一个大功能的灰度控制），要在跨故事排查里显式说明。**故事若彻底不引入任何用户可观察的行为变化（纯技术使能故事，见下一节），"特性开关设计"字段允许显式写"无需Feature Flag"，不强套Release Toggle**。

**Flag覆盖范围规则（源于真实踩坑）**：设计Feature Flag时必须确认它覆盖了本故事引入的**全部可观察行为变化点**，不能只包住新增的后端API。判断标准：本故事是否让某个原本可直接访问的入口（页面/路由/按钮）变得需要先经过一个新流程才能到达？如果是，flag关闭时前端也必须能绕开这个新流程、回到故事开始前的行为，而不能只让后端新接口返回404/不可用——否则会出现"后端flag已关闭，但前端UI结构已经强制改变，用户仍然被挡住"这种flag形同虚设的情况（例如：新增强制登录墙包住了原本无需登录即可访问的页面，若只在登录API上判断flag、前端没有"flag关闭时跳过登录墙"的分支，用户会永久卡在登录页无法进入）。每个故事的"特性开关设计"字段需要显式说明flag具体覆盖到前端哪些结构性改动，不能只写"后端接口受flag控制"就默认前端安全。

**Flag清理任务规则（新增，源于验证时发现的真实缺口）**：上一条"Feature Flag"规则已经要求Release Toggle"短命，全量发布后必须删除"——据此，**任何引入了Feature Flag的Walking Skeleton故事，任务清单末尾必须显式包含一个"发布收尾"任务**，负责"验收通过后flag全量开启、删除flag判断代码、把本故事新增的访问保护套用到既有相关模块"，不能让"必须删除"只停留在原则性描述上却没有对应的可执行任务、让flag永久留在代码里形成开关债务。这个任务的路由标签通常是`refactor`（需要把新增校验套用到既有模块，跨越认证模块与既有业务模块）；对应验收标准写"AC-1～AC-N回归"（本任务不改变已有业务行为，只要求flag关闭前后行为一致，外加"未授权不可访问受保护路由"这一新增的默认行为）；依赖=该故事其余全部任务（必须等它们都合并后才能派发）。**技术使能故事（无需Feature Flag时）不适用本条规则**，因为没有flag可清理。

**技术使能故事（enabler story）的特殊处理**：故事不面向最终用户业务能力、而是面向团队内部技术能力（如搭建后端脚手架、初始化CI/CD、引入日志框架）时，注意两点，不要机械套用面向业务故事的规则：

1. **路由标签判断依据里"没有可复制的既有模式"，指的是行业内没有成熟范式，不是本仓库恰好还没写过**。仓库自查发现"什么都没有"时，先判断这是(a)行业内都没有成熟范式、真的需要从头设计（→`novel-design`），还是(b)行业早有官方标准做法（框架官方脚手架命令/官方starter模板/官方文档），只是本仓库还没人搭过、复制现成范式即可（→`crud/config`，判断依据写"照官方标准初始化流程完成，不需要自创架构方案"）。误判成前者会连带把AI模式误判成🔴人工主导，把一个照文档初始化就能完成的任务人为拔高复杂度。
2. **没有业务逻辑可切时，用"按基础设施分层"切片**：先让工程跑起来（能启动+健康检查）→ 再加持久层连接 → 再加统一异常处理/日志 → 再加CI流水线……每一层仍要有验收标准，只是用**可执行命令**代替业务断言（如"`mvn spring-boot:run`成功+`curl /health`返回200""`mvn test`通过""CI流水线首次跑绿"）。

**路由建议标签规则（每个任务必须标注）**：标签取值固定为以下八类，不要自创标签名：

- `crud` / `config` / `test-generation` / `simple-ui`：增删改查、配置项、纯补测试、无复杂状态的展示交互——判断依据是"照既有模式复制就能完成，几乎不需要跨文件的架构判断"
- `business-logic`：多分支/状态机/中等复杂业务规则——判断依据是"需要梳理多个条件分支或状态迁移，但改动范围仍在单个模块内"
- `refactor` / `integration`：跨模块改动——判断依据是"改动必然牵扯到2个以上既有模块的接口或数据结构"
- `algorithm` / `novel-design` / `performance-tuning`：算法设计、全新架构方案、性能调优——判断依据是"没有可复制的既有模式，需要从头设计方案"（技术使能故事下这条的适用范围见上一节）
  每个任务标注一个主标签即可（如果同时符合两类特征，选复杂度更高的那一类），并标注证据等级——基于代码库自查得出的标 `[FACT]`/`[INFER]`，仅凭故事文字描述判断的标 `[ASSUME]`。这个标签不影响任务本身的拆分范围，只是下游路由和benchmark统计用的元数据。

**AI模式映射规则（在路由标签同一次自查基础上判定，不新增自查调用）**：每个任务除路由标签外，还要标注AI执行模式（🟢自主执行 / 🟡协作执行 / 🔴人工执行 / 🟣调研任务），供下游批次规划直接使用：

- `crud/config/test-generation/simple-ui` → 默认🟢
- `business-logic` → 默认🟡
- `refactor/integration` → 默认🟡（跨模块天然需要更多协调）
- `algorithm/novel-design/performance-tuning` → 有明确方案时🔴，无方案需要调研时🟣
- **否决规则（优先级最高，覆盖以上所有默认映射）**：任务涉及生产数据迁移、不可逆操作、合规红线，无论复杂度多低，强制标🔴，不能标🟢——这是安全底线，不能被复杂度判断覆盖。

**工时与依赖字段规则**：
- **预计工时**：允许半天粒度（参照故事级"S≈15h, M≈35h, L≈70h"的口径类比到单任务），不强制卡死在小时以内——纵向切片任务天然比横向拆分的单层任务大，硬按小时估算会诱导过度拆分，破坏"每个任务独立可验证、独立成PR"这条更高优先级的原则。
- **依赖**：不做自由文本判断，规则固定为——同故事内任务的依赖=该故事的前一个任务（该故事第一个任务=无，因为纵向切片天然严格线性，后一个任务必然建立在前一个任务之上）；跨故事的依赖=引用下方"跨故事依赖与文件冲突排查"一节的结论，不重复判断。

**跨故事冲突检测规则（多故事场景专属，单故事拆分不需要）**：所有故事的"预计涉及文件"自查完之后，两两比对是否有交集：

- 有交集且是"结构性改动"（如都要改同一张表的schema）→ 抽出来变成一个两个故事共享的前置任务，两个故事各自的任务序列都引用这个共享任务，不能各自重复拆一遍
- 有交集但其中一个故事的改动依赖另一个故事先完成（如故事B要用故事A新建的字段）→ 显式标注"故事B的任务X必须在故事A的任务Y合并后才能派发"，不能假装两个故事互相独立、可以任意顺序执行
- 没有交集 → 两个故事互相独立，可以并行推进，不需要额外处理

**反模式清单**（输出前必须自检，故事内部分）：横向按前端/后端/测试拆顶层任务；把Mock当独立任务立项；测试放最后阶段；对已上线行为做一次性切换；对全新功能强套Expand-Contract；用"故事已经很小"代替PR小批量纪律；批准的PR攒着不合并；Flag忘记清理。

**反模式清单（多故事场景专属）**：两个故事各自拆出了同一份文件的相同改动，没有识别为共享前置任务；故事之间有依赖关系但没有显式标注执行顺序，让调用方误以为可以随意排期；为了赶迭代进度，把本该独立验证的故事硬塞进同一个任务里"顺带做了"，导致这个任务的PR既不对应故事A的验收标准也不对应故事B的。

完整方法论、来源引用、三阶段表格、登录案例演练见：`/mnt/d/Programs/AI文档s/培训方案/核心方案/docs/AI故事任务拆解方法论-从横向分层到纵向安全切片.md`——只在判断细节不确定、需要更深依据时读取，不要凭空展开，不要每次全文复述。

### 任务ID命名规则

沿用 `tasks.md`的编号习惯：`T` + 故事序号（3位，与故事在材料2里出现的序号对齐，如第1个故事→001）+ 该故事内任务序号（2位，从01开始）。例如第1个故事的第2个任务记作 `T00102`。跨故事共享的前置任务（冲突检测识别出来的）编号前缀用 `TSHARED`+两位序号，如 `TSHARED01`，与普通任务区分开。

### 目标与意图

**核心目标**：把迭代内的多个故事，从"故事级黑盒"转成一份可执行、可排期、可勾选追踪的任务清单总览，同时把故事之间的文件冲突与依赖顺序显式暴露出来，而不是让每个故事自己拆自己的、互相看不见。

**具体目标**：

1. **判断有据可查**：每个故事的模式判断（新增/改造）基于代码库实际调查证据，不是凭故事文字臆测
2. **模式选对**：每个故事分别正确判断走 Walking Skeleton 还是 Expand-Contract
3. **任务可执行**：每个任务是一条端到端最小路径，能独立形成一个小PR
4. **验证内嵌**：每个任务自带验收标准，不把测试放到最后一步
5. **发布解耦**：每个故事明确是否需要特性开关及类型（或明确"无需Feature Flag"及理由）
6. **跨故事依赖可见**：迭代内多个故事之间的文件重叠与执行依赖，已被显式排查并标注处理方式，不是各故事自查自的
7. **颗粒度克制**：本方法论的任务清单只到"任务名+验收标准要点+对应AC+预计涉及文件概要+路由建议标签+AI模式+工时+依赖"这个颗粒度，不展开成完整实现说明——完整说明延后到派发前用 `task-implementation-brief` 技能现场生成，避免规划阶段的预判在派发时已经过时
8. **对齐追踪格式**：输出结构对齐 `tasks.md`（Sprint头+故事+checkbox任务），可以直接被迭代追踪机制（如 `sprint-execution-log`）消费，不需要二次转换格式
9. **路由与执行模式可执行**：每个任务的路由建议标签、AI模式、工时、依赖已标注，下游可以直接用于批次规划（拓扑排序+并行冲突过滤），不需要执行前再判断一次，也不需要单独一个技能重新分类

**业务价值**：

- **为迭代规划者/Scrum Master**：迭代开始前拿到一份可直接排期、已排查过冲突的任务清单，不用等到开发中期才发现两个故事撞车
- **为评审者**：每个任务的范围边界有基准线可核对
- **为执行者**：真正接到任务时，能拿到一份基于最新代码库状态生成的实现说明，而不是迭代规划时就过时的预判
- **为模型路由与批次决策**：路由标签、AI模式、依赖字段让"哪些任务能下沉到本地小模型、哪些必须上云端大模型、哪些能并行派发"这些判断在规划阶段就有据可查，不需要靠执行者事后自己感觉，也不需要额外一个技能重新走一遍分类

**成功标准**：

**2. 质量要求**

**可追溯性**：每个任务标注用了哪种切分技巧；模式判断标注调查依据；预计涉及文件概要要能追溯到同一次自查结果；路由建议标签、AI模式要能说明判断依据（复杂度体现在哪，是否触发否决规则）。

**证据分级标注**：模式判断依据、预计涉及文件概要、路由建议标签、AI模式、跨故事重叠判断，统一用 `[FACT]`/`[INFER]`/`[ASSUME]`/`[UNKNOWN]` 四档标注；`[ASSUME]`和 `[UNKNOWN]`必须同步出现在"假设与待确认项汇总"里。

**量化表达**：每条验收标准断言必须具体可判定，不能写"测试通过"这种空话。

**专业术语**：Walking Skeleton、Expand-Contract、Feature Flag 等术语首次出现时用一句话解释。

**3. 格式规范**

- Markdown格式，任务用 `- [ ]` checkbox格式（对齐 `tasks.md`，方便后续直接勾选追踪）
- 不使用emoji装饰、不写"我已经完成了……"这类寒暄——输出是给下游流程消费的，不是聊天
- 任务清单不展开完整实现说明（背景/预计涉及文件全量/技术选型/明确不要做的事/交付要求这些留给`task-implementation-brief`）

**4. 特别说明**

**强制自查规则（不可跳过）**：如果提供了 REPO_PATH，对每个故事分别用 Grep/Glob 搜索该故事涉及的功能关键词，判断代码库里是否已有相关实现；用 `git log` 确认是否有生产环境迭代历史；检查是否已有对应的feature flag配置。不能只凭故事文字描述猜。所有故事自查完成后，必须再做一轮"跨故事文件交叉比对"（拿故事A的自查结果和故事B的自查结果两两比对文件路径，是直接复用每个故事已查到的结果做比对，不需要为此额外发起新的Grep/Glob调用），这一步不能省略，是本方法论与单故事版最大的区别。

**自查范围收敛规则（防止大代码库/多故事叠加下自查消耗过多token甚至超时，不可跳过）**：自查不是"通读仓库"，每个故事的自查必须遵守以下边界：

- **关键词收窄**：只搜索该故事描述与已知验收标准里出现的业务名词，不做与该故事无关的通用扫描。
- **目录收窄**：如果REPO_PATH是monorepo或有明显模块划分（workspaces/packages/services等），优先把搜索范围限定在该故事可能涉及的模块内；无法判断归属模块时才扩大到仓库根目录。
- **单个故事的调用次数上限**：每个故事的自查控制在**8次工具调用以内**（先看目录结构/清单文件判断技术栈边界 → `Grep -l`定位候选文件 → 只对命中最少的1-3个核心文件做完整Read）；多故事场景下，总自查预算等于"故事数 × 8次"，不要因为故事多就无限增加单个故事的探索深度。
- **命中过多时的处理**：某故事关键词命中文件数远超预期，应先收窄关键词/目录重查一次，而不是把所有命中文件读一遍；收窄后仍然过多，允许中止该故事的深度自查，改为基于目录结构做 `[ASSUME]`级推断，并在该故事"调查过程"里如实注明"自查范围因项目规模过大未能穷尽"，不要为查全而无限制增加工具调用，也不要因为一个故事查太深而挤占其他故事的自查预算。

**NEEDS CLARIFICATION 兜底规则**：某个故事查完仍无法确定模式判断，不要猜——在返回结果最开头用 `NEEDS CLARIFICATION:` 起手，写清楚查过什么、卡在哪个具体问题上；同时仍给出一个基于最合理假设的方案（标注假设），不阻塞其他故事的输出。

**禁止编造**：不得编造材料里没有的业务规则或数字，缺的标 `[UNKNOWN]`。

**输出文件**：按上方"输出"表格路径，用 Write 工具写入，并在返回文本里注明写到了哪。

**信息不足的处理**：如果 REPO_PATH 未提供，直接在每个故事的"调查过程"里注明"未提供代码库路径，跳过自查"；跨故事文件冲突排查在没有REPO_PATH时只能基于故事文字描述做粗略判断（标 `[INFER]`或 `[ASSUME]`），必须在"假设与待确认项汇总"里注明"跨故事冲突排查未经代码库验证，建议有REPO_PATH后重新跑一次本方法论校准"。路由建议标签、AI模式在没有REPO_PATH时同样只能基于故事文字描述判断，标 `[ASSUME]`，并在假设清单里注明"路由标签/AI模式未经代码库复杂度验证，建议有REPO_PATH后校准"。

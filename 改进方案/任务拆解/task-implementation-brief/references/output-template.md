# task-implementation-brief · 输出结构模板与颗粒度规则

> **本文件的定位**：替代 `example-output.md` 的"形状锚定"职能。
>
> `example-output.md` 是一份**真实产出**（登录故事 6 个任务），它能锚定详尽程度，但也带来两个副作用：
> ①它与测试用例同题，会把答案（技术选型、文件路径、隐含规则）一并泄露；
> ②它承载的是某个特定仓库的事实，换了代码库或没有代码库时，会被照抄成幻觉。
>
> 本文件把 example 里**隐性的颗粒度基准**转写成**可判定的显式规则**，从而在保留"详尽程度"约束的同时，不再绑定任何具体故事与技术栈。

# 第一部分 · 输出结构模板（硬结构）

每个任务一节，章节顺序如下，**不得增删、不得改序、不得为空**。每个任务之间用 `---` 分隔。

```markdown
## {任务ID}：{任务标题}

你要做的事：{一句话说清本任务交付的具体行为，不用"完成X功能的需求"这类非行为式表述}
对应验收标准：{AC编号（AC原文摘录，逐字，不重新措辞）}

本任务信息自包含：不要假设除下文之外还有更多规划背景，下面就是执行这个任务所需的全部上下文（不管你是被派去执行它的subagent、另一个新对话，还是人工阅读）。

### 执行前必须确认清单
{见规则 Q1–Q6。无则写：本任务无需确认项，可直接开工。}

### 背景
{见规则 B1–B3}

### 预计涉及文件

**必须改动**（本任务范围内确定要动的文件，缺一不可）：
{见规则 F1}

**可能改动**（是否需要动取决于下方"技术选型"章节的决策落地方式，执行时需先确认再动）：
{见规则 F2–F3}

### 技术选型
{见规则 T1–T6}

### 你要做什么
{见规则 W1–W3}

**从验收标准推导出的隐含规则**（必须逐条列出并要求实现，不得遗漏；如无隐含规则，写"无，验收标准字面即完整，无需额外推导"）：
{见规则 H1–H3}

### 明确不要做的事
{见规则 X1–X3}

### 完成定义（DoD）
{见规则 D1–D4}

**CI/CD验收模式：{PR-only 或 CI/CD-verified}**（{注明选择依据}）
{PR-only：不追加额外断言，DoD到"改动通过现有测试、能独立形成PR"为止。
CI/CD-verified：追加一条——"提交的PR已触发现有CI流水线并全部通过，交付报告需附CI运行记录；若发现流水线未覆盖本次改动的关键路径，必须在交付报告里明确指出这个覆盖缺口，不能把'CI绿了'直接当成'这块新逻辑被验证过了'。"}

### 假设与待确认项（如有）
{见规则 C1}

### 交付要求
动手前：先处理《执行前必须确认清单》里标"阻塞"的每一条——获得明确答复，或说明为何在当前条件下可以判定不再阻塞；标"默认生效-可反馈"的条目若无人反对可直接按默认方案动手，无需等待。

改动应能独立形成一个PR，范围只覆盖本任务。完成后返回：实际改了哪些文件（与"预计涉及文件"逐项核对，一致的不用重复说明，不一致的必须说明原因）、"可能改动"清单里的文件最终有没有改、实际采用的技术选型是否与本说明一致（如不一致需说明原因）、新增了哪些测试用例、是否有偏离本任务范围的地方、《执行前必须确认清单》里每一条最终的处理方式（照单执行 / 收到反馈后变更为其他方案及原因）——这份汇报将作为下一个任务生成实现说明时的材料4，请如实填写，不要省略偏差说明。{CI/CD-verified模式下追加：同时附上CI流水线运行记录（链接/截图均可）以及是否发现覆盖缺口。}
```

# 第二部分 · 颗粒度规则

规则编号沿用上文的 `S/Q/B/F/T/W/H/X/D/L/C` 前缀。每条规则给出**判法**（怎么算通过）与**反例**（怎样算不合格）。

## S · 结构

| 编号 | 规则                                        | 判法                        | 反例                               |
| ---- | ------------------------------------------- | --------------------------- | ---------------------------------- |
| S1   | 12 个章节齐备、顺序固定                     | 逐节 grep 章节标题          | 缺《执行前必须确认清单》           |
| S2   | 章节不得为空，无内容时写"无…"式声明        | 每节正文长度 > 0 且非纯标题 | 《隐含规则》下留空                 |
| S3   | `## {任务ID}：{标题}` 必须与材料1逐字一致 | 与材料1字符串比对           | 把"端到端骨架"改写成"E2E 骨架搭建" |

## Q · 执行前必须确认清单

| 编号 | 规则                                                                                                                                                                                                                             | 判法           | 反例                                                                |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------- |
| Q1   | **清单条数 == 正文 `[ASSUME]`/`[UNKNOWN]`/`NEEDS CLARIFICATION` 的决策点数**；同一决策点被多处引用只算一条；`[FACT]` 项**不进**清单                                                                          | 分别计数比对   | 清单 8 条但正文有 11 个决策点；或把 `[FACT]` 的技术选型也塞进清单 |
| Q2   | 每条必须是**可回答的疑问句**（能答"是/否"或"选A/选B"）                                                                                                                                                                     | 句式判定       | `- [ ] Q1 技术选型已收敛` ← 陈述句，不合格                       |
| Q3   | 每条必须标注阻塞类型，**取值只有两种**                                                                                                                                                                                     | 正则匹配       | 出现"待定""看情况"等自造档位                                        |
| Q4   | 每条必须写明"对应正文「{章节名 #序号}」"                                                                                                                                                                                         | 字符串存在性   | 只写问题不写出处                                                    |
| Q5   | 每条必须写明"若不回答/若不反馈：{具体后果}"                                                                                                                                                                                      | 字符串存在性   | 只写"若不反馈：按默认执行"而默认方案是什么没写                      |
| Q6   | 阻塞类型判定：`NEEDS CLARIFICATION` → **阻塞**；"依赖未就绪"类提醒 → **阻塞**；`[ASSUME]` → **默认生效-可反馈**；`[UNKNOWN]` → 看是否导致任务说明本身残缺（残缺→阻塞，不影响开工→默认生效-可反馈） | 逐条对照源标签 | 把 `NEEDS CLARIFICATION` 标成"默认生效-可反馈"                    |

**Q1 的机械化做法**：先数正文里出现过的独立决策点（列一张表），再数清单条数，两边必须相等。这是 SKILL.md 的硬自查项，**必须真的做一遍，不能凭感觉**。

## B · 背景

| 编号 | 规则                                                                                      | 判法               |
| ---- | ----------------------------------------------------------------------------------------- | ------------------ |
| B1   | 必须含：本任务在故事中的位置（第 N/总数）                                                 | 正则 `第\d+/\d+` |
| B2   | 必须含前置状态，**并注明该状态的来源**（材料4 实际交付 / 代码库自查 / 规划预判）    | 关键词判定         |
| B3   | 前置状态若来自**规划预判**而非材料4，必须显式写出"基于规划预判展开，派发前需先核对" | 关键词判定         |
| B4   | 必须含 Feature Flag 状态说明；若故事为"无需Feature Flag"，写明理由                        | 关键词判定         |

## F · 预计涉及文件

| 编号 | 规则                                                                                        | 判法         | 反例                                               |
| ---- | ------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------- |
| F1   | "必须改动"每条 =`路径` + （新增/修改）+ `[证据等级]` + **判定依据或反查结论**     | 四要素齐备   | `` `X.java`（新增） `` ← 缺证据等级与依据，不合格 |
| F2   | "可能改动"每条必须写明**依赖哪个决策**                                                | 含"取决于…" | 只列路径                                           |
| F3   | 无"可能改动"时写穷举声明                                                                    | 固定句式     | 整节留空                                           |
| F4   | 与材料1"预计涉及文件概要"不一致时，必须说明差异原因                                         | 条件触发     | 默默替换                                           |
| F5   | 无 REPO_PATH 时标 `[UNKNOWN]`，并写明"由实现方在交付报告中列出实际改动文件"的强制回填要求 | 条件触发     | 凭想象编路径且不标 `[UNKNOWN]`                   |

## T · 技术选型

| 编号 | 规则                                                                                                                           | 判法                 | 反例                                                                                                                  |
| ---- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------- | --------------------------------------------------------------------------------------------------------------------- |
| T1   | 每条格式：`**{决策点}** → {唯一方案}。依据：{理由}。{证据等级}`                                                             | 结构匹配             | 只写方案不写理由                                                                                                      |
| T2   | 存在竞争方案时，必须写出**为什么不选另一个**                                                                             | 含"不采用/而非/避免" | "会话凭证用自建表" ← 不说为什么不选 JWT                                                                              |
| T3   | **禁止**开放表述：不得出现"由实现方选型""具体方案不限""由实现方自行""可选A或B""二选一"                                   | 全文 grep            | 任一命中即整节不合格                                                                                                  |
| T4   | 决策点必须**穷举**，包括材料没提但"实现时必然要选"的点（例：测试数据来源、本阶段默认值、时间可测试性设计、失败响应形态） | 对照任务清单人工核   | 只写了材料明示的 3 个决策点，漏掉"测试怎么造数据"                                                                     |
| T5   | 确无开放性选型时，写"本任务无开放性技术选型，均为既定实现方式的延伸"                                                           | 固定句式             | 整节留空                                                                                                              |
| T6   | **涉及具体工具/库/语法层行为的断言，未经实际验证（Read 到文档或实测确认）不得标 `[FACT]`**                             | 逐条核查             | 「某驱动版本支持某 SQL 语法」标成 `[FACT]` ← 必须降为 `[ASSUME]`，并补"若实测不支持，可替换为语义等价的实现方式" |
| T7   | 已收敛的决策点，执行者不得在"你要做什么"里另行选择                                                                             | 交叉比对             | 选型说用 A，"你要做什么"里写"可以用 A 或 B"                                                                           |

## W · 你要做什么

| 编号 | 规则                                                                                                                                                                                           | 判法                    |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| W1   | 必须分**后端/前端**交代；不涉及的一端要写明"本任务不涉及"及理由                                                                                                                          | 章节结构                |
| W2   | **颗粒度下限**：凡涉及新增文件/方法/SQL/接口的，必须给出**可直接照抄的签名级细节**——建表语句给 DDL、DTO 给完整类型签名、方法给完整签名、接口给完整路径与注解、请求给完整调用形态 | 抽查 3 处是否有可抄细节 |
| W3   | 每条动作应能对应回"预计涉及文件"里的某个文件                                                                                                                                                   | 交叉比对                |

> ⚠️ W2 是本模板中**最容易被偷工减料**的一条。只写"新增登录接口，校验用户名密码"不算合格，必须写到 `@RestController @RequestMapping("/api/auth")` + `POST /login` + `record LoginRequest(String username, String password)` 这个级别。

## H · 隐含规则

| 编号 | 规则                                                                           | 判法     | 反例                                                               |
| ---- | ------------------------------------------------------------------------------ | -------- | ------------------------------------------------------------------ |
| H1   | 无隐含规则时**必须写明确声明**，不得留空                                 | 非空判定 | 整节留空                                                           |
| H2   | 每条格式：`{规则描述}（{证据等级}）—— 依据材料1/材料2里的哪一条AC推导得出` | 结构匹配 | 只写规则不写推导来源                                               |
| H3   | 规则必须来自 AC 字面**之外**；复述 AC 不算隐含规则                       | 人工核   | AC 写"15分钟后自动恢复"，隐含规则写"15分钟后用户可以再登录"← 复述 |

## X · 明确不要做的事

| 编号 | 规则                                                                                      | 判法                         | 反例                                               |
| ---- | ----------------------------------------------------------------------------------------- | ---------------------------- | -------------------------------------------------- |
| X1   | **必须点名相邻任务 ID 及其范围**（"不要实现X（属于T00xxx）"）                       | 每任务至少 1 处 `属于T\d+` | 只写"不要做超出范围的事"                           |
| X2   | 必须覆盖三类：①同故事相邻任务 ②"技术选型"里已排除的方案 ③本任务不该碰的既有代码/schema | 三类各至少 1 条              | 只写了相邻任务                                     |
| X3   | 依赖未就绪时必须写"若 {依赖} 尚未合并，暂停并报告，不要绕过依赖自行实现"                  | 条件触发                     | 假装依赖已完成                                     |
| X4   | 不得出现与《隐含规则》矛盾的条目（同一行为不能既要求又禁止）                              | 交叉比对                     | 隐含规则要求"埋点四类分支"，排除项写"不要实现埋点" |

**X1 的定量下限**：每个任务该节 **≥3 条**，且至少 1 条点名任务 ID。

## D · 完成定义（DoD）

| 编号 | 规则                                                                                                                                   | 判法       | 反例                                             |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------ |
| D1   | **每条**必须挂 `{证据等级}` + `对应{AC编号}：`                                                                               | 逐条匹配   | `mvn test 均通过` ← 无标签无 AC 号，不合格    |
| D2   | 每条必须**可判定**：含具体数值 / 状态码 / 字段名 / 判定方式，禁止"测试通过""功能正常"                                            | 逐条人工核 | "登录功能正常工作"                               |
| D3   | 《隐含规则》里的**每一条**都要有对应 DoD 断言                                                                                    | 计数比对   | 隐含规则 4 条、DoD 里只覆盖 2 条                 |
| D4   | 数值来源分级：AC 原文直接给的 →`[FACT]`；推算得出的 → `[INFER]`；材料未给靠假设补的 → `[ASSUME]` **并同步写进假设清单** | 逐条溯源   | 15 分钟这个数取自 AC 却标 `[ASSUME]`（或反之） |
| D5   | CI/CD-verified 模式下必须有 CI 记录断言 + 覆盖缺口声明                                                                                 | 条件触发   | 只写"CI 通过"                                    |

## L · 证据标签

| 编号 | 规则                                                                                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| L1   | 四处必须逐条标证据等级：**预计涉及文件、技术选型、隐含规则、DoD**                                                                                            |
| L2   | `[ASSUME]`/`[UNKNOWN]`/`NEEDS CLARIFICATION` 必须**同时**出现在《执行前必须确认清单》（问题句+阻塞类型）与《假设与待确认项》（完整依据）**两处** |
| L3   | 不得用沉默假设替代 `[UNKNOWN]`/`NEEDS CLARIFICATION`                                                                                                           |
| L4   | `[ASSUME]` 必须给出**唯一可执行方案**，不能是"待定"                                                                                                        |

## C · 交叉一致性

| 编号 | 规则                                                          | 判法         |
| ---- | ------------------------------------------------------------- | ------------ |
| C1   | 《清单》↔《假设与待确认项》按**Q 编号一一对应**        | 编号集合相等 |
| C2   | 技术选型决定的行为（如 flag 关闭返回 404）必须有对应 DoD 断言 | 交叉比对     |
| C3   | 《你要做什么》每条能落到《预计涉及文件》某个文件              | 交叉比对     |
| C4   | 排除项与隐含规则不得互相矛盾                                  | 见 X4        |

# 第三部分 · 常见不合格样例（反例库）

以下是真实出现过的错误，生成后应逐条自查是否重蹈：

| # | 反例                                                                                        | 违反规则 | 为什么危险                                                                                                                                                                        |
| - | ------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | 「`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（sqlite-jdbc 版本支持该语法）」标 `[FACT]` | T6       | **SQLite 根本不支持该语法**，实测报 `near "EXISTS": syntax error`；且 `sql.init.mode=always` 下裸 `ADD COLUMN` 二次启动必报 `duplicate column name`。执行方必然踩坑 |
| 2 | 确认清单只覆盖部分 `[ASSUME]` 项，漏掉"是否做时序攻击防护"这类                            | Q1       | 清单形同虚设，等于没做确认这一步                                                                                                                                                  |
| 3 | "明确不要做的事"只写"不要做超出本任务范围的事"                                              | X1       | 执行者无法判断边界在哪，范围蔓延照样发生                                                                                                                                          |
| 4 | DoD 写"登录功能正常工作，测试通过"                                                          | D2       | 不可判定，验收时无法判分                                                                                                                                                          |
| 5 | 技术选型写"会话凭证可以用 JWT 或自建 Session 表，由实现方决定"                              | T3       | 把开放性选择题甩给执行者，正是本技能要消除的东西                                                                                                                                  |
| 6 | 隐含规则整节留空                                                                            | H1       | 无法判断是"确实没有"还是"漏了"                                                                                                                                                    |
| 7 | 有 REPO_PATH 却把材料1的"预计涉及文件概要"原样照抄，未回代码库核实                          | F1       | 规划阶段的预判可能已过时，这是强制自查规则存在的理由                                                                                                                              |
